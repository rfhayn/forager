## Overview

Added a BiLSTM-CRF sequence labeling model to the ingredient parsing pipeline. The model classifies each token in ingredient text (e.g., "2 cups flour") with semantic labels (QTY, UNIT, NAME, MODIFIER, PREP, COMMENT, OTHER). This supplements the existing regex parser with ML-based understanding of ingredient structure.

## Architecture

### 3-Tier Hybrid Parser

```
Input → Regex Parser (fast, deterministic)
          ├── confidence ≥ 0.9 → Return regex result
          └── confidence < 0.9 → ML Parser (CoreML)
                                    ├── confidence ≥ 0.8 → Return ML result
                                    └── confidence < 0.8 → NLP Parser (fallback)
```

**Key design decisions:**
- **Winner-only attribution**: `parserUsed` records which parser's result was returned (not all parsers that ran). This simplifies telemetry analysis.
- **Graceful degradation**: `MLIngredientParser.init?()` returns nil if CoreML model or resources are missing. `HybridIngredientParser` skips the ML tier entirely when this happens (e.g., in test builds).
- **NLP confidence cap at 0.75**: NLP can never beat a moderate regex or ML result. Its value is for completely unstructured inputs where both primary parsers fail.

### ML Pipeline

```
Swift Inference:
  Text → foragerTokenize() → Vocabulary lookup → CoreML emissions → ViterbiDecoder → Labels → Result

Python Training:
  JSONL dataset → BiLSTM-CRF (PyTorch) → Export emissions model (CoreML) + CRF params (JSON)
```

The model is split at the CRF boundary:
1. **BiLSTM emission scorer** → CoreML `.mlpackage` (runs on Neural Engine/GPU)
2. **CRF transition matrix** → `transitions.json` (7×7 matrix + start/end vectors)
3. **Viterbi decoder** → Pure Swift (deterministic, no CoreML dependency)

This split is necessary because CoreML doesn't support CRF layers. The Viterbi decoder is fast (<0.1ms for typical sequences) and benefits from exact floating-point control.

### Tokenizer Contract

The tokenizer is the critical contract boundary between Python training and Swift inference. Any mismatch causes silent accuracy degradation because the model receives different vocabulary IDs than it was trained on.

**TOKENIZER_SPEC.md** (frozen contract):
1. NFKD normalization (not NFD — important distinction)
2. Strip combining marks (diacritics) — matches Python's `encode('ascii','ignore')`
3. Lowercase
4. Whitespace normalization (strip + collapse)
5. Context-aware punctuation splitting (preserve `.` and `/` between digits)
6. Truncate to 64 tokens

**Shared implementation**: `foragerTokenize()` in `IngredientTokenizer.swift`, used by both `MLIngredientParser` (inference) and `ParsingTelemetryService` (correction export).

## Correction Feedback Loop

Phase 7-8 wired a continuous learning pipeline:

1. **Production corrections** → `ParsingCorrectionEvent` (schema v3) logged from 3 edit flows
2. **Export** → `ParsingTelemetryService.exportCorrectionsAsTrainingData()` produces JSONL
3. **Fine-tune** → `retrain_with_corrections.py` merges corrections with base data, fine-tunes with lower LR
4. **Gate** → Model saved only if both primary metrics improve

This is a manual developer workflow in v1 (not automated). Minimum corpus gate: ≥50 corrections.

## Key Gotchas Discovered

1. **NFKD vs NFD**: Swift's `.decomposedStringWithCanonicalMapping` is NFD, not NFKD. Must use `StringTransform("NFKD")` explicitly to match Python's `unicodedata.normalize('NFKD')`.

2. **Combining mark stripping**: After NFKD, `ñ` becomes `n` + combining tilde (U+0303). Python strips with `encode('ascii','ignore')`, Swift needs `CharacterSet.nonBaseCharacters` filtering.

3. **CoreML Neural Engine float16**: `MLMultiArray` from Neural Engine may use Float16 internally. Don't assume contiguous Float32 layout — use subscript access `emissions[[0, t, j] as [NSNumber]]`.

4. **CoreML JIT warmup**: First `prediction()` call triggers 100-500ms JIT compilation. Warm up on background queue in `foragerApp.init()` to avoid main thread stall.

5. **Fraction/decimal context splitting**: Naive punctuation splitting breaks `1/4` → `["1", "/", "4"]` and `14.5` → `["14", ".", "5"]`. Context-aware rule: only split `/` and `.` when NOT between digits.

6. **Test host app crashes**: `@FetchRequest` in SwiftUI views executes against unconfigured test stores. Fixed by keeping `isReady = false` in test mode so the full view hierarchy never renders.
