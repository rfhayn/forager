# Learning Note 41: Import Data Integrity and Category Preservation

**Milestone**: M10.6.9–M10.6.16
**Date**: March 2026
**Scope**: Silent data loss in the recipe import pipeline — category dropping, household scoping, child context pitfalls, state management

---

## Context

The M10.6 import feature appeared to work: recipes imported, ingredients appeared on grocery lists, categories showed in the UI. But across a series of bug reports from M10.6.9 through M10.6.16, a pattern emerged — the import pipeline was silently losing data at nearly every stage. Categories assigned by the AI parser vanished before reaching the grocery list. Household users saw empty template lists. Completed items absorbed new ingredients. None of these failures produced errors or warnings. They all compiled, ran, and looked correct in the simulator.

The unifying theme is **silent data loss**: the system degrades without signaling that anything went wrong. Each fix reinforced a set of defensive patterns that now apply across the entire codebase.

---

## 1. Index vs Name Keys

The first category-dropping bug was a name-matching mismatch between the preview layer and the save pipeline. The import preview built a dictionary keyed by parsed ingredient name — `parsedName.lowercased()` mapped to a category string. When the save pipeline later called `findOrCreateTemplate()`, normalization transformed the name: "diced tomatoes" became "tomato". The dictionary lookup against the original key returned nil, and the category was silently dropped.

```swift
// BUG: name-keyed dictionary breaks when normalization changes the key
var categoryMap: [String: String] = [:]
categoryMap["diced tomatoes"] = "Canned Goods"
// ... later in save pipeline ...
let normalized = normalize("diced tomatoes")  // "tomato"
let category = categoryMap[normalized]         // nil — category lost
```

**Fix**: Pass categories by index — `[Int: String]` where the key is the position in the ingredient array. Index keys are transformation-invariant. No matter how aggressively the normalization pipeline rewrites the ingredient name, the integer index still maps to the correct category.

```swift
// FIX: index-keyed dictionary is immune to name transformations
var categoryByIndex: [Int: String] = [:]
categoryByIndex[0] = "Canned Goods"
// ... later in save pipeline ...
let category = categoryByIndex[0]  // "Canned Goods" — always correct
```

**Principle**: When two pipeline stages transform data independently, never use the transformed data itself as a join key. Use a stable identifier that survives all transformations.

## 2. Category Preservation

Three separate bugs conspired to strip categories from ingredients after initial assignment.

### AI category validation

LLM parsers confidently return categories not in the user's actual list — "Other", "Pantry", "Staples". Strengthening the prompt helped reduce frequency but was never sufficient on its own. The fix was a hard validation gate: every AI-returned category is checked case-insensitively against the user's real category list. Anything not found falls back to nil rather than persisting a phantom category.

### Re-match overwrites user assignments

`reMatchIngredient()` removed explicit user category assignments when re-matching returned a nil category. If a user manually categorized an ingredient and then triggered a re-match (e.g., by editing the recipe), the nil result overwrote their explicit choice.

**Fix**: Only update categories on a positive signal. Never remove on a negative signal. User-explicit state should never be overwritten by absence-of-data.

```swift
// BUG: nil result clears user's explicit category
ingredient.category = reMatchResult.category  // nil overwrites "Dairy"

// FIX: only update when we have a positive signal
if let newCategory = reMatchResult.category {
    ingredient.category = newCategory
}
```

### EditRecipeView re-parse mismatch

`EditRecipeView` re-parsed ingredients from scratch via `IngredientMatchService` instead of consulting the existing `ingredient.ingredientTemplate` relationship. When the re-parsed name differed from the LLM-assigned template name, the match failed and the category was lost.

**Fix**: Nil-coalescing fallback to the existing relationship — `reMatchResult.category ?? ingredient.ingredientTemplate?.category?.name`. Relationships are authoritative; re-derived data is not.

## 3. Grocery Merge and LLM Count Validation

Two bugs in the grocery-list integration path silently dropped or misrouted ingredients.

### Merge skip completed

`findExistingItem()` matched ALL grocery list items including completed ones. A user checks off "flour", then adds a recipe containing flour — the merge silently updated the completed item instead of creating a new one. The flour never appeared as an active grocery item.

**Fix**: Filter out completed items in the existing-item query. Completed items are done; new demand should create new items.

### LLM count mismatch

`tryLLMParsing()` iterated over `llmResults` rather than the input `texts` array. If the LLM returned fewer results than inputs (which happens — LLMs occasionally merge or skip lines), ingredients were silently dropped with no error.

**Fix**: Validate that `llmResults.count == texts.count`. On mismatch, fall back to the local parsing pipeline for the entire batch. A complete local parse is better than a partial AI parse with silent gaps.

## 4. Household Scoping

Household scoping bugs were the most insidious because they were invisible in the simulator.

### Missing householdKey on creation

`HouseholdIngredientTemplateRepository.findOrCreate()` never set `householdKey` on newly created templates. `IngredientsView` filters by `householdKey == currentHouseholdKey`, so these templates were invisible to household users — they existed in the database but never appeared in any query result.

### findByCanonicalName scope leak

`findByCanonicalName()` had no `householdKey` filter. It found templates across all scopes but never updated the `householdKey` field. Templates created before M10.6.11 retained `householdKey = nil` permanently, making them orphans that matched in service code but never appeared in scoped views.

**Fix**: Add `householdKey` filters to all template queries and update `householdKey` on found templates in both the repository and service layers.

### Simulator vs device divergence

The simulator without a configured household masks all scoping bugs. `currentHouseholdKey` is nil, all entities default to nil `householdKey`, and the filter `householdKey == nil` matches everything. The code appears to work perfectly. On device with an active household, `currentHouseholdKey` is a real UUID, and every template missing a `householdKey` disappears.

**Rule**: Household features must be tested on device with an active household. Simulator-only testing for scoped features is insufficient.

## 5. Child Context Pitfalls

Recipe import uses child contexts for atomic saves. Child contexts turned out to be the single largest source of silent data bugs in M10.6.

### Missing householdKey in error paths

`findOrCreateTemplate()` had a fallback catch block that created a new template but never set `householdKey`. Additionally, `awakeFromInsert()` set `householdKey` from `Household.id`, which was nil in child contexts where the household object hadn't been faulted in.

### Redundant saves per ingredient

Callers redundantly called `incrementUsage()` which performed `context.save()` per ingredient. In a child context meant for batch-atomic operations, this triggered partial saves that could leave the database in an inconsistent state if a later ingredient failed.

**Principle**: Child-context error paths are the #1 source of silent data bugs. Every code path in a child context — including catch blocks, fallbacks, and utility methods — must be audited for correct scoping and save behavior.

## 6. State Management

### SwiftUI state race on dismiss

`dismissAfterSave()` called `cancelImport()` synchronously before SwiftUI's `onChange` handler could catch the transient `.saved` state. Both the save-complete and cancel transitions happened in the same `MainActor` turn, so the view never observed the intermediate state.

**Fix**: Use an explicit `onSaveComplete` callback that fires before any state reset. This guarantees the caller can react to the save event before the import state machine resets.

**Principle**: When SwiftUI state transitions depend on observing intermediate values, never collapse two transitions into a single `MainActor` turn. Either use explicit callbacks or introduce a delay between state changes.

## 7. Normalization Pipeline Ordering

M10.6 added two new normalization phases:

- **Phase 0c**: Parenthetical stripping — removes "(diced)", "(14 oz can)", etc.
- **Phase 0d**: Single-character artifact removal — cleans up stray characters left after stripping

Order matters critically. Parenthetical stripping must run before case normalization and pluralization. If pluralization runs first, "Tomatoes (diced)" becomes "tomato (diced)" — the parenthetical is still there, and downstream matching against "tomato" fails because of the trailing content.

```
Correct order:
  Input: "Tomatoes (diced)"
  Phase 0c: "Tomatoes"          ← strip parenthetical first
  Phase 0a: "tomatoes"          ← lowercase
  Phase 0b: "tomato"            ← depluralize

Wrong order:
  Input: "Tomatoes (diced)"
  Phase 0a: "tomatoes (diced)"  ← lowercase
  Phase 0b: "tomato (diced)"    ← depluralize (parenthetical survives)
```

## Defensive Principles

These bugs collectively established a set of patterns that now apply across the forager codebase:

| Principle | Example from M10.6 |
|-----------|-------------------|
| Use stable identifiers as join keys, not transformed data | Index-based category passing instead of name-keyed dictionaries |
| Validate external data against the real source of truth | AI categories checked against actual category list, not trusted blindly |
| Never overwrite explicit state with absence-of-data | Category re-match only updates on positive signal |
| Prefer existing relationships over re-derived data | `ingredient.ingredientTemplate` over re-parsed match results |
| Filter queries to match user-visible state | Skip completed items in merge queries |
| Validate counts when bridging between systems | LLM result count must match input count |
| Audit every child-context code path for scoping | householdKey, save behavior, error-path fallbacks |
| Test scoped features on device, not just simulator | nil == nil passes all filters; real UUIDs expose missing keys |
| Order pipeline phases by dependency | Strip content before normalizing what remains |
| Collapse nothing — let intermediate states be observable | Explicit callbacks before state reset |
