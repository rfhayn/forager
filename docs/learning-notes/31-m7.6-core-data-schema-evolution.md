# Learning Note 31: M7.6 Core Data Schema Evolution & CloudKit Constraints

**Date**: February 12, 2026

**Duration**: ~4 hours across 3 sessions (M7.6.4, M7.6.5, M7.6.6)

## What We Did

Executed a 3-phase Core Data schema cleanup across model versions v3→v4→v5 to remove dead entities, fix misnamed fields, correct cardinality errors, and eliminate code-schema mismatches — all before CloudKit Production locks the schema permanently. This was the first multi-version migration in the project.

---

## Key Learnings

### 1. CloudKit Production Is Append-Only — Clean Up Before You Deploy

CloudKit's Production schema is permanently additive: record types and fields can never be removed or renamed once deployed. Every unused entity and misnamed field becomes permanent baggage.

**What this meant for us**: We had 2 dead entities (`Tag`, `LeaveRequest`), a misnamed field (`ownerEmail` storing a CloudKit record ID, not an email), and 6 unused relationships. All would have been cemented forever in Production. We caught them because we did a comprehensive schema audit before deploying.

**The lesson**: Before your first CloudKit Production deployment, audit every entity, attribute, and relationship. Ask: "Is this used? Is the name correct? Will I regret this being permanent?" This is your last chance for a clean schema.

### 2. Lightweight Migration Is More Capable Than You'd Expect

Core Data's lightweight (automatic) migration handles a surprising range of changes without custom mapping models:

| Change | Supported? | Notes |
|--------|-----------|-------|
| Entity deletion | Yes | Core Data drops the table |
| toOne → toMany cardinality | Yes | Explicitly documented by Apple |
| Add new attributes | Yes | Default values applied |
| Remove attributes | Yes | Data silently dropped |
| Add relationships | Yes | New columns/tables created |
| Remove relationships | Yes | Foreign keys dropped |
| Rename attributes | **No** | Requires `renamingIdentifier` or custom migration |
| Change attribute types | **No** | String→Int requires custom mapping |

We made all three change types in a single migration (entity deletion + cardinality fix + attribute additions/removals) and lightweight migration handled it cleanly. The key test: `NSMappingModel.inferredMappingModel(forSourceModel:destinationModel:)` returns non-nil if Core Data can handle it automatically.

### 3. CloudKit "Renames" Are Really Add + Orphan

CloudKit cannot rename fields. To "rename" `ownerEmail` to `ownerRecordName`, we had to:

1. Add `ownerRecordName` as a new attribute in the Core Data model
2. Write a one-time migration in `performOneTimeSetup()` that copies data from old → new
3. Remove `ownerEmail` from the Core Data model (so the app no longer uses it)
4. Accept that `CD_Household.CD_ownerEmail` persists forever as an orphaned field in CloudKit

**The trade-off**: Two fields exist in CloudKit where one should. This is cosmetic — the orphan contains no new data and costs nothing — but it's permanent. Name your fields carefully the first time.

### 4. Model Versions Are Full Snapshots, Not Diffs

Each `.xcdatamodel` inside `.xcdatamodeld` is a complete schema snapshot, not a delta from the previous version. Core Data needs the old version as the "source" to compute lightweight migrations to the new "destination."

**Critical implication**: Never delete old model versions from your bundle. Core Data compares source (what's on disk) against destination (current version) at runtime. If the source model is missing, migration crashes.

We created v3, v4, and v5 in sequence. A user on v2 migrates v2→v3→v4→v5 transparently. All three intermediate models must ship in the bundle.

### 5. Xcode Silently Rewrites .xccurrentversion

The `.xccurrentversion` plist tells Core Data which model version is active. Xcode maintains this file from its in-memory project state and rewrites it on build. This caused a real crash during M7.6.3:

1. We set `.xccurrentversion` to v5 via file edit
2. Xcode's in-memory state still thought v2 was current
3. On next build, Xcode silently reverted the file to v2
4. App launched with v2 schema, couldn't find the `tags` attribute added in v5 → crash

**The fix**: Either make version changes through Xcode's model inspector (Design → Set Current Version), or close Xcode before editing the file externally. The committed file state is correct, but the build uses whatever Xcode last wrote to disk.

### 6. @NSManaged Properties Without Schema Backing Are Silent Nil

With Manual/None codegen, `@NSManaged` properties that don't exist in the Core Data schema compile successfully but return `nil` at runtime. Core Data uses KVC internally — accessing an undefined key on `NSManagedObject` returns nil rather than crashing.

**How we found it**: `PlannedMeal+CoreDataProperties.swift` declared `household` and `householdKey` properties that didn't exist in the schema. The code compiled, the properties returned nil, and nobody noticed until the schema audit.

**The lesson**: For Manual/None entities, periodically diff your `+CoreDataProperties.swift` declarations against the actual `.xcdatamodel` XML. Compile-time safety doesn't guarantee schema-time correctness. A property can exist in Swift but not in the persistent store, silently returning nil for every access.

### 7. Hack Migrations Are Simpler Than Field Renames

When data is stored via a hack (e.g., tags encoded as `"tags:tag1,tag2"` in `sourceURL`), migrating to a proper field is actually simpler than a CloudKit field rename:

- Add the new `tags` attribute to the schema
- Write an idempotent one-time migration: `WHERE sourceURL BEGINSWITH 'tags:' AND tags == nil`
- Clear the hack from the old field

No CloudKit orphan is created because the data was in a "real" field being used for the wrong purpose. The old field (`sourceURL`) gets cleaned up and can be used for its intended purpose.

**The pattern**: Idempotent predicates (`newField == nil`) make these migrations safe to run repeatedly. Gate with `UserDefaults` flags for efficiency.

## Schema Change Checklist (Validated by M7.6)

Before any Core Data schema change:

1. **Create a new model version** — never edit the current version in place
2. **Check CloudKit implications** — is this additive? Will orphans be created?
3. **Verify lightweight migration** — use `NSMappingModel.inferredMappingModel` in a test
4. **Diff code vs schema** — ensure `@NSManaged` properties match the model XML
5. **Set current version in Xcode** — use the model inspector, not file edits
6. **Keep old model versions** — never delete them from the bundle
7. **Test migration path** — install old version, upgrade, verify data integrity

## Impact on Project

These learnings are captured in ADR 007 (Core Data change process). The schema is now clean for CloudKit Production deployment:

- 2 dead entities removed (Tag, LeaveRequest)
- 1 cardinality bug fixed (Recipe.plannedMeals)
- 1 field renamed via add+migrate+orphan (ownerEmail → ownerRecordName)
- 6 unused relationships removed
- 3 dead attributes removed (titleKey, isFromRecipe, ingredientTemplate)
- 1 hack migrated to proper field (sourceURL tags → Recipe.tags)
- 1 fetch index typo fixed

Total: 3 model versions (v3, v4, v5), all lightweight-migrated, zero data loss.
