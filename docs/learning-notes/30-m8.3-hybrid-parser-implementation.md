# Learning Note 30: M8.3 Hybrid Parser Implementation

**Date**: February 8, 2026
**Context**: Refactoring monolithic parsing into protocol-based hybrid architecture
**Duration**: Single session (~4 hours actual implementation)
**Estimated**: 11 hours (plan) → ~4 hours (actual)

## What We Built

Transformed a monolithic `IngredientParsingService` with 4 regex patterns into a protocol-based hybrid architecture with 7 regex pattern categories and an NLP fallback — without changing a single call site.

---

## Key Learnings

### 1. Pattern Ordering Is a Correctness Concern, Not Just Optimization

The order in which regex patterns are tried determines whether inputs are parsed correctly at all. This bit us during implementation:

**The problem**: Unicode fractions like `½` don't match `[0-9]+`. If the standard numeric pattern runs first, "½ cup sugar" falls through to the name-only fallback with 0.0 confidence.

**The fix**: Unicode fraction detection must run *before* standard numeric patterns. Similarly, range patterns ("2-3") must run before standard because the hyphen confuses the standard parser.

**The lesson**: When building a multi-pattern parser, document the ordering rationale explicitly. Each pattern's position in the priority chain is a correctness invariant, not a performance choice.

### 2. Facade + Strategy = Zero-Disruption Refactors

The entire internal architecture changed (1 monolithic class → 4 protocol-based classes) while all 6 call sites remained untouched. This was possible because:

- `IngredientParsingService` was already the sole public API (good boundary from M3)
- `ParserResult` → `StructuredQuantity` conversion happens inside the service
- The `ParsedIngredient` legacy type is still supported for older code paths

**The lesson**: If your service layer already has clean boundaries, major internal refactors become surprisingly cheap. The M7.5 service layer pattern paid dividends here.

### 3. Confidence Scores as Architectural Routing Signals

Most systems use confidence scores for display only (showing badges, warnings). We used confidence as a **routing decision**: regex confidence < 0.8 triggers NLP consultation. This dual-purpose design means:

- The same value that drives UI badges also drives parser selection
- No separate "should I use NLP?" heuristic to maintain
- Telemetry captures the routing decision implicitly

**The lesson**: When designing confidence/quality scores, consider whether they can serve double duty as control flow signals. It reduces the number of knobs to tune.

### 4. Optional Codable Fields for Schema Evolution

Adding `parserUsed: String?` to `ParsingTelemetryEvent` (a Codable struct persisted as JSON) could have broken deserialization of existing v1 data. But because Swift's `Codable` treats missing keys as `nil` for optionals, v1 JSON files deserialize perfectly into v2 structs.

**The pattern**:
```swift
// v1: no parserUsed field
// v2: add as optional with default nil
let parserUsed: String?  // Missing in v1 JSON → decoded as nil

init(..., parserUsed: String? = nil, ...) // Default parameter for existing callers
```

**The lesson**: For locally-persisted Codable data, prefer adding optional fields over schema migrations. Only use required fields for data that must always be present going forward.

### 5. M8.2 Was Effectively Skipped — And That Was Fine

The plan called for M8.2 (Telemetry Analysis & Strategy) between M8.1 and M8.3. In practice, the PRD's failure analysis was thorough enough that the pattern categories were clear without collecting real telemetry data first. The 6 pattern categories came directly from the PRD's analysis:

- Range patterns (~27% of failures)
- Parenthetical patterns (~18%)
- Qualifier phrases (~15%)
- Compound phrases (~12%)
- Descriptive amounts (~10%)
- Unicode fractions (unknown %)

**The lesson**: When the PRD includes good failure analysis, you don't always need a data collection phase before implementation. The telemetry infrastructure (M8.1) still has value for *post-launch* monitoring, but the implementation priority was clear without it.

### 6. NLP as Safety Net, Not Primary

Early in planning, there was a temptation to make NLP the primary parser with regex as "fast path optimization." The opposite approach proved better:

- **Regex is predictable**: Same input always gives the same output
- **NLP varies by iOS version**: NLTagger behavior can change across OS updates
- **Regex is testable**: Deterministic patterns make unit tests reliable
- **NLP is best for ambiguity**: It shines when regex has no pattern to match

**The lesson**: In hybrid systems, put the deterministic component first. Use the probabilistic component only when the deterministic one signals uncertainty. This makes the system more testable and predictable.

## What Would I Do Differently?

### 1. Cache Compiled Regex Patterns

`RegexIngredientParser` creates `NSRegularExpression` objects on every parse call. These should be `static let` properties, compiled once at app startup. For 100 parses this doesn't matter, but at scale it's unnecessary allocation.

### 2. Consider Regex Builder (Swift 5.7+)

The raw string regex patterns (`#"^(\d+)\s*[-–—]\s*(\d+)..."#`) are hard to read. Swift's `RegexBuilder` DSL would make them more maintainable:

```swift
// Instead of:  #"^(\d+)\s*[-–—]\s*(\d+)\s+(.+)$"#
// Could write:
let rangePattern = Regex {
    Anchor.startOfLine
    Capture { OneOrMore(.digit) }
    Optionally(.whitespace)
    CharacterClass.anyOf("-–—")
    Optionally(.whitespace)
    Capture { OneOrMore(.digit) }
    OneOrMore(.whitespace)
    Capture { OneOrMore(.any) }
    Anchor.endOfLine
}
```

Deferred to avoid scope creep, but worth considering for M9 tech debt.

### 3. Share Unit Lists Between Parsers

Both `RegexIngredientParser` and `NLPIngredientParser` maintain their own lists of known units. These should be extracted into a shared `KnownUnits` utility to prevent drift. Again deferred to avoid scope creep.
