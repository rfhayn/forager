# Learning Note 39: The Recipe Import Pipeline Journey

**Milestones**: M10.1 (URL Import), M10.2 (Text Paste), M10.3 (Photo Import)
**Context**: Building three distinct import paths that all converge on a shared draft-confirm architecture
**Status**: COMPLETE

---

## Overview

Recipe import was the first feature in Forager that had to deal with untrusted, messy, real-world data at scale. Every previous feature assumed structured input — the user types a recipe name, picks a category, enters ingredients one at a time. Import flipped that assumption: the app receives a blob of HTML, pasted text, or a photograph, and has to extract something meaningful from it.

The journey across M10.1 through M10.3 taught hard lessons about the gap between controlled input and wild data, the value of draft-first persistence patterns, and why share extensions are a trap for import workflows.

---

## Part 1: The Draft-First Architecture Decision

### Why Not Just Save Directly?

The most natural approach to import would be: extract data, create a Recipe entity, save to Core Data, let the user edit it later. This is wrong for a subtle reason that only becomes clear when you trace through the persistence layer.

`RecipeService.createRecipe()` calls `context.save()` immediately. This is by design — the service layer pattern (M7.5) ensures every write is persisted atomically. But for import, immediate persistence creates two problems:

1. **Partial data is permanently stored.** If extraction pulls a title and three of seven ingredients, saving creates a broken recipe that syncs to CloudKit and appears on other household members' devices.
2. **No clean cancel path.** Once saved, canceling an import means deleting a recipe that might already be syncing. With CloudKit's eventual consistency, this creates ghost records and sync churn.

### ImportDraftRecipe: The In-Memory Model

The solution was `ImportDraftRecipe` — a plain Swift struct, completely separate from Core Data. Not a subclass of `RecipeFormData`, not an extension of `Recipe`. A standalone in-memory model that holds extracted data until the user explicitly confirms.

The key insight was that `RecipeFormData` was designed for form binding, not import staging. It lacks fields import needs (extraction confidence, source URL, extraction method) and carries form validation constraints that conflict with import's more permissive requirements. Extending it would have muddied two distinct responsibilities.

The pattern: extract into draft, present for review, persist only on confirm. The draft can be modified, discarded, or abandoned with zero Core Data impact.

## Part 2: URL Import (M10.1)

### Strategy Pattern Extractors

Recipe websites are not uniform. Some embed JSON-LD structured data. Some use Microdata. Some are just HTML with no machine-readable markup at all. A single extraction approach would either be too rigid (only handles JSON-LD sites) or too loose (heuristic scraping that breaks constantly).

The `RecipeExtractor` protocol with multiple implementations solved this cleanly. Each extractor attempts extraction and returns nil on failure — the same graceful degradation pattern used by `MLIngredientParser.init?()`. The router tries extractors in order of reliability: JSON-LD first, then Microdata, then heuristic HTML parsing.

### The JSON-LD Title Problem

JSON-LD seemed like the golden path. Structured, standardized, widely adopted by recipe sites. But early testing revealed a frustrating inconsistency: the `name` field in JSON-LD is unreliable.

The NYT Cooking page for "Pasta alla Carbonara (Pasta With Guanciale, Egg, and Black Pepper)" has `"name": "Carbonara"` in its JSON-LD. Technically not wrong — it is carbonara — but useless as a recipe title in a personal collection where you might have three different carbonara recipes.

The fix was a post-extraction title enhancement step that cross-references the JSON-LD `name` against HTML metadata: `<title>`, `og:title`, `<h1>` elements. If the HTML title is a superset of the JSON-LD name (contains it plus additional context), the HTML version wins. This catches the NYT case and similar truncated names without overriding JSON-LD titles that are already complete.

### From Share Extension to In-App Browser

The original plan was a share extension — the standard iOS pattern for "send this URL to my app." Safari's share sheet, tap Forager, done. The implementation worked. Content arrived, extraction ran, a draft was created.

The UX was terrible.

Share extensions are designed for content creation: share a photo to Instagram, send a link to Messages. The interaction model is fire-and-forget. But import is not fire-and-forget. Import needs review, editing, category assignment, confirmation. A share extension that flashes up briefly, does some work, and disappears leaves the user wondering what happened. Did it work? Where did the recipe go? Can I fix the title?

The pivot was to a Paprika-style in-app WKWebView browser. The user browses to a recipe within the app, taps "Import," and immediately sees the extracted data for review. No context switch. No flash-and-disappear. The imported data and the review UI are in the same flow.

A practical note for anyone removing a share extension target: it touches roughly 9 sections of the pbxproj file. Build phases, target definitions, embed entries, scheme references, entitlements. Missing any one of them leaves phantom build artifacts or signing errors. Clean removal requires methodical section-by-section deletion.

### WKWebView Extraction Timing

An early implementation added a 2-second delay after page load to let JavaScript settle before extracting content. This made sense in theory — many recipe sites render dynamically — but was unnecessary for the in-app browser use case.

When the user navigates to a page and taps "Import," they have already waited for the page to render. JavaScript has executed. The DOM is settled. `evaluateJavaScript` returns immediately with the fully rendered content. The 2-second delay was solving a problem that only exists in automated headless extraction, not user-initiated extraction from a live webview.

## Part 3: Text Paste (M10.2)

### Foundation Models Dual Path

M10.2 introduced the first use of Apple's Foundation Models framework in Forager. The architecture is a dual-path system: Foundation Models as primary, heuristic classification as fallback.

When FM is available, the pasted text goes directly to the on-device model, which produces a structured draft. The model handles the ambiguity of free-form text — figuring out which lines are ingredients, which are instructions, what the title might be. When FM is unavailable (older devices, restricted environments), a heuristic classifier takes over, but with a different UX: instead of a ready-to-confirm draft, the user sees a split-screen review UI where they can correct the classification.

The `extractionMethod` field on the draft tracks which path produced the result. This matters for two reasons: telemetry (understanding which path users actually hit) and UX branching (the heuristic path needs more user intervention than the FM path).

### Foundation Models in Extensions: A Dead End

An early consideration was running Foundation Models in the share extension (before it was removed). The `@Generable` macro compiles in extension mode without issues. But the runtime tells a different story: the on-device model requires approximately 1.2 GB to load, and iOS enforces a roughly 120 MB memory limit on app extensions. The model load would be killed instantly.

This was another reason the share extension approach was wrong for import. Even if the UX had been acceptable, the most powerful extraction tool was architecturally unavailable in extension context.

## Part 4: Photo Import (M10.3)

### Document Scanner and OCR

Photo import uses `VNDocumentCameraViewController` for capture, which turned out to be more capable than expected. The returned images are already processed — deskewed, contrast-enhanced, cropped to document boundaries. No need for manual image preprocessing before OCR.

The OCR pipeline uses Vision's `VNRecognizedTextObservation`, which works well but has a coordinate system gotcha that will bite anyone who doesn't read the documentation carefully. `boundingBox` uses normalized coordinates with a **bottom-left origin** — the UIKit/SwiftUI convention is top-left. To sort text observations in reading order (top to bottom), you sort by `1 - boundingBox.origin.y`, not by `boundingBox.origin.y` directly. Getting this wrong produces text in reverse vertical order, which is immediately obvious for recipes but could be subtle for other document types.

### PhotosPicker Privacy

SwiftUI's `PhotosPicker` runs out-of-process. The photo selection UI is rendered by the system, not by the app. This means no `NSPhotoLibraryUsageDescription` is needed in Info.plist — the app never accesses the photo library directly. Only `NSCameraUsageDescription` is required, for the document scanner camera access.

This distinction matters for App Store review. Declaring photo library access when you don't need it raises questions. Using `PhotosPicker` specifically to avoid that declaration is the intended Apple pattern.

## Part 5: Patterns That Emerged Across All Three Paths

### Inline Category Assignment

Early designs had category assignment as a separate modal step after import confirmation. Extract, review, confirm, then a second modal to assign categories. User testing (even informal self-testing) made it clear this was one step too many. Every extra tap between "I want this recipe" and "it's in my collection" is friction.

Moving category assignment inline into the review screen eliminated the extra step. The implementation tracks assignments as `[Int: String]` during preview, maps to `[String: String]` for the save call, and applies them post-save via `applyCategoryAssignmentsAndFinish`. The data flows through three representations because each layer has different key types (array index, ingredient name, Core Data identifier), but the user sees a single unified screen.

### Core Data Replace vs. Delete-Recreate

When re-importing a recipe (updating an existing one), the obvious approach is delete the old Recipe and create a new one from the updated draft. This breaks things.

`PlannedMeal` entities hold relationships to `Recipe`. Delete-recreate gives the new recipe a different `NSManagedObjectID`. Every `PlannedMeal` pointing to the old recipe is now an orphan. With CloudKit sync, the timing is even worse — the delete might sync before the create, leaving household members with broken meal plans.

The correct pattern is in-place update via a child context. Fetch the existing recipe, update its properties, save. The `NSManagedObjectID` is preserved. All relationships survive. `PlannedMeal` references remain valid. This is more code than delete-recreate, but it is the only approach that respects the relational integrity of the data model.

### Validation Limits: Manual Entry vs. Import

Forager's validation had 100-character limits on ingredient names, set during the manual entry era. These limits made sense for typed input — nobody types a 100-character ingredient by hand. Import blew past them immediately.

Real-world recipe ingredients from websites routinely exceed 100 characters: "1 (14.5-ounce) can diced tomatoes with Italian herbs, preferably San Marzano, drained and roughly chopped." The fix was separate validation limits for import context: 250 ingredients per recipe, 300-character titles. The manual entry limits remain tighter because they serve a different purpose (catching input errors vs. accommodating real data).

### PRD Auditing Catches Assumption Gaps

The M10.2 PRD assumed `RecipeFormData` had an `init(from: Recipe)` initializer for populating forms from existing recipes. It did not exist. The PRD was written against an imagined API surface, not the actual code.

This is the strongest argument for the `/forager-prd-audit` workflow. PRDs written more than two weeks before implementation accumulate assumptions that diverge from the codebase. Entity names change, properties get renamed, initializers that seemed obvious never get written. Auditing the PRD against `+CoreDataProperties` files and actual service signatures before implementation catches these gaps when they are cheap to fix — before you have built a feature on top of a method that does not exist.

### Wireframe-to-SwiftUI Mapping

The HTML wireframes created during design (with CSS class names for layout) mapped nearly 1:1 to SwiftUI components. A `div.card` became a `ForagerCard`. A `span.chip` became a `CategoryChipPill`. The CSS flexbox layout translated directly to `HStack` and `VStack` with spacing values.

This was not accidental — the design system (M15) was built with SwiftUI semantics in mind. But it validated that HTML mockups are a viable design tool for SwiftUI apps, especially when the CSS vocabulary mirrors the component library.

## Lessons Learned

### 1. Draft Models Protect Data Integrity

Any feature that ingests external data should stage it in a non-persistent model first. The cost of a draft struct is trivial. The cost of syncing broken data to CloudKit and other devices is significant. This applies beyond import — anywhere the app receives data it does not fully control.

### 2. Share Extensions Are for Sharing, Not Importing

The name says it. Share extensions are optimized for outbound content flows (share this thing to that service). Import is an inbound flow that needs review, editing, and confirmation. The interaction models are fundamentally different. An in-app browser or document picker is almost always the right choice for import.

### 3. Foundation Models Change the Architecture Calculus

FM availability creates a natural dual-path architecture. The FM path can be more ambitious (full structured extraction from ambiguous input) while the fallback path stays conservative (heuristic classification with user review). Designing for both paths from the start avoids the trap of building only for FM and having no fallback when it is unavailable.

### 4. Validation Must Be Context-Aware

A single set of validation rules cannot serve both manual entry and import. Manual entry validation catches user mistakes (typos, obviously wrong values). Import validation accommodates real-world data that is correct but exceeds manual entry assumptions. The validation layer needs to know which context it is operating in.

### 5. Preserve Object Identity on Updates

Whenever updating an existing Core Data object, modify in place rather than delete-and-recreate. Relationships, CloudKit sync state, and any external references depend on stable `NSManagedObjectID`. This is especially critical in a syncing app where the timing of delete vs. create propagation is unpredictable.
