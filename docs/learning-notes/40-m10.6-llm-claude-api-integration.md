# Learning Note 40: M10.6 LLM/Claude API Integration

**Milestone**: M10.6 LLM-Powered Ingredient Parsing
**Date**: March 2026
**Status**: COMPLETE

---

## Overview

Added Claude API integration to forager's ingredient parsing pipeline, enabling LLM-powered parsing as an optional enhancement. Unlike the ML parser (M8.4) which added a tier inside the hybrid pipeline, the LLM operates as a **pipeline bypass** — when enabled, it parses all ingredient lines in a single batch API call, skipping the local regex/ML/NLP chain entirely. On failure, the full local pipeline runs unchanged.

This note covers the architecture decisions, integration patterns, security model, and prompt engineering lessons learned along the way.

---

## Architecture

### Protocol Separation: Why LLM Isn't a 4th Tier

The existing `IngredientParser` protocol is synchronous, per-line, and local-only:

```swift
protocol IngredientParser {
    func parse(_ input: String) -> ParserResult
}
```

The LLM parser is fundamentally different: async, batch-oriented, and network-dependent. Making it conform to `IngredientParser` would have required making the protocol async, which would cascade through 11+ call sites — a massive blast radius for an optional feature.

Instead, `LLMIngredientParser` has its own protocol with `LLMParserResult`. A bridge method `toParserResult()` connects the two worlds at the boundary, converting LLM results into the same `ParserResult` type the rest of the pipeline understands:

```
IngredientParser (sync, per-line, local)
    ├── RegexIngredientParser
    ├── MLIngredientParser
    └── NLPIngredientParser

LLMIngredientParser (async, batch, network)
    └── LLMParserResult.toParserResult() → bridges to IngredientParser world
```

This separation was the right call. The two contracts differ in every dimension. Forcing them together would have created an awkward abstraction that serves neither use case well.

### Pipeline Bypass, Not Pipeline Extension

The LLM integrates at the `RecipeImportService.saveImport()` level, not inside `HybridIngredientParser`. When LLM is enabled:

1. All ingredient lines are sent in one batch API call
2. If the call succeeds, LLM results are used directly
3. If the call fails (network error, malformed response, API key missing), the full local pipeline runs unchanged

This bypass design has several advantages over making the LLM a 4th tier:

- **No async contagion**: `HybridIngredientParser` stays synchronous
- **Batch efficiency**: One API call for 15 ingredients vs. 15 separate calls
- **Clean fallback**: The local pipeline is completely unaware of the LLM's existence
- **Easy to disable**: Toggle off and the code path vanishes entirely

## Integration Pattern

### Facade API: Three Methods, Five Views

Rather than having views import and reference `ClaudeIngredientParser` directly, three methods were added to the existing `IngredientParsingService` facade:

- `isLLMAvailable` — checks both toggle and API key presence
- `parseSingleWithLLM()` — single-line parse for grocery views
- `parseBatchWithLLM()` — batch parse for recipe import

This meant five views needed only about three new lines each to gain LLM support. Views never know about the underlying `ClaudeIngredientParser`. The facade pattern from M7.5 continued to pay dividends — the same pattern that enabled zero-disruption refactors in M8.3 made LLM integration nearly invisible to the UI layer.

### Graceful Fallback in Grocery Views

For grocery list views, LLM parsing is exposed via a sparkle button. The interaction follows an early-return fallback pattern:

1. Try LLM parse
2. If it returns a result, use it
3. If it returns nil (not configured, network failure, bad response), fall back to local parse

The user always gets a result. The worst case is the same quality they would get without the LLM feature at all. No error dialogs, no broken flows — just a silent downgrade to local parsing.

### SwiftUI Async in Context Menus

A small but useful discovery: SwiftUI `.contextMenu` button actions cannot be async directly. The solution is straightforward:

```swift
Button("Parse with LLM") {
    Task { await viewModel.parseWithLLM(text) }
}
```

`Task { await ... }` works for fire-and-forget invocations. `@State` mutations from the async closure update the UI automatically when the view model is `@MainActor`. The blast radius of converting sync call sites to async was minimal — three call sites needed only `Task {}` wrappers since they were already in SwiftUI button handlers.

## Testing Strategy

### MockURLProtocol for Network Isolation

Tests use a `URLProtocol` subclass injected via `URLSessionConfiguration.ephemeral` that intercepts all requests. A static `requestHandler` closure enables per-test response stubbing:

```swift
MockURLProtocol.requestHandler = { request in
    let response = HTTPURLResponse(url: request.url!, statusCode: 200, ...)
    return (response, jsonData)
}
```

This pattern means tests never hit the real Claude API. Every response is deterministic and fast.

### Backoff Timing: Real Delays, Real Tests

Exponential backoff retry tests use real `Task.sleep` and take wall-clock time (~3 seconds). This was an intentional choice — the tests validate actual timing behavior, not just that some delay function was called. For a small test suite this is acceptable. If the suite grows, injecting a clock abstraction would let tests run instantly while still verifying the backoff logic.

## Security and Configuration

### Dual Storage Pattern

Two kinds of data, two storage mechanisms:

- **UserDefaults** for the LLM toggle — fast reads, `@Published` with `didSet` for SwiftUI reactivity
- **Keychain** for the API key — encrypted at rest, appropriate for secrets

The `activeParser()` factory method checks both: toggle must be on AND key must be present in Keychain for the LLM parser to activate.

### Per-User API Keys

Early designs considered storing the API key on the `Household` entity so all household members could share one key. This was removed entirely. Each user enters their own key. The simplicity gain was substantial:

- No security concern about API keys synced via CloudKit shared zones
- No UI complexity for "who entered the key" or "key was changed by another member"
- No permission model for key access

The `Household.llmAPIKey` property remains in the Core Data schema (CloudKit Production is append-only — no destructive changes) but is inert. New code never reads or writes it.

### Dots-Only Masking

The API key display was changed from a partial reveal pattern (e.g., `sk-ant-...xyz`) to dots-only masking. No key content should ever be visible in the UI. Even showing the prefix or suffix leaks information about the key format and could help an attacker narrow the search space.

## Prompt Engineering Lessons

### The Name Pollution Problem

The LLM prompt specified that ingredient names should be in singular form, but did not explicitly exclude unit-like or count words from names. This led to results like:

- "2 cloves garlic" parsed as name: "garlic clove" (the count word "clove" leaked into the name)

The fix required a belt-and-suspenders approach:

1. **Prompt rule**: Explicitly instruct the LLM to exclude unit and count words from names
2. **Normalization**: Suffix stripping in post-processing catches cases where the LLM still gets it wrong

Neither approach alone is sufficient. LLMs follow instructions imperfectly, and normalization rules cannot anticipate every edge case. The combination provides robust coverage.

### OAuth Landscape (Why API Keys)

Before committing to API keys, the OAuth landscape was evaluated:

- **Anthropic**: Banned third-party OAuth (January 2026). API keys are the only option.
- **OpenAI**: OAuth exists for ChatGPT but is backend-to-backend only, not suitable for mobile apps.
- **Google Gemini**: Supports OAuth but the integration is complex.

API keys turned out to be the universal approach — every major LLM provider supports them, and the UX of "paste your key" is simple and well-understood. The per-user key model means forager never handles billing or usage limits; users manage their own API relationship.

## Key Patterns

### Sentinel Value Anti-Pattern

`parseBatchWithLLM()` initially returned `nil` for both "not configured" and "API call failed." This is the sentinel value anti-pattern — the caller cannot distinguish between fundamentally different failure modes. The fix was adding `@Published lastLLMError` to provide specific error reporting. Views that care about the failure reason (e.g., to show a "check your API key" message) can read it; views that just want fallback behavior can ignore it.

### Facade + Strategy for Feature Flags

The combination of the facade pattern (views call `IngredientParsingService`) with the strategy pattern (service internally routes to local or LLM parser) makes the LLM feature trivially toggleable. The toggle in Settings changes which strategy the facade uses. No view code changes when the feature is enabled or disabled.

### Async Conversion Blast Radius

A recurring theme: the blast radius of making a sync method async depends entirely on where it is called. Button handlers and view model methods are already in async-friendly contexts (SwiftUI runs on `@MainActor`). The three call sites that needed updating required only `Task { await ... }` wrappers. If the same method had been called from tight loops or synchronous pipelines, the migration would have been far more disruptive. This validates the bypass design — keeping `HybridIngredientParser` synchronous avoided the worst-case async cascade.
