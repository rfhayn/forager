## 🚨 Problem Statement

### Current Limitations

**After M7.2.2, users can:**
- ✅ Create households
- ✅ Invite members
- ✅ Accept invitations
- ✅ Share all data automatically

**But users CANNOT:**
- ❌ Leave a household (stuck once joined)
- ❌ Remove problematic members (owner has no control)
- ❌ Delete a household (no exit strategy)
- ❌ Rename a household (fixed name forever)
- ❌ See CloudKit storage usage (5GB free limit invisible)
- ❌ Control iCloud sync (no opt-out for privacy)

### User Stories

**Story 1: Roommate Moves Out**
> "My roommate Mike moved out. I want to remove him from our shared household grocery lists. Currently, he still has access to everything and I can't remove him."

**Story 2: Want to Start Fresh**
> "I joined my partner's household but want to start my own. I need to leave their household, but I'd like to keep a copy of the recipes I contributed."

**Story 3: Relationship Ends**
> "My ex and I shared a household. I want to delete the household and keep the recipes we created together in my own account."

**Story 4: Privacy Concerns**
> "I love the app but don't want my data syncing to iCloud. I can't find a way to disable sync and use it locally only."

**Story 5: Storage Confusion**
> "I'm getting 'iCloud storage full' errors. I don't know how much of my 5GB free tier Forager is using."

```swift
// HouseholdService.swift
func removeMember(_ member: HouseholdMember, from household: Household) async throws {
    guard household.isOwner else {
        throw HouseholdError.notOwner
    }

    // 1. Get CKShare
    guard let share = try await getShare(for: household) else {
        throw HouseholdError.noShareRecord
    }

    // 2. Find participant in CKShare
    // Note: This requires CKFetchShareParticipantsOperation
    // Participant matching is by email/userRecordID

    // 3. Remove participant from share
    let participants = share.participants.filter { participant in
        // Match by email or userRecordID
        participant.userIdentity.userRecordID != member.cloudKitRecordID
    }

    // 4. Update share (requires server operation)
    // share.participants is read-only, need to use CKModifyRecordsOperation

    // 5. Delete HouseholdMember record
    viewContext.delete(member)
    try viewContext.save()

    print("✅ Removed member: \(member.displayName ?? "Unknown")")
}
```

```swift
        throw HouseholdError.notOwner

    try await migrateSharedDataToPrivate(household: household)
```

## 🏗️ Technical Architecture

### CloudKit Share Participant Management

**Challenge**: CKShare.participants is read-only from client

**Solution Options:**

**Option A: CKModifyRecordsOperation** (server-side update)
```swift
let operation = CKModifyRecordsOperation()
operation.recordsToSave = [updatedShare]
operation.modifyRecordsCompletionBlock = { saved, deleted, error in
    // Handle result
}
cloudKitContainer.privateCloudDatabase.add(operation)
```

**Option B: Delete and Recreate Share** (nuclear but reliable)
```swift
// 1. Delete old share
try await cloudKitContainer.privateCloudDatabase.delete(withRecordID: oldShare.recordID)

// 2. Create new share without removed participant
let newShare = try await container.share([household], to: nil)

// 3. Manually add back desired participants
// (complex - requires CKFetchShareParticipantsOperation)
```

**Recommendation**: Start with Option A (proper API), fall back to Option B if needed.

### Data Migration (Shared → Private)

**Architecture from M7.2.3:**
```swift
// Use existing ManagedObjectFactory pattern
// Change scope for all entities:

// BEFORE (in shared store):
factory.createRecipe(scope: .household(household))

// AFTER (in private store):
factory.createRecipe(scope: .private)
```

**Migration Process:**
```swift
func migrateSharedDataToPrivate(household: Household) async throws {
    let context = persistence.newBackgroundContext(for: .userEdit)

    // Fetch all household-scoped entities
    let recipes = try context.fetch(Recipe.fetchRequest()).filter {
        $0.household == household
    }
    let lists = try context.fetch(WeeklyList.fetchRequest()).filter {
        $0.household == household
    }
    // ... etc for all entity types

    // Create copies in private store
    for recipe in recipes {
        let privateRecipe = factory.createRecipe(
            scope: .private,
            title: recipe.title,
            // ... copy all properties
        )

        // Copy relationships (ingredients, etc.)
        for ingredient in recipe.ingredients {
            let privateIngredient = factory.createIngredient(
                scope: .private,
                // ... copy properties
            )
            privateRecipe.addToIngredients(privateIngredient)
        }
    }

    try context.save()
    print("✅ Migrated \(recipes.count) recipes to private store")
}
```

**Challenges:**
- Preserve all relationships (recipes → ingredients, lists → items)
- Handle large datasets (batch operations)
- Progress indication for user
- Rollback on failure

### Sync Controls Architecture

**State Machine:**
```
Sync Enabled (default)
├── User can join households
├── Data syncs across devices
└── CloudKit active

Sync Disabled (local-only mode)
├── Cannot join households
├── No multi-device sync
├── CloudKit container nil
└── Data stays local
```

**Persistence Config:**
```swift
if SyncSettings.syncEnabled {
    // CloudKit enabled
    description.cloudKitContainerOptions = NSPersistentCloudKitContainerOptions(
        containerIdentifier: "iCloud.com.richhayn.forager"
    )
} else {
    // Local-only mode
    description.cloudKitContainerOptions = nil
}
```

**Restart Required:**
NSPersistentCloudKitContainer configuration happens at init. Changing sync settings requires app restart to take effect.

**UX:** Show alert: "Restart Forager for changes to take effect"
