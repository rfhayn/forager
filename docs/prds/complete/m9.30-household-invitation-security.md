# M9.30: Household Invitation Security Hardening

**Status**: ⏳ PLANNED
**Estimated**: 3-5 hours (5 phases)
**Priority**: Launch-blocking (CRITICAL + HIGH severity findings)
**Depends On**: None
**Last Updated**: March 22, 2026

---

## Problem Statement

Security audit of the household sharing system identified **2 CRITICAL and 6 HIGH severity vulnerabilities**:

### CRITICAL
1. **`publicPermission = .readWrite` is permanent** — Once an invitation URL is created via `createOneTimeInvitationURL()`, the CKShare's public permission is set to `.readWrite` and never reverted. Anyone with the URL gets full read/write access to the entire household — forever. A single leaked URL compromises all recipes, grocery lists, meal plans, and the API key.

2. **API key stored in plaintext in Core Data** — The owner's Claude API key is stored unencrypted in `Household.llmAPIKey`, synced to all members via CloudKit. A removed member retains the key in their local SQLite database.

### HIGH
3. No invitation URL expiration — share URLs valid indefinitely
4. No way to revoke/cancel an invitation without deleting the household
5. Any participant can modify/delete the Household entity (CloudKit `.readWrite`)
6. Any member can read the owner's API key from the Household entity
7. Role checking is client-side only (CloudKit limitation)
8. View-layer `@FetchRequest` lacks `householdKey` predicates (ghost data risk)

---

## Solution: 5 Security Fixes

### Phase 1: Schema v10 + 24-Hour Invite Expiration (1-1.5h)

**Core Data model v10**: Add `invitedDate: Date?` to HouseholdMember entity.

When a pending member is created during `createOneTimeInvitationURL()`, set `invitedDate = Date()`. On acceptance, check if `Date().timeIntervalSince(invitedDate) > 86400` (24 hours) — reject if expired.

**Cleanup**: On app launch, `cleanExpiredInvitations()` deletes all pending HouseholdMember records older than 24 hours.

**Computed property**: `HouseholdMember.isExpired` — true when pending AND `invitedDate` is >24h ago.

### Phase 2: Revert publicPermission After Acceptance (0.5-1h)

**CRITICAL: Permission revert is owner-only.** Only the CKShare owner can modify `publicPermission`. This code MUST be guarded by `isOwner` check — member devices cannot modify the share and will throw.

**Owner-side flow**: Create a dedicated `revertPublicPermissionIfNeeded(household:)` method, called from the owner's polling path (after detecting a new participant). NOT embedded in the member-side `checkForAcceptedInvitations()`.

**Cancel individual invitation**: New `cancelInvitation(member:)` method — deletes the pending HouseholdMember. If no more pending members exist, also reverts `publicPermission = .none`. Owner-only.

**Revoke all invitations**: New `revokeAllPendingInvitations(household:)` method — deletes all pending members and sets `publicPermission = .none`. Owner-only.

**UI**: Swipe-to-cancel on pending member rows in HouseholdMembersView. "Revoke All Invitations" button when pending members exist.

### Phase 3: 10-Member Cap (0.5h)

Validate total members (accepted + pending) before generating URL:
```swift
let acceptedCount = share.participants.count
let pendingCount = household.memberArray.filter { $0.isPending && !$0.isExpired }.count
guard acceptedCount + pendingCount < 10 else { throw .memberCapReached(10) }
```

**Note**: `share.participants` only includes accepted members (public link sharing doesn't add pending CloudKit participants). Pending members are tracked only in HouseholdMember Core Data records. The cap must check BOTH.

New error: `HouseholdError.memberCapReached`.

### Phase 4: API Key Encryption with AES-GCM (1-1.5h)

Encrypt the API key before storing in `Household.llmAPIKey` using AES-GCM with a random encryption key stored in Keychain.

```
Owner saves API key:
    → Generate random 256-bit encryption key (once per household, stored in owner's Keychain)
    → AES.GCM.seal(plaintext, key) → nonce + ciphertext + tag
    → Base64 encode → store in Household.llmAPIKey
    → Share encryption key with members via separate Keychain-synced mechanism

Member decrypts:
    → Read encryption key from local Keychain (received during household join)
    → AES.GCM.open(ciphertext, key) → plaintext
```

**Security review finding**: Using household UUID as key derivation input provides NO protection against a removed member who already has the UUID and cached ciphertext. Instead, use a random key stored in Keychain:

- **Owner**: Generates random key, stores in Keychain, encrypts API key
- **Members**: Receive the encryption key during household join (passed via the existing HouseholdMember record or a dedicated key-exchange field)
- **On member removal**: Owner generates new random key, re-encrypts API key. Removed member's cached ciphertext is now undecryptable (they don't have the new key)
- **Race window**: Between removal and CloudKit purge, the old ciphertext is still locally cached — but without the new key, it's useless

**Alternative (simpler)**: Accept that CloudKit access revocation IS the security boundary. Encrypt with household UUID for defense-in-depth against casual SQLite snooping only. Document the threat model honestly.

**Migration**: On first launch after update, detect unencrypted key and encrypt in place.

### Phase 5: Duplicate Invite Prevention (0.25h)

Use the already-defined `HouseholdError.alreadyMember` and `.invitationPending` error cases (currently defined but never thrown). Add checks in `createOneTimeInvitationURL()` before generating URL.

## Security Model After Fixes

| Vector | Before | After |
|--------|--------|-------|
| Leaked invite URL | Full access forever | Expires in 24h, owner can revoke |
| Multiple joins from same URL | Unlimited | Permission reverts to `.none` after first acceptance |
| API key exposure | Plaintext in CloudKit | AES-GCM encrypted, rotated on member removal |
| Unlimited members | No cap | 10 member maximum |
| Stale pending invites | Live forever | Auto-cleaned after 24h |
| No cancellation | Delete household only option | Swipe-to-cancel + Revoke All |
