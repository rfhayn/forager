**Status**: READY
**Priority**: Critical (blocks core app functionality)
**Estimated**: 4-6 hours (3 phases)
**Branch**: `bugfix/M9.14-household-scope-fixes`

**Reported From**: Build 30 TestFlight — fresh install while remaining household member

## Problem Statement

After deleting and reinstalling forager (build 30) while remaining a member of an existing household via CloudKit, two critical creation flows fail silently:

1. **Meal plan creation fails** — tapping "Create Your First Plan" or "+" does nothing
2. **Grocery list creation from recipe fails** — "Add Selected" from Add to Grocery List does nothing

Both features worked in previous builds. The regression was introduced in **M9.13** (ManagedObjectFactory enforcement), which routed all HouseholdScoped entity creation through `ManagedObjectFactory.make()`. The factory throws in Release builds when household scope resolution fails, and callers silently swallow the error.

Additionally, two non-blocking bugs were identified:
3. **HTML entity encoding in recipe titles** — `&amp;` displayed instead of `&`
4. **Ingredient name parsing discrepancy** — AI parse shows "beef" but template saves as "lean ground beef" (review only, may be working as designed)

---

## Reproduction Steps

### Setup
1. Be a member of an existing household
2. Delete the forager app
3. Reinstall from TestFlight (build 30)
4. Launch app — CloudKit syncs household data to shared store

### Bug 1: Meal Plan Creation
1. Navigate to Meals tab
2. Tap "Create Your First Plan" or "+"
3. Fill in dates, tap "Create"
4. **Expected**: Meal plan appears in list
5. **Actual**: Nothing happens, stays on empty state. `validationError` shows "Failed to create meal plan. Please try again."

### Bug 2: Grocery List from Recipe
1. Import a recipe (import works correctly)
2. Tap "Add to Grocery List" from recipe detail
3. Select ingredients, tap "Add Selected"
4. **Expected**: Grocery list created with selected ingredients
5. **Actual**: Nothing happens, returns to Lists tab showing "No Grocery Lists"

### Bug 3: Ampersand Encoding
1. Import recipe from URL containing `&` in site name (e.g., saltandlavender.com)
2. **Expected**: Title shows "Salt & Lavender"
3. **Actual**: Title shows "Salt &amp; Lavender" in recipe list and detail views

## Root Cause Analysis

### Bugs 1 & 2: Silent Factory Failure in Release Builds

**The failure chain:**

```
User action → Service.create() → factory.make(Entity.self)
  → HouseholdScopeProvider.activeScope
    → householdService.currentHousehold exists ✓
    → household.objectID.persistentStore exists ✓
    → storeURL.contains("shared") → true → .household(id, .shared)
  → ManagedObjectFactory.make() in .household scope
    → context.assign(object, to: sharedStore) ✓
    → context.existingObject(with: householdID)
      → FAILS: throws or returns wrong type
    → Release: throws FactoryError.householdNotFound
  → Service catches error, returns nil
  → View receives nil, shows generic error or does nothing
```

**Key code locations:**

| File | Lines | Issue |
|------|-------|-------|
| `ManagedObjectFactory.swift` | 230-254 | `context.existingObject(with: householdID)` fails for objects synced from CloudKit with potentially stale ObjectIDs |
| `MealPlanService.swift` | 169-174 | Catches factory error, returns nil. Only prints in DEBUG. |
| `AddIngredientsToListView.swift` | 387-390 | Catches factory error, falls back to `weeklyListService.createList()` — but that likely also fails for same reason |
| `HouseholdScopeProvider.swift` | 87-128 | Resolves to `.household` scope correctly, but the ObjectID it passes may be from a CloudKit-synced context that doesn't survive reinstall cleanly |

**Why this regressed in M9.13**: Before M9.13, all code used direct `Entity(context:)` which bypasses store assignment entirely. The entities would be created in whatever store the context defaulted to (usually private). M9.13 correctly enforced factory routing, but the factory's `.household` path is fragile — it assumes `context.existingObject(with:)` will always succeed for the household ObjectID, which isn't guaranteed after a fresh CloudKit sync.

**Likely specific failure**: After reinstall, the Household entity syncs from CloudKit. The `HouseholdService.loadCurrentHousehold()` fetches it and sets `currentHousehold`. But the `objectID` stored in `DataScope.household(id:, storeID:)` may become stale if the context resets or the persistent store coordinator renegotiates object IDs during CloudKit sync reconciliation. When `factory.make()` later calls `context.existingObject(with: thatObjectID)`, it throws `NSObjectNotReachable` or returns nil.

### Bug 3: Missing HTML Entity Decoding in OG Title Extraction

**File**: `Services/Import/RecipeJSONLDExtractor.swift`, lines 360-378

The `extractMetaOGTitle(from:)` method extracts the `og:title` meta tag content via regex but does **not** pass the result through `HTMLEntityDecoder.decode()`. When the HTML contains `&amp;` in the og:title attribute, it's returned raw.

The `enhanceTitleFromHTML()` method at line 335 then replaces the (already decoded) JSON-LD title with this un-decoded og:title, reintroducing the entity.

Same issue exists in `extractTitleTag(from:)` at line 381.

### Bug 4: Ingredient Name Parsing Discrepancy (Review Only)

**Observed**: Pre-parse shows "lean ground beef" → AI parse returns "beef" → final template is "lean ground beef"

**Analysis**: This is likely working as designed through fallback behavior:
- The local parser (tier 1 regex) correctly parses "lean ground beef" as the ingredient name
- The AI parser simplifies to "beef" (arguably too aggressive)
- During save, `IngredientTemplateService.findOrCreateTemplate()` may match an existing "lean ground beef" template created by the local parse pass, or the LLM result may have been discarded in favor of the local parse during the actual import save

**Recommendation**: No code fix needed. Document as known AI parsing behavior. If the user wants tighter AI→template alignment, that's a future M8.x enhancement.

## Proposed Fixes

### Phase 1: Diagnose and Fix Entity Creation (2-3h) — CRITICAL

**Goal**: Make MealPlan and WeeklyList creation work reliably when user is in a household after reinstall.

#### P1.1: Add Resilient Household Resolution to ManagedObjectFactory

**File**: `Services/Persistence/ManagedObjectFactory.swift`

Current code at line 231:
```swift
guard let household = try context.existingObject(with: householdID) as? Household else {
    throw FactoryError.invalidHouseholdObjectID
}
```

**Fix**: Add a fallback fetch when `existingObject(with:)` fails:
```swift
// Try direct object resolution first
var household: Household?
do {
    household = try context.existingObject(with: householdID) as? Household
} catch {
    // Fallback: ObjectID may be stale after CloudKit sync/reinstall.
    // Fetch household by predicate instead.
    let request: NSFetchRequest<Household> = Household.fetchRequest()
    request.fetchLimit = 1
    household = try context.fetch(request).first

    #if DEBUG
    print("⚠️ Factory: existingObject(with:) failed, used fetch fallback")
    #endif
}

guard let resolvedHousehold = household else {
    throw FactoryError.householdNotFound(householdID)
}
```

**Rationale**: The household exists in the store — the ObjectID reference is just stale. A simple fetch is a reliable fallback.

#### P1.2: Add User-Visible Error Surfacing in MealPlanService

**File**: `Services/MealPlanService.swift`

Current code at line 169-174 silently returns nil. Fix:
```swift
} catch {
    #if DEBUG
    print("⚠️ Factory error creating MealPlan: \(error)")
    #endif
    lastError = error
    errorMessage = "Unable to create meal plan: \(error.localizedDescription)"
    return nil
}
```

Ensure `errorMessage` is `@Published` and the view observes it.

#### P1.3: Verify WeeklyList Creation Path

**File**: `forager/Views/Grocery/AddIngredientsToListView.swift`

The fallback at line 391 (`weeklyListService.createList()`) also needs factory resilience. Verify that `WeeklyListService.createList()` either:
- Uses the factory with the same resilient fallback, OR
- Can create lists without factory when factory throws

#### P1.4: Add Defensive Re-fetch in HouseholdScopeProvider

**File**: `Services/Persistence/HouseholdScopeProvider.swift`

After getting `household.objectID`, verify the object is still valid before passing the ID downstream:
```swift
// Verify object is still reachable in current context
guard !household.objectID.isTemporaryID,
      household.managedObjectContext != nil else {
    // Household object became invalid — trigger re-load
    return .personal
}
```

### Phase 2: Fix HTML Entity Decoding (30min) — MODERATE

**Goal**: Decode HTML entities in extracted og:title and title tags.

#### P2.1: Decode og:title

**File**: `Services/Import/RecipeJSONLDExtractor.swift`, line 372

After extracting the content string, apply HTMLEntityDecoder:
```swift
let content = nsHTML.substring(with: match.range(at: 1))
    .trimmingCharacters(in: .whitespacesAndNewlines)
let decoded = HTMLEntityDecoder.containsEntities(content)
    ? HTMLEntityDecoder.decode(content)
    : content
if !decoded.isEmpty { return decoded }
```

#### P2.2: Decode title tag

**File**: `Services/Import/RecipeJSONLDExtractor.swift`, line 382+

Same treatment for `extractTitleTag(from:)` return value.
