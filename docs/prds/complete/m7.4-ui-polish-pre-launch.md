## Major Feature: Custom Bottom Navigation (Apple Music Pattern)

### Problem Statement

The app was using standard iOS TabView with 6 tabs (Lists, Ingredients, Recipes, Meal Plans, Categories, Settings). This created several issues:

1. **5-Tab Limitation**: iOS automatically creates a "More" tab when >5 tabs exist, hiding Categories and Settings in a generic list
2. **No Search Integration**: Search functionality existed on individual screens (`.searchable()`) but not at the navigation level
3. **Inconsistent Search**: Each tab had its own search implementation with different behaviors
4. **Generic Appearance**: Standard TabView looks like every other iOS app - no distinctive character

### Design Goal

Create an Apple Music-style navigation system that:
- Groups 4 main content tabs (Lists, Ingredients, Recipes, Meal Plans) in a pill-shaped container at the bottom
- Provides a separate circular search button next to the pill
- Expands search inline when tapped (pill collapses, search bar expands with home button)
- Uses translucent materials (iOS 26 Liquid Glass aesthetic)
- Works seamlessly in both light and dark mode
- Moves Settings and Categories to a hamburger menu in the top-left corner

---

---

#### Iteration 7: Material Backgrounds (Dark Mode Fix)
**What was built**: Replaced all `systemBackground.opacity()` backgrounds with `.regularMaterial` - Apple's adaptive translucent material.

**Why this works**:
- `.regularMaterial` automatically adapts to light/dark mode
- Provides contextual blur based on background content
- Aligns with iOS 26 Liquid Glass design system
- Maintains readability through dynamic vibrancy

**Before**:
```swift
.background(Color(.systemBackground).opacity(0.95))
// Problem: systemBackground is black in dark mode, opacity just makes it slightly transparent black
```

**After**:
```swift
.background(Capsule().fill(.regularMaterial))
// Solution: Adaptive material that works in both light and dark
```

**Feedback**: ✅ Much better!

**Result**: Proper dark mode support achieved

---

#### Iteration 8: Keyboard Interaction
**What was built**: Search button auto-focused keyboard on tap.

**Feedback**: *"there is a problem. when i click the search button a keyboard pops up and blocks the search bar. I want it to behave like apple music where clicking the search button opens the pill search bar and then when the user clicks into the search bar the keyboard comes up and moves the screen"*

**Result**: Two-step interaction - button expands bar (no keyboard), tapping field shows keyboard

**Code change**:
```swift
// Before: Auto-focus keyboard
Button {
    isSearchActive = true
    isSearchFocused = true  // ❌ Keyboard blocks search bar
}

// After: Two-step interaction
Button {
    isSearchActive = true
    // Don't focus yet - let user tap the field to show keyboard ✅
}
```

---

#### Iteration 9: Keyboard Avoidance
**What was built**: Removed `isSearchFocused = true` from search button action.

**Feedback**: *"the search fix is close, but when the user clicks on the search bar, the screen doesn't move/adjust and the search bar gets hidden behind the pop up keyboard"*

**Problem**: Line 40 of CustomBottomNavigationView had `.ignoresSafeArea(.keyboard, edges: .bottom)` which explicitly prevented iOS from adjusting the layout when the keyboard appears.

**Result**: Removed `.ignoresSafeArea(.keyboard, edges: .bottom)` to enable iOS's natural keyboard avoidance behavior - navigation bar slides up when keyboard appears.

**Key insight**: Apple's default behaviors are usually correct. The modifier was fighting against helpful OS behavior.

## Follow-up Fix: Ingredients Tab Button Sizing

**Problem**: On the Ingredients tab filter section, the buttons had sizing issues:
1. "All Categories" button text was cut off/truncated
2. "Staples First" button was verbose and should just say "Staples" (it's in the sort menu, not describing staples)

**Solution**: Created a size-aware FilterPill component with three size variants.

### Implementation

Added `Size` enum to FilterPill:
```swift
enum Size {
    case compact, regular, large

    var horizontalPadding: CGFloat {
        switch self {
        case .compact: return 8   // Smaller
        case .regular: return 10  // Default
        case .large: return 14    // Bigger
        }
    }

    var verticalPadding: CGFloat {
        switch self {
        case .compact: return 5
        case .regular: return 6
        case .large: return 7
        }
    }

    var fontSize: Font {
        switch self {
        case .compact: return .caption2
        case .regular: return .caption
        case .large: return .caption
        }
    }
}
```

### Changes Made

1. **Changed Sort Option Display Name**:
   - Line 552: `case .staplesFirst: return "Staples First"` → `return "Staples"`
   - Shorter text fits better in compact button

2. **Added Size Parameter to FilterPill**:
   - Made size parameter with default `.regular` for backward compatibility
   - Added `.fixedSize()` to text to prevent truncation

3. **Applied Size Variants**:
   - Category filter (All Categories): `.large` - most prominent, more padding
   - Staples toggle filter: `.regular` - middle size for visual balance
   - Sort filter (Staples/A-Z/etc): `.compact` - smallest, less visual weight

**Visual hierarchy**: Large → Regular → Compact creates natural emphasis on category selection (most commonly used filter).

## Technical Decisions

### Why .regularMaterial Instead of Opacity?

**Initial approach**: `Color(.systemBackground).opacity(0.95)`

**Problem**:
- In light mode: systemBackground is white, opacity works okay
- In dark mode: systemBackground is black, opacity just makes it slightly transparent black
- No adaptivity, no vibrancy, no contextual blur

**Solution**: `.regularMaterial`

**Why it's better**:
- Automatically adapts to light/dark mode
- Provides contextual blur based on background content
- Aligns with iOS 26 Liquid Glass design system
- Maintains text readability through dynamic vibrancy layers
- Apple's built-in solution for translucent UI

---

### Why Two-Step Search Interaction?

**User expectation**: *"I want it to behave like apple music where clicking the search button opens the pill search bar and then when the user clicks into the search bar the keyboard comes up and moves the screen"*

**Implementation**:
1. **Step 1**: Tap search button → `isSearchActive = true` (bar expands, pill collapses)
2. **Step 2**: Tap search field → `@FocusState` triggers, keyboard appears, iOS naturally pushes navigation bar up

**Why not auto-focus?**
- Gives user control over when keyboard appears
- Prevents keyboard from blocking the search bar before user is ready
- Matches Apple Music's behavior
- Reduces unexpected UI changes

**Key insight**: Removing `.ignoresSafeArea(.keyboard, edges: .bottom)` enables iOS's built-in keyboard avoidance behavior. The default is almost always correct - modifications should be minimal and intentional.

---

### Why Hamburger Menu Instead of TabView "More"?

**Problem**: With 6 tabs, iOS automatically creates a "More" tab that shows items 5+ in a generic list with poor UX.

**Solution**: Hamburger menu (☰) in top-left corner gives explicit control over secondary navigation.

**Benefits**:
- Settings and Categories remain easily accessible
- Don't clutter main navigation
- Familiar pattern from other apps
- Consistent with sheet-based modal presentation throughout app

**Trade-off**: Requires one extra tap vs dedicated tab, but worth it for cleaner main navigation.

## Web Research: Apple Music Search & Liquid Glass

During implementation, web research was conducted to understand Apple Music's search pattern and iOS 26 Liquid Glass design system.

### Apple Music Search Pattern

- **Two-step interaction**: Tap button to expand bar, tap field to show keyboard
- Search bar stays **anchored at bottom** of screen
- Keyboard pushes content up rather than covering search UI
- Material backgrounds with translucent blur
- Smooth spring animations for expansion/collapse

**Our implementation matches this pattern exactly.**

---

### iOS 26 Liquid Glass Design System

**What it is**:
- New material design system introduced in iOS 26 (currently in beta)
- Translucent materials that dynamically adapt to background content
- Contextual blur that changes based on what's behind it
- Vibrancy layers ensure text/UI maintains readability

**Key APIs**:
- `.regularMaterial` - Standard translucent background
- `.thinMaterial` - More transparent
- `.ultraThinMaterial` - Very subtle
- `.ultraThickMaterial` - More opaque

**Known challenge**:
iOS 26 Liquid Glass has had some usability issues with text disappearing into translucent backgrounds in certain lighting conditions. Apple added transparency controls in iOS 26.2 to address this.

**Our use**:
We use `.regularMaterial` throughout, which is the recommended default for navigation and control surfaces. The stroke borders (`.strokeBorder(Color.primary.opacity(0.15))`) help with definition and work around the visibility challenge.

**Our implementation aligns perfectly with Liquid Glass principles.**

## Lessons Learned

### 1. Visual Iteration Works for UI Polish

Ad-hoc implementation with continuous visual feedback was **highly effective** for this type of work. Screenshots from the device in different lighting conditions revealed issues (dark mode, consistency, keyboard behavior) that would be impossible to catch in upfront planning.

**Takeaway**: For UI/UX work, rapid iteration with real device testing beats extensive planning.

---

### 2. Start with Apple's Defaults

The keyboard avoidance issue was solved instantly by **removing** a modifier (`.ignoresSafeArea(.keyboard, edges: .bottom)`). Apple's default behaviors (keyboard avoidance, material backgrounds, safe areas) are the result of extensive UX research and testing.

**Takeaway**: Modifications to iOS defaults should be minimal, intentional, and well-justified. When something feels wrong, try removing customizations first.

---

### 3. Material Backgrounds > Manual Opacity

`.regularMaterial` handles light/dark mode automatically and provides proper translucency with vibrancy. Using `systemBackground.opacity()` was the wrong approach from the start - it doesn't adapt, doesn't blur, and looks wrong in dark mode.

**Takeaway**: Use Apple's material system APIs instead of manual color/opacity manipulation.

---

### 4. Two-Step Interactions Reduce Frustration

Separating "expand search bar" from "show keyboard" gave the user control over when the keyboard appears. This matches user mental models and reduces unexpected behavior.

**Takeaway**: Give users control over disruptive UI changes (like showing keyboard). Automatic behavior should be predictable.

---

### 5. Consistency Matters More Than You Think

The inconsistent list styles (PlainListStyle vs InsetGroupedListStyle) created subtle visual differences that felt "off" to the user across tabs. Small details compound - inconsistency is more noticeable than individual imperfections.

**Takeaway**: Audit for consistency systematically. Visual consistency is about the whole app, not individual screens.

---

### 6. Retroactive Documentation is Valuable

Writing this PRD after implementation forced reflection on the implementation journey, captured design decisions with full context, and created a detailed record of what actually works.

**Takeaway**: Even retroactive documentation has significant value. Document the "why" behind decisions while they're fresh.
