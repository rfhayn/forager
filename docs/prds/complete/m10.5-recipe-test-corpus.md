## 1. Problem Statement

Forager has two pipelines that process recipe text:

1. **OCRLineClassifier** (M10.2/M10.3) — classifies lines of recipe text as title/ingredient/instruction/metadata/sectionHeader/unknown. Uses heuristic scoring with section-aware context boosting.
2. **HybridIngredientParser** (M8.4) — 3-tier parser (Regex >= 0.9 -> ML >= 0.8 -> NLP fallback) that extracts quantity/unit/name from ingredient lines.

Both pipelines were developed with synthetic test cases and limited real-world validation. Real-world recipe testing has revealed parsing issues that unit tests do not cover — unusual formatting, metric conventions, missing section headers, and non-standard metadata patterns.

### What's Missing

| Gap | Impact |
|-----|--------|
| No real-world test corpus | Cannot measure accuracy on diverse recipe formats |
| No accuracy baseline | Cannot quantify improvement from tuning or training |
| No systematic failure catalog | Fixes are reactive (one-off bug reports), not proactive |
| No correction pipeline for classification | Parsing corrections exist via `ParsingTelemetryService`, but OCRLineClassifier has no equivalent feedback loop |

### Why Now

M10.5 sits between the existing import infrastructure (M10.1-M10.3) and future scaling work. Establishing accuracy baselines now means every subsequent tuning effort (regex pattern additions, ML retraining, classifier weight adjustments) has a measurable before/after. Without baselines, improvements are anecdotal.

## 2. Approach

### 2.1 One Dataset, Two Pipelines

A single corpus of 50 real recipe texts is processed through both pipelines in sequence:

```
Raw recipe text
  -> OCRLine.fromText() -> OCRLineClassifier.classifyLines()
     -> Classification results (line type per line)
     -> Lines classified as .ingredient
        -> HybridIngredientParser.parse()
           -> Parsing results (qty/unit/name per ingredient)
```

This mirrors the actual app flow: classification determines which lines are ingredients, then parsing extracts structured data from those lines. Testing them together reveals compounding errors (e.g., a misclassified instruction fed to the parser).

### 2.2 Confirm-or-Correct Review Model

The test harness pre-fills predictions from both pipelines. The human reviewer only edits incorrect predictions. This minimizes reviewer effort — correct predictions (expected to be the majority) require zero action.

This is the same approach that produced strangetom's 68,846 training samples: human-reviewed corrections on machine predictions are the gold standard for training data.

### 2.3 Corpus Categories

Five categories of 10 recipes each target distinct failure modes:

| # | Category | Target Failure Mode | Example Sources |
|---|----------|--------------------|-----------------|
| 1 | Clean well-formatted | Baseline — section headers, standard US units | AllRecipes, Food Network |
| 2 | No section headers | Forces classifier scoring without context boosting | Blog posts with minimal structure |
| 3 | Unusual metadata formats | Metadata misclassified as ingredients or instructions | "Yield: 2 dozen", "Active time: 15m", "Hands-on: 10 min" |
| 4 | Messy/mixed formatting | Paragraph-style, inline ingredients, run-on text | Food blogs, social media transcriptions |
| 5 | International/metric | Metric units, different conventions, unfamiliar terms | BBC Good Food, Australian/Indian recipe sites |

## 4. Architecture Decisions

### Decision 1: Plain Text Corpus, Not JSON-LD

**Decision**: Store recipes as raw plain text files simulating user paste input (or OCR output), not as structured JSON-LD.

**Rationale**: JSON-LD extraction is tested separately (M10.1). The classification and parsing pipelines operate on unstructured text. Testing with plain text exercises the exact code path that produces real-world failures.

**Format**: One `.txt` file per recipe in `foragerTests/TestData/RecipeCorpus/`. Filename convention: `{category}-{nn}-{brief-name}.txt` (e.g., `clean-01-chicken-tikka.txt`, `metric-03-victoria-sponge.txt`).

### Decision 2: Markdown Review Files (Human-in-the-Loop)

**Decision**: Generate a single markdown file with pre-filled predictions for human review. Not a GUI tool, not a database.

**Rationale**: Markdown is version-controllable, diff-friendly, and requires no tooling. The reviewer opens it in any text editor and edits only the incorrect cells. This is the simplest possible review interface.

**Trade-off**: Markdown tables are tedious for large volumes. Acceptable for the 50-recipe pilot. If M10.5.5 scales to 250+, a structured format (CSV or JSON) may be more practical.

### Decision 3: Test Harness as XCTest, Not Standalone Script

**Decision**: The corpus runner is an XCTest that executes within the app's test target, using real `OCRLineClassifier` and `HybridIngredientParser` instances.

**Rationale**: Tests use actual app code with real dependencies (CoreML model, vocabulary, etc.). Results reflect true production behavior. No risk of testing against a simulation that diverges from the real implementation.

**Output**: Test writes structured results to a file in a known location (test bundle or temp directory) for post-processing into the review markdown.

### Decision 4: Corrections Feed Both Pipelines

**Decision**: Classification corrections tune OCRLineClassifier scoring weights. Parsing corrections feed into regex pattern additions and ML training data via the existing `ParsingTelemetryService.exportCorrectionsAsTrainingData()` JSONL export.

**Rationale**: Reuses the existing correction-to-training pipeline for parsing (M8.4 infrastructure). Classification corrections are new — they produce a weight adjustment report rather than training data, since OCRLineClassifier uses heuristic scoring, not ML.

#### Decision Framework

| Pilot Result | Action |
|-------------|--------|
| Classification >= 85% AND parsing >= 80% | Corpus is validation-sufficient. Archive baselines. Scale only if specific category underperforms. |
| Classification < 85% OR parsing < 80% | Expand to 250 recipes, focused on failing categories. Budget additional 8-10h. |
| Systematic failure in one category | Targeted collection of 50 more recipes in that category only. Budget 3-4h. |
| Both pipelines < 70% | Major tuning effort needed. Pause scaling, focus on pipeline fixes first. |

## 8. Risk Register

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Recipe collection takes longer than estimated (formatting cleanup, deduplication) | Medium | Low | Set 45-min timebox per category. Accept imperfect formatting — messy input IS the test case. |
| Accuracy is much lower than expected (< 70%) | Low | Medium | Deprioritize scaling (M10.5.5), focus on targeted fixes. Low accuracy is valuable data. |
| Review process is too tedious at 50 recipes | Medium | Low | Split review across sessions. 50 recipes with ~20 lines each = ~1000 rows, reviewable in 2-3 hours. |
| Correction ingestion format doesn't align with existing JSONL export | Low | Medium | Audit `ParsingTelemetryService.exportCorrectionsAsTrainingData()` format in M10.5.4 task 4 before implementing. |
| CoreML model not available in test environment | Low | High | `MLIngredientParser.init?()` returns nil gracefully. Test harness logs which parser tier was used per line. Regex + NLP results are still valid. |
| Test data files bloat repository size | Low | Low | Plain text files are small (~1-2 KB each). 50 files = ~75 KB total. Acceptable. |
