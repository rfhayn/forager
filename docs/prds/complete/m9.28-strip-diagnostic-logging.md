# M9.28: Remove Diagnostic Logging for Production

**Status**: PLANNED
**Estimated**: 1-2 hours
**Priority**: High (pre-launch cleanup — no debug logging in App Store builds)
**Last Updated**: April 1, 2026

---

## Problem Statement

Three diagnostic logging systems were added during M7–M10 development for CloudKit troubleshooting and AI parsing debugging. Two of them (DiagnosticLogger, DebugLogService) are active in Release builds:

1. **DiagnosticLogger** (M9.15.3) — writes to `Documents/forager-diagnostics.log` on every app launch. File grows up to 2 MB, persists across restarts, and is exportable from Settings. Originally added to debug CloudKit household sync issues on physical devices.
2. **DebugLogService** (M10.6.5) — in-memory, 500-entry cap. Toggle-guarded (`isEnabled` defaults to `false`), but the service singleton is instantiated and the UI is accessible in Release.
3. **CloudKitLogger** (M7.3.4) — structured OSLog wrapper. OSLog calls are production-appropriate, but every call *also* pipes through `DiagnosticLogger.shared.log()`, writing to the diagnostic file in Release builds.

### Impact

- **Disk I/O on every launch**: DiagnosticLogger writes a session header (5 lines) on init, then logs every CloudKit and household operation to disk.
- **User-visible debug artifact**: Settings > Diagnostics section exposes a log viewer with clear/export — confusing for non-technical users.
- **Privacy risk**: Diagnostic file contains household IDs, CKShare record IDs, sync event details, and error messages. Exportable via share sheet.
- **Performance**: 76 `diag.info/warning/error` calls in Services/ alone. Each call formats a string, writes to FileHandle, and increments a counter — all on the main actor.

## Scope

### What to KEEP (production-appropriate)

- **CloudKitLogger's OSLog calls** — `Logger(subsystem:category:)` is Apple's recommended structured logging. Retrievable from Console.app and sysdiagnose. Keep all `logger.info/debug/warning/error` calls as-is.
- **CloudKitErrorMapper** — error mapping utility, no logging side effects.

### What to GATE behind `#if DEBUG`

- **DiagnosticLogger.swift** — the entire class. Only useful for development troubleshooting.
- **DiagnosticLogView.swift** — the Settings log viewer UI.
- **DebugLogService.swift** — the in-memory debug log service.
- **DebugLogView.swift** — the debug log viewer UI.
- **Settings > Diagnostics section** — `diagnosticLogSection` in SettingsView.swift.
- **CloudKitLogger → DiagnosticLogger bridge** — the `persist()` method should only call DiagnosticLogger in DEBUG.

### What to CLEAN UP in callers

- **76 `diag.*` calls across 3 service files** (HouseholdService: 58, RecipeImportService: 15, MealPlanService: 3) — wrap in `#if DEBUG` or convert to `os.Logger` calls.
- **~30 `DebugLogService.shared.log()` calls** across 6 service files — wrap in `#if DEBUG`.
- **2 `DiagnosticLogger.shared.*` calls in LLMSettingsService** — wrap in `#if DEBUG`.
- **2 `DiagnosticLogger.shared.*` calls in AddIngredientsToListView** — wrap in `#if DEBUG`.

## Implementation Plan

### Phase 1: Gate DiagnosticLogger and Views (30 min)

1. Wrap `DiagnosticLogger` class body in `#if DEBUG` with a no-op stub for Release:
   ```swift
   #if DEBUG
   @MainActor
   class DiagnosticLogger: ObservableObject {
       // ... full implementation
   }
   #else
   @MainActor
   class DiagnosticLogger: ObservableObject {
       static let shared = DiagnosticLogger()
       @Published var isEnabled: Bool = false
       @Published private(set) var lineCount: Int = 0
       func log(_ message: String, category: Category = .app, level: Level = .info) {}
       func debug(_ message: String, category: Category = .app) {}
       func info(_ message: String, category: Category = .app) {}
       func warning(_ message: String, category: Category = .app) {}
       func error(_ message: String, category: Category = .app) {}
       enum Category: String { /* same cases */ }
       enum Level: String { /* same cases */ }
   }
   #endif
   ```
   This keeps call sites compiling without changes. The no-op stub is zero-cost in Release.

2. Wrap `diagnosticLogSection` in SettingsView with `#if DEBUG`.

3. Wrap `DiagnosticLogView` body in `#if DEBUG` (or just gate its only entry point in SettingsView).

## Design Decisions

### Why no-op stub instead of removing call sites?

Wrapping 100+ call sites in `#if DEBUG` is tedious and clutters the code. A no-op stub means:
- Call sites compile unchanged in Release — empty function calls are optimized away by the compiler.
- Debug logging can be re-enabled by building Debug without touching service code.
- If a future milestone needs production logging (e.g., crash diagnostics), the call sites are already wired up.

The hybrid approach (stub for DiagnosticLogger/DebugLogService + `#if DEBUG` for the heaviest call sites in HouseholdService) balances code clarity with binary size.

### Why keep CloudKitLogger's OSLog?

OSLog is Apple's sanctioned production logging framework. It's:
- Privacy-aware (`.private` redaction available)
- Retrievable from sysdiagnose for TestFlight/production debugging
- Zero disk I/O cost when not being observed
- Already using structured categories (`subsystem: "com.richhayn.forager", category: "CloudKit"`)

### Why not delete the files entirely?

DiagnosticLogger and DebugLogService are useful development tools. Gating them behind `#if DEBUG` keeps them available for future debugging sessions without shipping them to users.
