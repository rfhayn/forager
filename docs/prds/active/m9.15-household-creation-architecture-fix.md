# M9.15: Household Creation Architecture Fix — Replace Attach-Then-Share with Create-Empty-Then-Copy

**Status**: READY
**Priority**: Critical (household creation completely broken since M9.13)
**Estimated**: 12-16 hours (3 phases)
**Branch**: `bugfix/M9.15-household-creation-fix`
**Date**: March 12, 2026
**Depends On**: M9.14 (ObjectID staleness fixes, merged as PRs #70-72)
**Reported From**: Builds 31-33 TestFlight — household creation fails with CloudKit error 134060

---

## Problem Statement

Household creation fails 100% of the time with CloudKit error 134060 ("objects assigned to multiple zones") whenever a user has existing personal data (recipes, ingredients, categories, etc.) in the private CloudKit zone.

Three successive fix attempts (PRs #70-72) addressed symptoms — stale ObjectIDs, cross-store IngredientTemplate relationships, cross-store Ingredient relationships — but the error cascades to the next entity in the graph each time. The root cause is architectural: the **attach-then-share** migration pattern (ADR 008) is fundamentally incompatible with objects that already have CKRecords in the private CloudKit zone.

### Root Cause: Attach-Then-Share is Broken

The current flow in `HouseholdService.createHouseholdAndShare()`:

1. Create Household entity in **private store** (no CKRecord yet — fine)
2. Migrate personal data: set `entity.household = household` on Recipes, WeeklyLists, MealPlans, PlannedMeals, Categories (still in private store)
3. Save context — CloudKit mirroring delegate creates/updates CKRecords in **private zone**
4. Call `container.share([household])` — asks CloudKit to move the entire object graph to a **shared zone**
5. **FAILS**: CloudKit sees CKRecords that already exist in the private zone being assigned to a shared zone → error 134060

The entity graph walks through relationships. Even if we break some relationships (IngredientTemplate, Ingredient), the error moves to the next connected entity. There is no way to "attach-then-share" an existing object graph without hitting this conflict.

### Evidence

| Build | Fix Applied | Result |
|-------|------------|--------|
| 31 | Nil'd `ingredient.ingredientTemplate` before share | Error 134060 on IngredientTemplate |
| 32 | Deleted all IngredientTemplates before share | Error 134060 on Ingredient |
| 33 | (Would cascade to GroceryListItem, Category, Recipe...) | Not attempted |

### Secondary Problem: Data Loss After Reinstall

When a user deletes and reinstalls the app, CloudKit re-downloads Household + HouseholdMember to the shared store, but `HouseholdService.currentHousehold` is nil (UserDefaults lost). User sees the app as if they have no household — all shared data is invisible. This was deferred during M7 and is documented in the development journal as an open issue.

---

## Solution: Create Empty → Share → Copy → Delete

Replace the attach-then-share pattern with a safe pattern that never moves existing CKRecords between zones.

### New Flow

```
1. cleanOrphanedHouseholdData()           — existing cleanup
2. Create Household + HouseholdMember     — in private store (empty, no data)
3. Save context
4. container.share([household])           — shares ONLY the Household entity (no relationships = no conflicts)
5. Save context (persist CKShare)
6. WAIT for shared store to be ready      — poll with user-visible progress
7. COPY data from private → shared store  — full fidelity via ManagedObjectFactory
8. DELETE old private-store objects        — after copy verified
9. Save context, update state
```

### Why This Works

- Step 4 shares a **single object** (Household) with zero relationships — no graph to walk, no zone conflicts
- Step 7 creates **brand new objects** in the shared store via ManagedObjectFactory. These objects get fresh CKRecords in the shared zone — no private zone contamination
- Step 8 deletes the old private-store objects, which cleanly removes their private-zone CKRecords

### Key Design Decisions

1. **Full fidelity copy** — Every property on every entity copied exactly. Zero data loss. Relationships reconstructed in shared store.
2. **User-visible progress** — Waiting for shared store shows progress to user. CloudKit zone setup can take 5-30 seconds.
3. **Atomic copy-then-delete** — Copy all data first, verify, then delete originals. Never delete before copy succeeds.
4. **ManagedObjectFactory for all copies** — Ensures correct store assignment and householdKey binding automatically.
5. **Promote Ingredient + GroceryListItem to HouseholdScoped** — Eliminates cross-store relationships entirely. All shared data has explicit householdKey.

## Phase 1: Promote Ingredient & GroceryListItem to HouseholdScoped (M9.15.1)

**Estimated**: 3-4 hours
**Goal**: All entities that live in shared store have explicit `household` relationship and `householdKey`

### Rationale

Currently Ingredient and GroceryListItem are NOT HouseholdScoped — they "inherit" store placement via their parent relationship (Recipe, WeeklyList). This creates cross-store relationship problems: when a parent moves to the shared store, child objects are still in the private store, and Core Data requires related objects to share the same persistent store.

Making them HouseholdScoped means:
- Factory handles store assignment automatically during copy
- `householdKey` predicates prevent ghost objects on ALL entities (ADR 013 compliance)
- No cross-store relationships anywhere in the model
- Consistent architecture: you're sharing your data or you're not

- `householdKey` attribute (String, optional)

- `household` relationship (to-one, optional, destination: Household)

This is **additive** — CloudKit Production schema allows it (append-only). Lightweight migration handles it automatically.

### 1.6 Backfill Migration

For existing users who already have a household, add a one-time migration to backfill `householdKey` on existing Ingredient and GroceryListItem records:

```swift
func backfillChildEntityHouseholdKeys() {
    // Ingredients: copy householdKey from parent Recipe
    let ingredientRequest: NSFetchRequest<Ingredient> = Ingredient.fetchRequest()
    ingredientRequest.predicate = NSPredicate(format: "householdKey == nil AND recipe.householdKey != nil")
    let ingredients = try? viewContext.fetch(ingredientRequest)
    for ingredient in ingredients ?? [] {
        ingredient.householdKey = ingredient.recipe?.householdKey
        ingredient.household = ingredient.recipe?.household
    }

    // GroceryListItems: copy householdKey from parent WeeklyList
    let itemRequest: NSFetchRequest<GroceryListItem> = GroceryListItem.fetchRequest()
    itemRequest.predicate = NSPredicate(format: "householdKey == nil AND weeklyList.householdKey != nil")
    let items = try? viewContext.fetch(itemRequest)
    for item in items ?? [] {
        item.householdKey = item.weeklyList?.householdKey
        item.household = item.weeklyList?.household
    }

    try? viewContext.save()
}
```

Call this from `HouseholdService.init()` or app launch, guarded by a UserDefaults flag to run only once.

## Phase 2: Fix Household Creation (M9.15.2)

**Estimated**: 6-8 hours
**Goal**: Household creation works reliably with zero data loss

### 2.1 Rewrite `createHouseholdAndShare()`

Replace the migration-before-share flow with create-empty-then-share:

```swift
func createHouseholdAndShare(name: String) async throws {
    // Pre-flight (existing logic)
    await MainActor.run { householdCreationPhase = .creatingHousehold }
    cleanOrphanedHouseholdData()

    // 1. Create empty Household + owner HouseholdMember
    let household = Household(context: viewContext)
    household.id = UUID()
    household.name = name
    household.createdAt = Date()

    let member = HouseholdMember(context: viewContext)
    member.id = UUID()
    member.household = household
    member.role = "owner"
    // ... other member properties

    try viewContext.save()

    // 2. Share the empty household (no relationships = no zone conflicts)
    await MainActor.run { householdCreationPhase = .sharingWithCloudKit }
    let share = try await shareWithRetry(household: household)
    try viewContext.save()  // Persist CKShare

    // 3. Wait for shared store to be ready
    try await waitForSharedStoreReady(household: household)

    // 4. Copy personal data to shared store
    await MainActor.run { householdCreationPhase = .migratingData }
    try copyPersonalDataToSharedStore(household: household)

    // 5. Update state
    await MainActor.run {
        self.currentHousehold = household
        self.shareRecord = share
        self.householdCreationPhase = .complete
    }
}
```

### 2.2 Implement `waitForSharedStoreReady()`

Poll until the Household object is accessible from the shared store:

```swift
private func waitForSharedStoreReady(household: Household) async throws {
    await MainActor.run { householdCreationPhase = .waitingForCloudKit }

    let maxAttempts = 30  // 30 × 2s = 60s max
    for attempt in 1...maxAttempts {
        let request: NSFetchRequest<Household> = Household.fetchRequest()
        request.predicate = NSPredicate(format: "id == %@", household.id! as CVarArg)
        request.affectedStores = [persistence.sharedStore]

        if let _ = try? viewContext.fetch(request).first {
            return  // Shared store is ready
        }

        try await Task.sleep(nanoseconds: 2_000_000_000)  // 2 seconds
    }

    throw HouseholdError.sharedStoreTimeout
}
```

### 2.3 Implement `copyPersonalDataToSharedStore()`

Full-fidelity property copy using ManagedObjectFactory. Copy order respects the relationship dependency graph — parents first, children second.

**Entity relationship map** (all entities now HouseholdScoped after Phase 1):

| Entity | Dependencies | Copy Order |
|--------|-------------|------------|
| Category | none | 1 |
| IngredientTemplate | → Category (optional) | 2 |
| Recipe | none | 3 |
| Ingredient | → Recipe (required), → IngredientTemplate (optional) | 4 |
| WeeklyList | none | 5 |
| GroceryListItem | → WeeklyList (required), → Category (optional) | 6 |
| MealPlan | none | 7 |
| PlannedMeal | → MealPlan (required), → Recipe (optional) | 8 |

**Implementation approach:**

```swift
private func copyPersonalDataToSharedStore(household: Household) throws {
    let scope = DataScope.household(id: household.objectID, storeID: .shared)

    // old→new ID maps for relationship reconstruction
    var categoryMap: [NSManagedObjectID: Category] = [:]
    var templateMap: [NSManagedObjectID: IngredientTemplate] = [:]
    var recipeMap: [NSManagedObjectID: Recipe] = [:]
    var weeklyListMap: [NSManagedObjectID: WeeklyList] = [:]
    var mealPlanMap: [NSManagedObjectID: MealPlan] = [:]

    // 1. Categories
    let oldCategories = try fetchPrivateStoreEntities(Category.self)
    for old in oldCategories {
        let new = try factory.make(Category.self, in: scope) { cat in
            copyAllProperties(from: old, to: cat)
        }
        categoryMap[old.objectID] = new
    }

    // 2. IngredientTemplates
    let oldTemplates = try fetchPrivateStoreEntities(IngredientTemplate.self)
    for old in oldTemplates {
        let new = try factory.make(IngredientTemplate.self, in: scope) { tmpl in
            copyAllProperties(from: old, to: tmpl)
            // Reconstruct category relationship
            if let oldCat = old.category {
                tmpl.category = categoryMap[oldCat.objectID]
            }
        }
        templateMap[old.objectID] = new
    }

    // 3. Recipes
    let oldRecipes = try fetchPrivateStoreEntities(Recipe.self)
    for old in oldRecipes {
        let new = try factory.make(Recipe.self, in: scope) { recipe in
            copyAllProperties(from: old, to: recipe)
        }
        recipeMap[old.objectID] = new
    }

    // 4. Ingredients (now HouseholdScoped)
    let oldIngredients = try fetchPrivateStoreEntities(Ingredient.self)
    for old in oldIngredients {
        let _ = try factory.make(Ingredient.self, in: scope) { ing in
            copyAllProperties(from: old, to: ing)
            // Reconstruct relationships
            if let oldRecipe = old.recipe {
                ing.recipe = recipeMap[oldRecipe.objectID]
            }
            if let oldTemplate = old.ingredientTemplate {
                ing.ingredientTemplate = templateMap[oldTemplate.objectID]
            }
        }
    }

    // 5. WeeklyLists
    let oldLists = try fetchPrivateStoreEntities(WeeklyList.self)
    for old in oldLists {
        let new = try factory.make(WeeklyList.self, in: scope) { list in
            copyAllProperties(from: old, to: list)
        }
        weeklyListMap[old.objectID] = new
    }

    // 6. GroceryListItems (now HouseholdScoped)
    let oldItems = try fetchPrivateStoreEntities(GroceryListItem.self)
    for old in oldItems {
        let _ = try factory.make(GroceryListItem.self, in: scope) { item in
            copyAllProperties(from: old, to: item)
            // Reconstruct relationships
            if let oldList = old.weeklyList {
                item.weeklyList = weeklyListMap[oldList.objectID]
            }
            if let oldCat = old.categoryEntity {
                item.categoryEntity = categoryMap[oldCat.objectID]
            }
        }
    }

    // 7. MealPlans
    let oldPlans = try fetchPrivateStoreEntities(MealPlan.self)
    for old in oldPlans {
        let new = try factory.make(MealPlan.self, in: scope) { plan in
            copyAllProperties(from: old, to: plan)
        }
        mealPlanMap[old.objectID] = new
    }

    // 8. PlannedMeals
    let oldMeals = try fetchPrivateStoreEntities(PlannedMeal.self)
    for old in oldMeals {
        let _ = try factory.make(PlannedMeal.self, in: scope) { meal in
            copyAllProperties(from: old, to: meal)
            if let oldPlan = old.mealPlan {
                meal.mealPlan = mealPlanMap[oldPlan.objectID]
            }
            if let oldRecipe = old.recipe {
                meal.recipe = recipeMap[oldRecipe.objectID]
            }
        }
    }

    // Verify counts match
    assert(categoryMap.count == oldCategories.count)
    assert(templateMap.count == oldTemplates.count)
    assert(recipeMap.count == oldRecipes.count)

    // Delete originals from private store (copy succeeded)
    // Delete in reverse order (children first, parents last)
    for old in oldMeals { viewContext.delete(old) }
    for old in oldPlans { viewContext.delete(old) }
    for old in oldItems { viewContext.delete(old) }
    for old in oldLists { viewContext.delete(old) }
    for old in oldIngredients { viewContext.delete(old) }
    for old in oldRecipes { viewContext.delete(old) }
    for old in oldTemplates { viewContext.delete(old) }
    for old in oldCategories { viewContext.delete(old) }

    try viewContext.save()
}
```

**Helper: `fetchPrivateStoreEntities()`** — fetches entities from the private store only (excludes shared store objects):

```swift
private func fetchPrivateStoreEntities<T: NSManagedObject>(_ type: T.Type) throws -> [T] {
    let request = T.fetchRequest() as! NSFetchRequest<T>
    request.affectedStores = [persistence.privateStore]
    return try viewContext.fetch(request)
}
```

**Helper: `copyAllProperties()`** — copies all non-relationship attributes from one managed object to another. Implementation uses entity description to enumerate attributes dynamically, ensuring full fidelity without manually listing every property.

### 2.4 Add User-Visible Progress

Add published state to HouseholdService:

```swift
enum HouseholdCreationPhase: String {
    case idle = ""
    case creatingHousehold = "Creating household..."
    case sharingWithCloudKit = "Setting up CloudKit sharing..."
    case waitingForCloudKit = "Syncing with iCloud..."
    case migratingData = "Moving your data to household..."
    case complete = "Done!"
    case failed = "Failed"
}

@Published var householdCreationPhase: HouseholdCreationPhase = .idle
```

The household creation UI binds to this to show a `ProgressView` with the current phase label. The view should disable dismiss/cancel while creation is in progress.

### 2.5 Error Handling & Rollback

**If copy fails partway through:**
- Do NOT delete any original data (originals untouched until copy fully succeeds)
- Delete any partially-copied shared store objects
- Reset `householdCreationPhase` to `.failed`
- Surface error to user with actionable message

**If `waitForSharedStoreReady()` times out:**
- The household was shared but CloudKit hasn't synced yet
- Offer retry: "iCloud is taking longer than expected. Tap to retry."
- Do NOT delete the household — it's validly shared, just slow

### 2.6 Remove `migratePersonalDataToHousehold()`

The old migration method is no longer needed. Remove it entirely along with the relationship-breaking hacks (nil'ing ingredientTemplate, deleting templates, breaking GroceryListItem→Category links).

## Phase 3: Returning User Detection (M9.15.3)

**Estimated**: 2-4 hours
**Goal**: After app delete + reinstall, auto-detect existing household membership

### 3.1 The Problem

When a user deletes and reinstalls the app:
1. Local Core Data stores are deleted
2. CloudKit re-downloads Household + HouseholdMember to shared store
3. `HouseholdService.currentHousehold` is nil (UserDefaults lost, no local state)
4. User sees the app as if they have no household — data is invisible

### 3.2 Solution: Startup Household Discovery

On app launch, after CloudKit initial sync settles, check for existing household membership:

```swift
func discoverExistingHousehold() async {
    guard currentHousehold == nil else { return }

    // Wait briefly for CloudKit to sync
    try? await Task.sleep(nanoseconds: 3_000_000_000)  // 3 seconds

    // Check for Household entities (any store)
    let request: NSFetchRequest<Household> = Household.fetchRequest()
    request.fetchLimit = 1

    if let household = try? viewContext.fetch(request).first {
        if let members = household.members as? Set<HouseholdMember>,
           members.contains(where: { $0.isCurrentUser }) {
            self.currentHousehold = household
            self.isInHousehold = true
            restoreShareRecord(for: household)
        }
    }
}
```

### 3.3 Integration Points

- Call `discoverExistingHousehold()` from `foragerApp.swift` on launch, after persistence controller is initialized
- Show a brief "Restoring your data..." indicator if household is discovered
- Also observe `NSPersistentStoreRemoteChangeNotification` as a secondary trigger — if CloudKit sync completes after the initial 3-second wait, re-check

### 3.4 Edge Cases

- **Multiple households synced**: Pick the one where user is owner, or most recently created
- **Household synced but member record missing**: User was removed — don't restore
- **Race condition with CloudKit sync**: 3-second wait may not be enough. The notification observer handles late arrivals

## Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| Shared store not ready after share | Creation stalls | 60s timeout with retry option, do not delete household |
| Copy fails midway | Partial data in shared store | Atomic: don't delete originals until copy verified |
| Relationship reconstruction misses an entity | Orphaned objects | Use old→new ID maps, verify counts match after copy |
| CloudKit rate limiting during bulk copy | Throttled writes | Batch saves (50 objects per save), not one-at-a-time |
| Returning user detection false positive | Wrong household restored | Verify current user is member, not just that household exists |
| Schema migration fails | App crash on launch | Lightweight migration (additive only), test with production-size data |
| Backfill migration on large datasets | Slow launch | Guard with UserDefaults flag, run once |
