# M9.36: CloudKit Public Permission Member Protection

**Status**: ACTIVE
**Created**: April 2, 2026
**Estimated**: 0.5h
**Branch**: `main` (hotfix — included with pending M18 testing work)
**Related**: ADR 009 (Public Link Sharing), M9.30 (Invitation Security), M9.31 (CKShare Resilience)

---

## Problem

Members who join a household via the public CKShare URL (ADR 009) are being kicked on every app restart. The M9.30 invitation security code (`revertPublicPermissionIfNeeded`) automatically sets `publicPermission = .none` after 24 hours, which removes all public-link participants from the share.

### Evidence (diagnostic log, April 2, 2026)

```
19:45:07  Fresh CKShare participants: 2   <- Both members present
19:45:20  Reverted publicPermission to .none (24h expired)
19:45:20  Fresh CKShare participants: 1   <- Member kicked
```

### Root Cause

The M9.30 PRD assumed that once a user accepts a CKShare via the public URL, they become a permanent `CKShare.Participant` independent of `publicPermission`. **This assumption is wrong.** In CloudKit, public-link participants' access is governed by the `publicPermission` setting — it is not a one-time gate. Setting it to `.none` revokes their access entirely.

This was not caught during M9.30 testing because the 24-hour expiry timer hadn't elapsed during the test window.

---

## Solution

Check for non-owner accepted participants before reverting `publicPermission` in all three code paths:

1. **`revertPublicPermissionIfNeeded()`** — auto-expiry on startup
2. **`cancelInvitation()`** — single invitation cancellation
3. **`revokeAllPendingInvitations()`** — bulk revocation

If non-owner participants exist on the CKShare, skip the revert. Clear `lastInviteDate` so the check doesn't repeat every launch.

### Changes

| File | Method | Change |
|------|--------|--------|
| `Services/HouseholdService.swift` | `revertPublicPermissionIfNeeded()` | Add `share.participants.filter { $0.role != .owner }` guard before revert |
| `Services/HouseholdService.swift` | `cancelInvitation()` | Same guard before permission revert block |
| `Services/HouseholdService.swift` | `revokeAllPendingInvitations()` | Same guard before permission revert block |
| `docs/architecture/009-*.md` | Known Constraints | Document that `publicPermission` must stay `.readWrite` while members exist |

### What is NOT Changed

- `loadCurrentHousehold()` flow — structure is correct
- M9.31 ghost detection (4-layer protection)
- `checkForMemberDepartures()` / departure detection
- SceneDelegate share acceptance
- Schema / Core Data model
- ADRs 008, 013, 014

## Edge Cases

| Scenario | Expected Behavior |
|----------|-------------------|
| Invite sent, nobody joins, 24h passes | Safe to revert — no non-owner participants |
| Invite sent, member joins, 24h passes | Skip revert — member would be kicked |
| Member leaves, then 24h passes | Safe to revert — only owner remains |
| Owner cancels invitation with active member | Skip revert — member still on share |
| `getShare()` fails during check | Caught by existing catch — revert skipped (safe) |
| Multiple invites over time | `lastInviteDate` cleared after skip |

---

## Security Model Update

The revised security model (post-M9.36) accepts that `publicPermission` must remain `.readWrite` for the lifetime of any household with non-owner members. The invitation URL remains technically valid, but this is acceptable because:

- URLs are not guessable or discoverable
- iCloud authentication is required to join
- The 10-member cap still applies (M9.30)
- The owner can see all participants in the UI
- AES-GCM API key encryption protects sensitive household data (M9.30)

True member removal requires household deletion or future `UICloudSharingController` support (when Apple fixes it).

- [ ] Diagnostic log shows "Skipping publicPermission revert" when members exist
- [ ] ADR 009 updated with Known Constraints section
