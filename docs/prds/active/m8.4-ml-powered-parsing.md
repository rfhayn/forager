## 1. Problem Statement

Forager's current parsing pipeline — `RegexIngredientParser` (fast path) → `NLPIngredientParser` (Apple NaturalLanguage fallback) → `HybridIngredientParser` (router) — handles standard recipe formats well but fails on:

| Input | Expected | Current Result | Root Cause |
|-------|----------|----------------|------------|
| `3 cloves garlic` | qty=3, unit=clove, name=garlic | name="cloves garlic" | Regex doesn't know "clove" is a unit in this context |
| `1/4 tsp black pepper` (via meal plan) | name=black pepper | name="/ black pepper" | `extractCleanIngredientName()` strips fraction parts separately |
| `bananas` | template=bananas | template=banana | Pluralization table incomplete |
| `milk 2%` | no warning | needsReview=true | Digit heuristic doesn't know about product variants |
| `a handful of fresh cilantro` | qty=1, name=cilantro | name="handful fresh cilantro" | Descriptive amounts not fully extracted |
| `salt and pepper to taste` | name=salt and pepper | name="salt and pepper to taste" | Qualifier stripping incomplete |

These are **class-level failures** — fixing them one-by-one with regex additions creates an ever-growing rule set that's brittle and untestable. A machine-learned model trained on real ingredient data solves the entire class.

## 2. Approach: Dataset-Bootstrapped CoreML Sequence Labeler

### Why Not the Original M8.4 Plan?

The M8.4 plan in the M8 Meta-PRD (lines 1585-2384) proposed a Create ML Text Classifier that:
- Requires **100+ user corrections** before training — cold start problem
- Uses flat classification ("2.0|cup|flour") — loses token-level context
- Can't handle unseen ingredient formats without retraining

### What Changed: Open-Source Dataset Bootstrapping

Two high-quality open-source datasets provide immediate training data:

| Dataset | Size | Format | License | Accuracy | Approach |
|---------|------|--------|---------|----------|----------|
| [strangetom/ingredient-parser](https://github.com/strangetom/ingredient-parser) | 81,316 sentences | **SQLite** (`en` table) | MIT | 95.25% sentence / 98.09% word | CRF (pycrfsuite) |
| [NYT ingredient-phrase-tagger](https://github.com/NYTimes/ingredient-phrase-tagger) | 180,000 examples | CSV (7 columns) | Apache 2.0 | N/A (CRF baseline) | CRF + manual review |

**Key finding**: strangetom already **includes NYT data** as one of its 5 sources (NYT, BBC, cookstr, allrecipes, tastecooking). Direct combination would create duplicates. Strategy: use strangetom as primary (pre-tokenized, richer labels), supplement with NYT rows not in strangetom for additional coverage.

After dedup, expect **~120,000-150,000 unique sentences** — still more than sufficient for a BiLSTM model.

### Architecture: Sequence Labeling (Token-Level)

Instead of flat classification, use **token-level sequence labeling** (the standard approach in NLP for entity extraction):

```
Input:  "2    cups   all-purpose   flour"
Labels:  QTY  UNIT   B_NAME_TOK   I_NAME_TOK
```

**strangetom's native label set (13 labels)**:
| Label | Meaning | Example tokens |
|-------|---------|----------------|
| `QTY` | Quantity | `2`, `1/4`, `one` |
| `UNIT` | Unit of measure | `cups`, `tsp`, `cloves` |
| `B_NAME_TOK` | Name (first token) | `all-purpose` |
| `I_NAME_TOK` | Name (continuation) | `flour` |
| `NAME_VAR` | Name variant/modifier | `2%` in "milk 2%" |
| `NAME_SEP` | Name separator | `and` in "salt and pepper" |
| `NAME_MOD` | Name modification | `fresh` in "fresh cilantro" |
| `SIZE` | Size descriptor | `large` in "3 large eggs" |
| `PREP` | Preparation | `chopped`, `diced` |
| `COMMENT` | Comment/qualifier | `to taste`, `optional` |
| `PURPOSE` | Purpose clause | `for garnish` |
| `PUNC` | Punctuation | `,`, `(`, `)` |
| `OTHER` | Other | tokens that don't fit |

**Simplified label mapping for Forager** (strangetom 13 → Forager 7):
```
QTY                          → QTY
UNIT                         → UNIT
B_NAME_TOK, I_NAME_TOK,
  NAME_VAR, NAME_SEP         → NAME
NAME_MOD, SIZE               → MODIFIER
PREP                         → PREP
COMMENT, PURPOSE             → COMMENT
PUNC, OTHER                  → OTHER
```

This reduces label count while preserving the distinctions Forager needs. The model learns what role each token plays, regardless of ordering.

### On-Device CoreML Pipeline

> **Critical architecture decision**: CRF layers **cannot** convert to CoreML via coremltools.
> The solution: split the BiLSTM-CRF into two components:
> 1. **BiLSTM emission scorer** → CoreML (standard LSTM conversion, well-supported)
> 2. **CRF parameters** → JSON (7×7 transition matrix + 1×7 start transitions + 1×7 end transitions)
> 3. **Viterbi decoder** → Pure Swift (~30 lines, runs the CRF decoding step)

```
Training (Mac):
  strangetom SQLite + NYT CSV
  → Unified token-labeled format (7 Forager labels)
  → PyTorch BiLSTM-CRF
  → Export BiLSTM emission scorer via coremltools → .mlpackage
  → Export CRF parameters (7×7 transitions + start/end vectors) → transitions.json

Runtime (iOS):
  Input text
  → Tokenize → token IDs (via vocabulary.json)
  → CoreML prediction (emission scores per token × 7 labels)
  → Swift Viterbi decoder (emissions + CRF parameters → optimal label sequence)
  → Decode labels → ParserResult
  → Slot into HybridIngredientParser
```

**Privacy**: All inference on-device. Training data is open-source. No user data ever leaves the device.

## 5. Implementation Phases

### Phase 0: Feasibility + Contract Lock (2-3h)

**Deliverable**: Locked engineering contracts, single-parse refactor, parity test harness, and governance artifacts. No coding proceeds until Phase 0 exit criteria are met.

> **Why a Phase 0 gate?** Principal engineering review identified that contract ambiguity (tokenizer behavior, model I/O, CRF decode parity) creates silent quality regression risk downstream. Spending 2-3 hours locking contracts saves rework later.

#### 0a: Architecture Lock — Word-Only v1

**Decision**: v1 uses word-level embeddings only. No character CNN/LSTM features.

Rationale: char features add dual-input CoreML conversion complexity and per-token character ID preprocessing with marginal accuracy gain on this vocabulary. strangetom CRF achieves 95.25% without them. This decision is already locked in Section 2 model specification.

#### 0b: Tokenizer Specification

Write a tokenizer contract document (`tools/ml-training/TOKENIZER_SPEC.md`) that both the Python training code and the Swift runtime code must satisfy:

| Property | Value | Rationale |
|----------|-------|-----------|
| Normalization | lowercased, Unicode NFKD, strip leading/trailing whitespace | Consistency across inputs |
| Token splitting | split on whitespace, then split punctuation from word boundaries | Matches strangetom tokenization |
| Max sequence length | 64 tokens | Ingredient strings rarely exceed 20 tokens; 64 provides generous headroom |
| Truncation | Right-truncate (drop tokens beyond position 64) | Preserve quantity/unit at start |
| Padding | **No padding** — pass actual token count to CoreML (dynamic `RangeDim` input shape) | `RangeDim(1, 64)` accepts variable-length input; padding would produce spurious emission scores that must be stripped before Viterbi. Only pad if switching to fixed-shape input. |
| UNK token | ID=0 | Unknown words get a trainable UNK embedding |
| PAD token | ID=1 | Padding for batch/fixed-shape |
| Vocabulary | Built from training data, frequency threshold ≥2 | Rare tokens → UNK |

**Swift NFKD note**: Swift's `decomposedStringWithCanonicalMapping` produces NFD, not NFKD. For NFKD, use `applyingTransform(.init("NFKD"), reverse: false)`. Getting this wrong means the Swift tokenizer won't match the Python tokenizer.

**Deliverable**: `TOKENIZER_SPEC.md` + a Python reference tokenizer function + 100-sentence test vectors (input → expected token IDs). Swift tokenizer in Phase 4 must match these vectors exactly.

#### 0c: Single-Parse Refactor + Telemetry Consolidation

The double-parse pattern (calling both `parseIngredient()` and `parseToStructured()` on the same text, each invoking the full hybrid parser chain) exists in **multiple call sites**, not just `parseAndConnectIngredients`. Additionally, `parseIngredient()` generates **zero telemetry** — only `parseToStructured()` logs to `ParsingTelemetryService`. This means 11+ production parse operations are currently invisible to telemetry.

### Phase 1: Dataset Preparation (3-4h)

**Deliverable**: Unified token-labeled dataset ready for training

**Step 1: Download and inspect strangetom dataset** (primary — 81,316 sentences)

The strangetom dataset is a **SQLite database** (not CSV). Schema:
```sql
-- Table: en
-- Columns:
--   id        INTEGER PRIMARY KEY
--   source    TEXT     -- "nyt", "bbc", "cookstr", "allrecipes", "tastecooking"
--   sentence  TEXT     -- Original ingredient string: "2 cups all-purpose flour"
--   tokens    TEXT     -- JSON array: ["2", "cups", "all-purpose", "flour"]
--   labels    TEXT     -- JSON array: ["QTY", "UNIT", "B_NAME_TOK", "I_NAME_TOK"]
--   sentence_split  TEXT  -- Not needed (sentence-level grouping)
--   fdc_mapping     TEXT  -- Not needed (USDA food codes)
```

**Fraction encoding gotcha**: strangetom uses non-standard fraction notation:
- `1#1$2` = 1½ (1 + 1/2) — format: `whole#numerator$denominator`
- `3$4` = ¾ — format: `numerator$denominator`
- Must decode these to decimal during prep

**Step 2: Download NYT dataset** (supplement — 180k examples)

NYT is a flat CSV with 7 columns:
```
index, input, name, qty, range_end, unit, comment
```

NYT provides **sentence-level labels** (not token-level). Converting to token labels requires:
- Tokenize the `input` string
- Match each token against the `qty`, `unit`, `name`, `comment` fields
- Assign label based on which field the token belongs to

**Important**: strangetom already includes NYT data (source="nyt"). Use sentence-level dedup to avoid duplicates.

**Step 3: Write converter** (`tools/ml-training/prepare_dataset.py`):
1. Load strangetom SQLite → extract `tokens` and `labels` JSON arrays
2. Decode fraction notation (`1#1$2` → `1.5`)
3. Map strangetom's 13 labels → Forager's 7 labels (see Section 2)
4. Load NYT CSV → tokenize + align to generate token labels
5. Deduplicate by normalized sentence text (strangetom includes NYT already)
6. 80/10/10 train/validation/test split (stratified by source)
7. Output: `training_data.jsonl`, `validation_data.jsonl`, `test_data.jsonl`

**Output format** (JSON Lines — one sentence per line):
```json
{"tokens": ["2", "cups", "all-purpose", "flour"], "labels": ["QTY", "UNIT", "NAME", "NAME"]}
{"tokens": ["1/4", "tsp", "salt"], "labels": ["QTY", "UNIT", "NAME"]}
```

**Step 4: Validate**
- Spot-check 100 random samples for label accuracy
- Log statistics: total sentences, label distribution, vocabulary size
- Verify no data leakage between splits

**Acceptance criteria**:
- ≥80,000 unique sentences after dedup (strangetom alone provides 81k)
- All tokens have valid Forager labels (7 classes)
- Fraction notation fully decoded (no `#` or `$` in output)
- Train/val/test splits are stratified (similar label distributions)
- No data leakage between splits

### Phase 2: Model Architecture & Training (4-5h)

**Deliverable**: Trained PyTorch BiLSTM-CRF model with ≥95% token accuracy on test set

**Architecture choice**: BiLSTM-CRF (split export — see Phase 3)

Why BiLSTM-CRF over Transformer:
- **Model size**: ~2-5 MB vs. 50-100 MB for a transformer — critical for app bundle size
- **Inference speed**: <5ms vs. 20-50ms — must stay under parsing target (<50ms)
- **Training data**: 80-150k sentences is enough for BiLSTM-CRF but marginal for a transformer
- **Proven on this exact domain**: strangetom's CRF achieves 95.25% sentence accuracy on ingredient parsing

**v1 simplification**: Word-only embeddings (no character CNN/LSTM). See Phase 0a for rationale.

**Architecture decision (locked)**: **Word-only embeddings for v1.** Character-level features (char CNN/LSTM) add preprocessing complexity (per-token character ID sequences, variable-length padding, dual-input CoreML conversion) with marginal accuracy gain on this vocabulary. The strangetom CRF achieves 95.25% sentence accuracy without char features. Char features may be revisited in v2 if token-level accuracy plateaus below target.

**Model specification**:
```python
# tools/ml-training/train_model.py
class IngredientTagger(nn.Module):
    embedding_dim = 128     # Word embeddings only (v1: no char features)
    hidden_dim = 256        # BiLSTM hidden size
    num_labels = 7          # QTY, UNIT, NAME, MODIFIER, PREP, COMMENT, OTHER
    vocab_size = ~8000      # Word vocabulary from training data

    # Components:
    # 1. Word embedding (vocab_size × embedding_dim)
    # 2. BiLSTM (2 layers, hidden_dim)
    # 3. Linear projection (hidden_dim → num_labels)
    # 4. CRF layer (num_labels × num_labels transition matrix + start/end transitions)
```

**Training script** (`tools/ml-training/train_model.py`):
1. Load prepared JSONL datasets
2. Build word vocabulary (word-only v1, no char vocabulary) → save as `vocabulary.json`
3. Train BiLSTM-CRF (word-only, per Phase 0a lock) with:
   - Learning rate: 0.001 (Adam)
   - Batch size: 64
   - Max epochs: 30 with early stopping (patience=5)
   - Dropout: 0.5
4. Evaluate on test set — log per-class F1 for QTY/UNIT/NAME (key slots)
5. Export model checkpoint (`ingredient_tagger.pt`)
6. Export CRF parameters separately:
   - `transitions.json` — 7×7 transition matrix + 1×7 start transitions + 1×7 end transitions + label names
7. Export vocabulary mapping (`vocabulary.json`)
8. Fill in model card (`MODEL_CARD.md`) with training metadata (per Phase 0e template)

**Acceptance criteria**:
- Token-level accuracy ≥ 96% on test set
- Sentence-level accuracy ≥ 92% on test set
- Per-class F1 ≥ 0.90 for QTY, UNIT, NAME (key extraction slots)
- Model file < 10 MB
- Training completes in < 2 hours on MacBook Pro
- CRF parameters exported: 7×7 transitions + start_transitions + end_transitions + label names
- Vocabulary exported as JSON
- Model card filled with training metadata

**Deliverable**: `.mlpackage` (emission scorer) + `transitions.json` + `vocabulary.json` integrated into Xcode project

> Solution: export only the BiLSTM emission scorer to CoreML. The CRF parameters
> (7×7 transition matrix + 1×7 start transitions + 1×7 end transitions) ship as a JSON resource. Viterbi decoding runs in Swift (Phase 4).

   ```python
       def __init__(self, full_model):
           super().__init__()
           self.embedding = full_model.embedding  # Word embeddings only (v1)
           self.lstm = full_model.lstm
           self.hidden2tag = full_model.hidden2tag  # Linear(hidden_dim, num_labels)

       def forward(self, token_ids):
           # Returns emission scores: (batch, seq_len, num_labels)
           ...
   ```
3. Trace emission scorer with example input (single `token_ids` tensor, no char_ids)
4. Convert via coremltools:
   ```python
   import coremltools as ct
   mlmodel = ct.convert(
       traced_emission_scorer,
       inputs=[ct.TensorType(name="token_ids", shape=(1, ct.RangeDim(1, 64)))],
       outputs=[ct.TensorType(name="emissions")]  # (1, seq_len, 7)
   )
   mlmodel.save("IngredientTaggerEmissions.mlpackage")
   ```
5. **Export ALL CRF parameters** from trained model:
   ```python
   crf_params = {
       "transitions": model.crf.transitions.detach().numpy().tolist(),      # 7×7
       "start_transitions": model.crf.start_transitions.detach().numpy().tolist(),  # 1×7
       "end_transitions": model.crf.end_transitions.detach().numpy().tolist(),      # 1×7
       "labels": label_names  # ["QTY", "UNIT", "NAME", "MODIFIER", "PREP", "COMMENT", "OTHER"]
   }
   json.dump(crf_params, open("transitions.json", "w"))
   ```
6. **Viterbi parity gate (HARD GATE — must pass before proceeding to Phase 4)**:
   - Run Python reference Viterbi decoder on 1000 held-out test samples using exported CRF params
   - Run CoreML emissions + Python Viterbi on same 1000 samples
   - Compare full PyTorch CRF decode vs. split decode (CoreML emissions + exported CRF params)
   - **Gate criterion**: Token-level agreement = (matching tokens / total tokens across all 1000 sentences) ≥ 99.9%. One metric, one denominator, one threshold.
   - Document any disagreements and their root causes
   - Save parity report as `tools/ml-training/parity_report.md`
7. Add to Xcode project:
   - `IngredientTaggerEmissions.mlpackage` → forager target (Xcode compiles model)
   - `transitions.json` → forager target (Copy Bundle Resources)
   - `vocabulary.json` → forager target (Copy Bundle Resources)

**Acceptance criteria**:
- **Viterbi parity gate passed** (≥99.9% token agreement on 1000 samples)
- CoreML emissions + Python Viterbi match full PyTorch model within 0.01%
- `transitions.json` includes `transitions`, `start_transitions`, `end_transitions`, and `labels`
- Model loads and runs on iOS Simulator
- Bundle size increase < 5 MB on disk (emission model + JSON files). Runtime memory footprint may be higher (~8-10MB including CoreML internal buffers); consider `compute_precision=ct.precision.FLOAT16` at conversion time to halve parameter memory.
- Xcode auto-generates `IngredientTaggerEmissions` prediction class

### Phase 4: MLIngredientParser Implementation (3-4h)

**Deliverable**: `Services/Parsing/MLIngredientParser.swift` + `Services/Parsing/ViterbiDecoder.swift` passing all tests

#### 4a: Viterbi Decoder (~40 lines of Swift)

**File**: `Services/Parsing/ViterbiDecoder.swift`

The Viterbi algorithm finds the optimal label sequence given emission scores and transition costs. This is the CRF decoding step that can't run in CoreML.

> **Critical**: The decoder must consume **all** CRF parameters — the 7×7 transition matrix **plus** start and end transition vectors. Omitting start/end transitions produces different label sequences than the Python CRF for some inputs, even when emissions match. See Phase 0d parity gate.

```swift
struct ViterbiDecoder {
    let transitions: [[Float]]      // 7×7 transition scores (label_i → label_j)
    let startTransitions: [Float]   // 1×7 start-of-sequence transition scores
    let endTransitions: [Float]     // 1×7 end-of-sequence transition scores
    let labels: [String]            // ["QTY", "UNIT", "NAME", "MODIFIER", "PREP", "COMMENT", "OTHER"]

    /// Decode the optimal label sequence from emission scores
    /// - Parameter emissions: (seq_len × num_labels) matrix of emission scores from CoreML
    /// - Returns: Array of label strings, one per token
    func decode(emissions: [[Float]]) -> [String] {
        let seqLen = emissions.count
        let numLabels = labels.count
        guard seqLen > 0 else { return [] }

        // Standard Viterbi: forward pass with backpointers, then backtrace
        var viterbi = [[Float]](repeating: [Float](repeating: -Float.infinity, count: numLabels), count: seqLen)
        var backpointers = [[Int]](repeating: [Int](repeating: 0, count: numLabels), count: seqLen)

        // Initialize with start transitions + first token emissions
        for j in 0..<numLabels {
            viterbi[0][j] = startTransitions[j] + emissions[0][j]
        }

        // Forward pass
        for t in 1..<seqLen {
            for j in 0..<numLabels {
                for i in 0..<numLabels {
                    let score = viterbi[t-1][i] + transitions[i][j] + emissions[t][j]
                    if score > viterbi[t][j] {
                        viterbi[t][j] = score
                        backpointers[t][j] = i
                    }
                }
            }
        }

        // Add end transitions before backtrace
        for j in 0..<numLabels {
            viterbi[seqLen - 1][j] += endTransitions[j]
        }

        // Backtrace
        var bestPath = [Int](repeating: 0, count: seqLen)
        bestPath[seqLen - 1] = viterbi[seqLen - 1].enumerated().max(by: { $0.1 < $1.1 })!.0
        for t in stride(from: seqLen - 2, through: 0, by: -1) {
            bestPath[t] = backpointers[t + 1][bestPath[t + 1]]
        }

        return bestPath.map { labels[$0] }
    }
}
```

```swift
import CoreML

class MLIngredientParser: IngredientParser {

    private let model: IngredientTaggerEmissions  // Auto-generated by Xcode
    private let vocabulary: [String: Int]
    private let viterbiDecoder: ViterbiDecoder

            return nil
        }

        self.vocabulary = vocab
        self.viterbiDecoder = decoder
    }

    func parse(_ input: String) -> ParserResult {
        let tokens = tokenize(input)
        let tokenIds = tokens.map { vocabulary[$0.lowercased()] ?? 0 }

        // Step 1: CoreML emission scores
        guard let emissions = runEmissionModel(tokenIds: tokenIds) else {
            return fallbackResult(input)
        }

        // Step 2: Viterbi decode (CRF step, in Swift)
        let labelSequence = viterbiDecoder.decode(emissions: emissions)

        // Step 3: Assemble structured result from token labels
        let components = assembleComponents(tokens: tokens, labels: labelSequence)

        return ParserResult(
            name: components.name,
            quantity: components.quantity,
            unit: components.unit,
            notes: components.comment,
            confidence: components.confidence,
            originalText: input,
            parserUsed: parserName
        )
    }

    private static func loadVocabulary() -> [String: Int]? {
        guard let url = Bundle.main.url(forResource: "vocabulary", withExtension: "json"),
              let data = try? Data(contentsOf: url) else { return nil }
        return try? JSONDecoder().decode([String: Int].self, from: data)
    }

    private static func loadViterbiDecoder() -> ViterbiDecoder? {
        guard let url = Bundle.main.url(forResource: "transitions", withExtension: "json"),
              let data = try? Data(contentsOf: url) else { return nil }
        // Decode {"transitions": [[Float]], "start_transitions": [Float],
        //         "end_transitions": [Float], "labels": [String]}
        guard let dict = try? JSONSerialization.jsonObject(with: data) as? [String: Any],
              let transitions = dict["transitions"] as? [[Double]],
              let startTransitions = dict["start_transitions"] as? [Double],
              let endTransitions = dict["end_transitions"] as? [Double],
              let labels = dict["labels"] as? [String] else { return nil }
        return ViterbiDecoder(
            transitions: transitions.map { $0.map { Float($0) } },
            startTransitions: startTransitions.map { Float($0) },
            endTransitions: endTransitions.map { Float($0) },
            labels: labels
        )
    }
```

**`MLMultiArray` extraction (critical implementation detail)**:
CoreML returns `MLMultiArray` with shape `[1, seq_len, 7]`. Extracting to `[[Float]]` requires stride-based access:
```swift
private func runEmissionModel(tokenIds: [Int]) -> [[Float]]? {
    let inputArray = try? MLMultiArray(shape: [1, tokenIds.count as NSNumber], dataType: .int32)
    guard let inputArray else { return nil }
    for (i, id) in tokenIds.enumerated() {
        inputArray[[0, i] as [NSNumber]] = NSNumber(value: id)
    }
    guard let output = try? model.prediction(token_ids: inputArray),
          let emissions = output.emissions else { return nil }
    // Extract using strides — do NOT assume contiguous Float32 layout
    // Neural Engine may use Float16; MLMultiArray.dataType tells you
    let seqLen = emissions.shape[1].intValue
    let numLabels = emissions.shape[2].intValue
    var result = [[Float]]()
    for t in 0..<seqLen {
        var row = [Float]()
        for j in 0..<numLabels {
            row.append(emissions[[0, t, j] as [NSNumber]].floatValue)
        }
        result.append(row)
    }
    return result
}
```

```swift
func parse(_ input: String) -> ParserResult {
    // Step 1: Regex fast path (microseconds)
    let regexResult = regexParser.parse(input)
    if regexResult.confidence >= 0.9 { return regexResult }

    // Step 2: ML model (milliseconds)
    if let mlParser = mlParser {
        let mlResult = mlParser.parse(input)
        if mlResult.confidence >= 0.8 { return mlResult }

        // Step 3: NLP fallback only if ML also uncertain
        if regexResult.confidence < 0.5 && mlResult.confidence < 0.5 {
            let nlpResult = nlpParser.parse(input)
            return [regexResult, mlResult, nlpResult]
                .max(by: { $0.confidence < $1.confidence })!
        }

        // Return better of regex vs ML
        return mlResult.confidence > regexResult.confidence ? mlResult : regexResult
    }

    // Fallback: original behavior (no ML model available)
    if regexResult.confidence >= 0.8 { return regexResult }
    let nlpResult = nlpParser.parse(input)
    return nlpResult.confidence > regexResult.confidence ? nlpResult : regexResult
}
```

**File modified**: `Services/ParsingTelemetryService.swift` — added export method:

```swift
func exportCorrectionsAsTrainingData() -> String
```

Algorithm: synthetic reconstruction from corrected fields (not raw input alignment):
1. Quality filter: skip no-op corrections and empty corrected names
2. Tokenize corrected quantity → label QTY, unit → label UNIT, name → label NAME
3. Serialize as `{"labels":[...],"tokens":[...]}` JSONL lines
4. Uses shared `foragerTokenize()` for token consistency

#### Step 4: Python Retraining Script

**File created**: `Tools/ml-training/retrain_with_corrections.py`

Imports all infrastructure from `train_model.py` — no model/dataset/training code duplication.

```bash
python retrain_with_corrections.py --corrections corrections.jsonl
python retrain_with_corrections.py --corrections corrections.jsonl --skip-gate  # testing
```

Pipeline (6 steps):
1. Load corrections JSONL — validate format (token/label count match, valid labels)
2. Corpus gate — require ≥50 corrections (skip with `--skip-gate`)
3. Load base training data (55k train + 6.8k val + 6.8k test)
4. Load existing model checkpoint, evaluate baseline metrics on test set
5. Merge corrections with oversampling (auto-calculated, capped at 50x), fine-tune from checkpoint with lower LR (0.0005 vs 0.001), max 10 epochs, patience 3
6. Compare before/after metrics table. Save retrained artifacts to `models/retrained/` only if both token AND sentence accuracy improve

Design decisions:
- **Fine-tune, not retrain from scratch** — lower LR prevents catastrophic forgetting
- **Oversampling** — corrections are negligible vs 55k base; auto-oversample up to 50x (~4.5% of training set)
- **Improvement gate** — only save if both primary metrics ≥ baseline
- **No vocabulary rebuild** — reuse existing vocab; unknown correction tokens → UNK (ID 0)

**This is NOT automated in v1.** The workflow is:
1. User uses app normally → corrections accumulate in telemetry (Phase 7)
2. Developer exports corrections via debug menu (already exists in M8.1)
3. Developer verifies minimum corpus gate is met (≥50 corrections)
4. Developer runs retraining script locally
5. If model improves → ship updated model in next app update

## 8. Risks and Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| CoreML model too large for app bundle | App size bloat | BiLSTM emission scorer targets 2-5 MB; quantize to float16 if needed |
| Model accuracy lower than regex for standard formats | Regression | Regex still handles high-confidence inputs (≥0.9); ML only consulted for ambiguous cases |
| Tokenizer misalignment (Python ↔ Swift) | Wrong predictions | Shared 100-sentence test set validated in both environments. Tokenizer is the #1 subtle failure mode. |
| NYT dataset quality issues | Poor training | strangetom dataset is cleaner (95% accuracy); use it as primary, NYT as supplement only for non-overlapping rows |
| Training requires GPU | Developer bottleneck | BiLSTM-CRF trains on CPU in <2h for this dataset size; no GPU required |
| Python tooling dependency | Setup complexity | Minimal deps (torch, coremltools, numpy, pandas); documented in requirements.txt |
| strangetom fraction encoding (`1#1$2`) | Data quality | Must decode during dataset prep (Phase 1). Test with spot-checks. |
| CoreML first-prediction warmup (100-500ms) | UI latency spike on first parse | Background warmup prediction during app init (Phase 5). Steady-state latency is <5ms. |
| `MLMultiArray` data type varies by compute unit | Silent precision errors | Neural Engine returns Float16; CPU returns Float32. Always use `.floatValue` accessor (handles conversion). See Phase 4b implementation sketch. |
| `RangeDim` non-default shapes fall back to CPU | Battery during bulk ops | For a 2-5MB BiLSTM, CPU is fast enough (<5ms). Consider `EnumeratedShapes` with common lengths in v2 if ANE execution matters. |
| ML parser fails to load silently | Undetected degradation | Model presence guard test + `#if DEBUG` warning log (Phase 5). Failable `init?()` is correct for production graceful degradation. |

**Resolved risks** (from research + principal engineering review):
- ~~coremltools conversion fails for CRF layer~~ → **Resolved**: CRF layer is NOT exported to CoreML. The architecture splits into BiLSTM emission scorer (CoreML) + CRF transition matrix (JSON) + Viterbi decoder (Swift). This is the standard approach and is well-tested.
- ~~CRF decode parity risk~~ → **Mitigated**: Phase 0d defines hard parity gate (≥99.9% token agreement). ViterbiDecoder consumes start/end transitions. Phase 3 blocks on parity report.
- ~~Model architecture ambiguity (word vs word+char)~~ → **Resolved**: Locked to word-only for v1 (Phase 0a). Removes dual-input conversion complexity.
- ~~Double parsing per ingredient~~ → **Resolved**: Phase 0c refactors all double-parse call sites (5 identified) + consolidates telemetry to cover 11 previously unlogged `parseIngredient()` callers.
- ~~Correction data not wired~~ → **Mitigated**: Phase 7 wires `logCorrection()` into 4 production edit flows. Phase 8 gated on ≥50 corrections.
- ~~Correction linkage depends on non-existent `parseEventId`~~ → **Resolved**: v1 uses unlinked corrections (`originalEventId: nil`). Linkage design deferred — see Phase 7 Correction Linkage Contract.
- ~~Per-parser correction rate underspecified with unlinked corrections~~ → **Resolved**: Provenance rules define which flows produce attributable corrections. Per-parser rates computed on attributable subset only, with denominator guardrails (N ≥ 20).
- ~~Correction source typing ambiguous~~ → **Resolved**: Dedicated `CorrectionSource` enum (edit-flow oriented) distinct from `ParsingSource` (parse-context oriented).
- ~~Background dispatch conflicts with synchronous parser protocol~~ → **Resolved**: Parsers remain synchronous. Background dispatch owned by service/callsite layers (Phase 5). Includes `AddIngredientsToListView` and `MealPlanDetailView` bulk call sites.
- ~~Parser attribution semantics conflict (`hybrid` vs winner-only)~~ → **Resolved**: Winner-only attribution with explicit Phase 5 sub-steps (code change, comment updates, test updates). `parserUsed` reports the winning parser (`regex`/`ml`/`nlp`).
- ~~Telemetry schema v3 not specified~~ → **Resolved**: Phase 7 includes schema v3 migration plan (`parserUsed` + `source: CorrectionSource` fields) with backward-compatible decoding.
- ~~Stale char-feature and 7×7-only references~~ → **Resolved**: All model/CRF text normalized to match v1 contract (including Section 2 overview and training diagram).
- ~~Static `sharedParser` implicitly gets ML parser~~ → **Documented**: Phase 5 acknowledges lazy CoreML model loading via static `sharedParser` is acceptable (<10MB runtime memory). Background warmup prediction added to prevent first-call latency spike. `#if DEBUG` warning log added for failed model loads.

- ~~Legacy `"hybrid"` telemetry values~~ → **Documented**: Keep as legacy bucket in historical reports; map to `"legacy_hybrid"` if aggregating across versions.

## 9. Out of Scope

- **Automated retraining**: v1 is manual export + retrain. Automated pipeline is M10+
- **Recipe import parsing**: Different input format (HTML/text blocks). Separate initiative.
- **Multi-language support**: English only for launch. Dataset is English.
- **Cloud-based model serving**: All inference on-device. Period.
- **Character-level features**: v1 uses word-only embeddings. Char CNN/LSTM may be added in v2 if accuracy plateaus.
- **Transformer architecture**: BiLSTM + Viterbi unless size/speed targets missed, then revisit.
- **End-to-end CRF in CoreML**: CRF layers don't convert. The split architecture (CoreML emissions + Swift Viterbi) is the final design.
- **Automated threshold tuning**: v1 uses heuristic thresholds with offline calibration. Online A/B testing or auto-tuning is v2+.
- **Disagreement arbitration**: If regex and ML disagree on structural slots, v1 uses confidence-based routing. Structural disagreement detection is v2+.
