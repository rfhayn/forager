## 1. Problem Statement

Forager's current parsing pipeline — `RegexIngredientParser` (fast path) → `NLPIngredientParser` (Apple NaturalLanguage fallback) → `HybridIngredientParser` (router) — handles standard recipe formats well but fails on:

| Input | Expected | Current Result | Root Cause |
|-------|----------|----------------|------------|
| `3 cloves garlic` | qty=3, unit=clove, name=garlic | name="cloves garlic" | Regex doesn't know "clove" is a unit in this context |
| `1/4 tsp black pepper` (via meal plan) | name=black pepper | name="/ black pepper" | `extractCleanIngredientName()` strips fraction parts separately |
| `bananas` | template=bananas | template=banana | Pluralization table incomplete |
| `milk 2%` | no warning | needsReview=true | Digit heuristic doesn't know about product variants |
| `a handful of fresh cilantro` | qty=1, name=cilantro | name="handful fresh cilantro" | Descriptive amounts not fully extracted |
| `salt and pepper to taste` | name=salt and pepper | name="salt and pepper to taste" | Qualifier stripping incomplete |

These are **class-level failures** — fixing them one-by-one with regex additions creates an ever-growing rule set that's brittle and untestable. A machine-learned model trained on real ingredient data solves the entire class.

## 2. Approach: Dataset-Bootstrapped CoreML Sequence Labeler

### Why Not the Original M8.4 Plan?

The M8.4 plan in the M8 Meta-PRD (lines 1585-2384) proposed a Create ML Text Classifier that:
- Requires **100+ user corrections** before training — cold start problem
- Uses flat classification ("2.0|cup|flour") — loses token-level context
- Can't handle unseen ingredient formats without retraining

### What Changed: Open-Source Dataset Bootstrapping

Two high-quality open-source datasets provide immediate training data:

| Dataset | Size | Format | License | Accuracy | Approach |
|---------|------|--------|---------|----------|----------|
| [strangetom/ingredient-parser](https://github.com/strangetom/ingredient-parser) | 81,316 sentences | **SQLite** (`en` table) | MIT | 95.25% sentence / 98.09% word | CRF (pycrfsuite) |
| [NYT ingredient-phrase-tagger](https://github.com/NYTimes/ingredient-phrase-tagger) | 180,000 examples | CSV (7 columns) | Apache 2.0 | N/A (CRF baseline) | CRF + manual review |

**Key finding**: strangetom already **includes NYT data** as one of its 5 sources (NYT, BBC, cookstr, allrecipes, tastecooking). Direct combination would create duplicates. Strategy: use strangetom as primary (pre-tokenized, richer labels), supplement with NYT rows not in strangetom for additional coverage.

After dedup, expect **~120,000-150,000 unique sentences** — still more than sufficient for a BiLSTM model.

### Architecture: Sequence Labeling (Token-Level)

Instead of flat classification, use **token-level sequence labeling** (the standard approach in NLP for entity extraction):

```
Input:  "2    cups   all-purpose   flour"
Labels:  QTY  UNIT   B_NAME_TOK   I_NAME_TOK
```

**strangetom's native label set (12 labels)**:
| Label | Meaning | Example tokens |
|-------|---------|----------------|
| `QTY` | Quantity | `2`, `1/4`, `one` |
| `UNIT` | Unit of measure | `cups`, `tsp`, `cloves` |
| `B_NAME_TOK` | Name (first token) | `all-purpose` |
| `I_NAME_TOK` | Name (continuation) | `flour` |
| `NAME_VAR` | Name variant/modifier | `2%` in "milk 2%" |
| `NAME_SEP` | Name separator | `and` in "salt and pepper" |
| `NAME_MOD` | Name modification | `fresh` in "fresh cilantro" |
| `SIZE` | Size descriptor | `large` in "3 large eggs" |
| `PREP` | Preparation | `chopped`, `diced` |
| `COMMENT` | Comment/qualifier | `to taste`, `optional` |
| `PURPOSE` | Purpose clause | `for garnish` |
| `PUNC` | Punctuation | `,`, `(`, `)` |
| `OTHER` | Other | tokens that don't fit |

**Simplified label mapping for Forager** (strangetom 12 → Forager 7):
```
QTY                          → QTY
UNIT                         → UNIT
B_NAME_TOK, I_NAME_TOK,
  NAME_VAR, NAME_SEP         → NAME
NAME_MOD, SIZE               → MODIFIER
PREP                         → PREP
COMMENT, PURPOSE             → COMMENT
PUNC, OTHER                  → OTHER
```

This reduces label count while preserving the distinctions Forager needs. The model learns what role each token plays, regardless of ordering.

### On-Device CoreML Pipeline

> **Critical architecture decision**: CRF layers **cannot** convert to CoreML via coremltools.
> The solution: split the BiLSTM-CRF into two components:
> 1. **BiLSTM emission scorer** → CoreML (standard LSTM conversion, well-supported)
> 2. **CRF transition matrix** → JSON/plist (just a 7×7 float array = 49 numbers)
> 3. **Viterbi decoder** → Pure Swift (~30 lines, runs the CRF decoding step)

```
Training (Mac):
  strangetom SQLite + NYT CSV
  → Unified token-labeled format (7 Forager labels)
  → PyTorch BiLSTM-CRF
  → Export BiLSTM emission scorer via coremltools → .mlpackage
  → Export CRF transition matrix → transitions.json

Runtime (iOS):
  Input text
  → Tokenize → token IDs (via vocabulary.json)
  → CoreML prediction (emission scores per token × 7 labels)
  → Swift Viterbi decoder (emissions + transition matrix → optimal label sequence)
  → Decode labels → ParserResult
  → Slot into HybridIngredientParser
```

**Privacy**: All inference on-device. Training data is open-source. No user data ever leaves the device.

## 5. Implementation Phases

### Phase 1: Dataset Preparation (3-4h)

**Deliverable**: Unified token-labeled dataset ready for training

**Step 1: Download and inspect strangetom dataset** (primary — 81,316 sentences)

The strangetom dataset is a **SQLite database** (not CSV). Schema:
```sql
-- Table: en
-- Columns:
--   id        INTEGER PRIMARY KEY
--   source    TEXT     -- "nyt", "bbc", "cookstr", "allrecipes", "tastecooking"
--   sentence  TEXT     -- Original ingredient string: "2 cups all-purpose flour"
--   tokens    TEXT     -- JSON array: ["2", "cups", "all-purpose", "flour"]
--   labels    TEXT     -- JSON array: ["QTY", "UNIT", "B_NAME_TOK", "I_NAME_TOK"]
--   sentence_split  TEXT  -- Not needed (sentence-level grouping)
--   fdc_mapping     TEXT  -- Not needed (USDA food codes)
```

**Fraction encoding gotcha**: strangetom uses non-standard fraction notation:
- `1#1$2` = 1½ (1 + 1/2) — format: `whole#numerator$denominator`
- `3$4` = ¾ — format: `numerator$denominator`
- Must decode these to decimal during prep

**Step 2: Download NYT dataset** (supplement — 180k examples)

NYT is a flat CSV with 7 columns:
```
index, input, name, qty, range_end, unit, comment
```

NYT provides **sentence-level labels** (not token-level). Converting to token labels requires:
- Tokenize the `input` string
- Match each token against the `qty`, `unit`, `name`, `comment` fields
- Assign label based on which field the token belongs to

**Important**: strangetom already includes NYT data (source="nyt"). Use sentence-level dedup to avoid duplicates.

**Step 3: Write converter** (`tools/ml-training/prepare_dataset.py`):
1. Load strangetom SQLite → extract `tokens` and `labels` JSON arrays
2. Decode fraction notation (`1#1$2` → `1.5`)
3. Map strangetom's 12 labels → Forager's 7 labels (see Section 2)
4. Load NYT CSV → tokenize + align to generate token labels
5. Deduplicate by normalized sentence text (strangetom includes NYT already)
6. 80/10/10 train/validation/test split (stratified by source)
7. Output: `training_data.jsonl`, `validation_data.jsonl`, `test_data.jsonl`

**Output format** (JSON Lines — one sentence per line):
```json
{"tokens": ["2", "cups", "all-purpose", "flour"], "labels": ["QTY", "UNIT", "NAME", "NAME"]}
{"tokens": ["1/4", "tsp", "salt"], "labels": ["QTY", "UNIT", "NAME"]}
```

**Step 4: Validate**
- Spot-check 100 random samples for label accuracy
- Log statistics: total sentences, label distribution, vocabulary size
- Verify no data leakage between splits

**Acceptance criteria**:
- ≥80,000 unique sentences after dedup (strangetom alone provides 81k)
- All tokens have valid Forager labels (7 classes)
- Fraction notation fully decoded (no `#` or `$` in output)
- Train/val/test splits are stratified (similar label distributions)
- No data leakage between splits

### Phase 2: Model Architecture & Training (4-5h)

**Deliverable**: Trained PyTorch BiLSTM-CRF model with ≥95% token accuracy on test set

**Architecture choice**: BiLSTM-CRF (split export — see Phase 3)

Why BiLSTM-CRF over Transformer:
- **Model size**: ~2-5 MB vs. 50-100 MB for a transformer — critical for app bundle size
- **Inference speed**: <5ms vs. 20-50ms — must stay under parsing target (<50ms)
- **Training data**: 80-150k sentences is enough for BiLSTM-CRF but marginal for a transformer
- **Proven on this exact domain**: strangetom's CRF achieves 95.25% sentence accuracy on ingredient parsing

**Model specification**:
```python
# tools/ml-training/train_model.py
class IngredientTagger(nn.Module):
    embedding_dim = 128     # Character + word embeddings
    hidden_dim = 256        # BiLSTM hidden size
    num_labels = 7          # QTY, UNIT, NAME, MODIFIER, PREP, COMMENT, OTHER
    vocab_size = ~8000      # Word vocabulary from training data
    char_vocab = 128        # ASCII character vocabulary

    # Components:
    # 1. Word embedding (vocab_size × embedding_dim)
    # 2. Character CNN/LSTM (char_vocab × 32, per-word)
    # 3. BiLSTM (2 layers, hidden_dim)
    # 4. CRF layer (num_labels × num_labels transition matrix)
```

**Training script** (`tools/ml-training/train_model.py`):
1. Load prepared JSONL datasets
2. Build word + character vocabularies → save as `vocabulary.json`
3. Train BiLSTM-CRF with:
   - Learning rate: 0.001 (Adam)
   - Batch size: 64
   - Max epochs: 30 with early stopping (patience=5)
   - Dropout: 0.5
4. Evaluate on test set
5. Export model checkpoint (`ingredient_tagger.pt`)
6. Export CRF transition matrix separately (`transitions.json` — 7×7 float array)
7. Export vocabulary mapping (`vocabulary.json`)

**Acceptance criteria**:
- Token-level accuracy ≥ 96% on test set
- Sentence-level accuracy ≥ 92% on test set
- Model file < 10 MB
- Training completes in < 2 hours on MacBook Pro
- Transition matrix and vocabulary exported as separate JSON files

#### 4a: Viterbi Decoder (~30 lines of Swift)

**File**: `Services/Parsing/ViterbiDecoder.swift`

The Viterbi algorithm finds the optimal label sequence given emission scores and transition costs. This is the CRF decoding step that can't run in CoreML.

```swift
struct ViterbiDecoder {
    let transitions: [[Float]]  // 7×7 transition scores (label_i → label_j)
    let labels: [String]        // ["QTY", "UNIT", "NAME", "MODIFIER", "PREP", "COMMENT", "OTHER"]

    /// Decode the optimal label sequence from emission scores
    /// - Parameter emissions: (seq_len × num_labels) matrix of emission scores from CoreML
    /// - Returns: Array of label strings, one per token
    func decode(emissions: [[Float]]) -> [String] {
        let seqLen = emissions.count
        let numLabels = labels.count
        guard seqLen > 0 else { return [] }

        // Standard Viterbi: forward pass with backpointers, then backtrace
        var viterbi = [[Float]](repeating: [Float](repeating: -Float.infinity, count: numLabels), count: seqLen)
        var backpointers = [[Int]](repeating: [Int](repeating: 0, count: numLabels), count: seqLen)

        // Initialize
        for j in 0..<numLabels { viterbi[0][j] = emissions[0][j] }

        // Forward pass
        for t in 1..<seqLen {
            for j in 0..<numLabels {
                for i in 0..<numLabels {
                    let score = viterbi[t-1][i] + transitions[i][j] + emissions[t][j]
                    if score > viterbi[t][j] {
                        viterbi[t][j] = score
                        backpointers[t][j] = i
                    }
                }
            }
        }

        // Backtrace
        var bestPath = [Int](repeating: 0, count: seqLen)
        bestPath[seqLen - 1] = viterbi[seqLen - 1].enumerated().max(by: { $0.1 < $1.1 })!.0
        for t in stride(from: seqLen - 2, through: 0, by: -1) {
            bestPath[t] = backpointers[t + 1][bestPath[t + 1]]
        }

        return bestPath.map { labels[$0] }
    }
}
```

#### 4b: MLIngredientParser

**File**: `Services/Parsing/MLIngredientParser.swift`

```swift
import Foundation
import CoreML

class MLIngredientParser: IngredientParser {
    let parserName = "ml"

    private let model: IngredientTaggerEmissions  // Auto-generated by Xcode
    private let vocabulary: [String: Int]
    private let viterbiDecoder: ViterbiDecoder

    init?() {
        // Load CoreML emission model
        guard let model = try? IngredientTaggerEmissions(configuration: .init()) else {
            return nil
        }
        // Load vocabulary and transition matrix from bundle
        guard let vocab = Self.loadVocabulary(),
              let decoder = Self.loadViterbiDecoder() else {
            return nil
        }
        self.model = model
        self.vocabulary = vocab
        self.viterbiDecoder = decoder
    }

    func parse(_ input: String) -> ParserResult {
        let tokens = tokenize(input)
        let tokenIds = tokens.map { vocabulary[$0.lowercased()] ?? 0 }

        // Step 1: CoreML emission scores
        guard let emissions = runEmissionModel(tokenIds: tokenIds) else {
            return fallbackResult(input)
        }

        // Step 2: Viterbi decode (CRF step, in Swift)
        let labelSequence = viterbiDecoder.decode(emissions: emissions)

        // Step 3: Assemble structured result from token labels
        let components = assembleComponents(tokens: tokens, labels: labelSequence)

        return ParserResult(
            name: components.name,
            quantity: components.quantity,
            unit: components.unit,
            notes: components.comment,
            confidence: components.confidence,
            originalText: input,
            parserUsed: parserName
        )
    }

    private static func loadVocabulary() -> [String: Int]? {
        guard let url = Bundle.main.url(forResource: "vocabulary", withExtension: "json"),
              let data = try? Data(contentsOf: url) else { return nil }
        return try? JSONDecoder().decode([String: Int].self, from: data)
    }

    private static func loadViterbiDecoder() -> ViterbiDecoder? {
        guard let url = Bundle.main.url(forResource: "transitions", withExtension: "json"),
              let data = try? Data(contentsOf: url) else { return nil }
        // Decode {"transitions": [[Float]], "labels": [String]}
        guard let dict = try? JSONSerialization.jsonObject(with: data) as? [String: Any],
              let transitions = dict["transitions"] as? [[Double]],
              let labels = dict["labels"] as? [String] else { return nil }
        return ViterbiDecoder(
            transitions: transitions.map { $0.map { Float($0) } },
            labels: labels
        )
    }
}
```

**Key implementation details**:
- **Tokenization**: Split on whitespace, handle punctuation, Unicode fractions → decimal
- **Vocabulary lookup**: Map tokens to integer IDs using `vocabulary.json` from training; unknown tokens → ID 0 (UNK)
- **Two-step inference**: CoreML emissions → Swift Viterbi → label sequence
- **Label assembly**: Group consecutive same-label tokens, extract qty/unit/name/comment
- **Confidence**: Derived from emission softmax probabilities (geometric mean of max per-token probability)
- **Graceful fallback**: If any resource (model, vocabulary, transitions) fails to load → `init?()` returns nil → HybridIngredientParser skips ML step

**Tokenizer alignment contract**: The Swift tokenizer must match the Python tokenizer exactly — same whitespace splitting, same punctuation handling, same lowercasing. Misalignment = wrong predictions. Write a shared test set (100 sentences) validated in both Python and Swift.

**Acceptance criteria**:
- Implements `IngredientParser` protocol
- Handles all 7 regex pattern categories (unicode fractions, ranges, parentheticals, compounds, standard, qualifiers, descriptive)
- Returns correct `parserUsed: "ml"` for telemetry
- Gracefully returns nil from init if any resource unavailable
- Viterbi decoder matches Python reference implementation on 1000 test cases
- All tokens decoded — no lost information

> **Note**: M9.5-partial (✅ complete) provides the DI infrastructure. Sub-parsers and threshold

> + update routing logic. Uses `IngredientParser?` (protocol type) to enable mock injection in Phase 6.

Change from (post-M9.5-partial state):
```swift
private let regexParser: IngredientParser
private let nlpParser: IngredientParser
private let regexConfidenceThreshold: Float

init(regexParser: IngredientParser = RegexIngredientParser(),
     nlpParser: IngredientParser = NLPIngredientParser(),
     regexConfidenceThreshold: Float = 0.8) { ... }
```

To:
```swift
private let regexParser: IngredientParser

private let nlpParser: IngredientParser
private let regexConfidenceThreshold: Float

init(regexParser: IngredientParser = RegexIngredientParser(),
     nlpParser: IngredientParser = NLPIngredientParser(),
     mlParser: IngredientParser? = MLIngredientParser(),
     regexConfidenceThreshold: Float = 0.9) { ... }
```

New routing logic:
```swift
func parse(_ input: String) -> ParserResult {
    // Step 1: Regex fast path (microseconds)
    let regexResult = regexParser.parse(input)
    if regexResult.confidence >= 0.9 { return regexResult }

    // Step 2: ML model (milliseconds)
    if let mlParser = mlParser {
        let mlResult = mlParser.parse(input)
        if mlResult.confidence >= 0.8 { return mlResult }

        // Step 3: NLP fallback only if ML also uncertain
        if regexResult.confidence < 0.5 && mlResult.confidence < 0.5 {
            let nlpResult = nlpParser.parse(input)
            return [regexResult, mlResult, nlpResult]
                .max(by: { $0.confidence < $1.confidence })!
        }

        // Return better of regex vs ML
        return mlResult.confidence > regexResult.confidence ? mlResult : regexResult
    }

    // Fallback: original behavior (no ML model available)
    if regexResult.confidence >= 0.8 { return regexResult }
    let nlpResult = nlpParser.parse(input)
    return nlpResult.confidence > regexResult.confidence ? nlpResult : regexResult
}
```

**Key design decisions**:
- Regex threshold raised from 0.8 → 0.9 (only skip ML for very high-confidence regex)
- ML parser is optional (`MLIngredientParser?`) — app works without model
- NLP only consulted when both regex and ML are uncertain
- `parserUsed` telemetry tracks which parser won

**Acceptance criteria**:
- Existing tests pass unchanged (regex-dominated inputs still work)
- ML parser consulted for ambiguous inputs
- App still works if model file is removed from bundle
- Telemetry correctly tracks "regex", "ml", "nlp", "hybrid" attribution

## 8. Risks and Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| CoreML model too large for app bundle | App size bloat | BiLSTM emission scorer targets 2-5 MB; quantize to float16 if needed |
| Model accuracy lower than regex for standard formats | Regression | Regex still handles high-confidence inputs (≥0.9); ML only consulted for ambiguous cases |
| Tokenizer misalignment (Python ↔ Swift) | Wrong predictions | Shared 100-sentence test set validated in both environments. Tokenizer is the #1 subtle failure mode. |
| NYT dataset quality issues | Poor training | strangetom dataset is cleaner (95% accuracy); use it as primary, NYT as supplement only for non-overlapping rows |
| Training requires GPU | Developer bottleneck | BiLSTM-CRF trains on CPU in <2h for this dataset size; no GPU required |
| Python tooling dependency | Setup complexity | Minimal deps (torch, coremltools, numpy, pandas); documented in requirements.txt |
| strangetom fraction encoding (`1#1$2`) | Data quality | Must decode during dataset prep (Phase 1). Test with spot-checks. |

**Resolved risk** (from research):
- ~~coremltools conversion fails for CRF layer~~ → **Resolved**: CRF layer is NOT exported to CoreML. The architecture splits into BiLSTM emission scorer (CoreML) + CRF transition matrix (JSON) + Viterbi decoder (Swift). This is the standard approach and is well-tested.

## 9. Out of Scope

- **Automated retraining**: v1 is manual export + retrain. Automated pipeline is M10+
- **Recipe import parsing**: Different input format (HTML/text blocks). Separate initiative.
- **Multi-language support**: English only for launch. Dataset is English.
- **Cloud-based model serving**: All inference on-device. Period.
- **Transformer architecture**: BiLSTM + Viterbi unless size/speed targets missed, then revisit.
- **End-to-end CRF in CoreML**: CRF layers don't convert. The split architecture (CoreML emissions + Swift Viterbi) is the final design.
