# M9.1.2: Centralize `extractCleanIngredientName`

**Status**: COMPLETE
**Branch**: `feature/M9.1.2-centralize-extract-clean-name`
**Estimate**: ~1.5 hours

## Problem

Two private implementations of `extractCleanIngredientName(from:)` existed in view files:

1. **AddIngredientsToListView** (40 lines, 5 call sites) — comprehensive regex with qualifier stripping
2. **MealPlanDetailView** (18 lines, 1 call site) — weaker regex, no qualifier stripping

They used different regex patterns and handled different edge cases, causing inconsistent template names (e.g., MealPlanDetailView producing "Salt To Taste" instead of "Salt").

Meanwhile, `HybridIngredientParser.parse()` already extracts ingredient names using 7 regex pattern categories + NLP fallback — the view-layer functions were reimplementing what the parser does, poorly.

## Solution

A single `static` method on `IngredientParsingService` that delegates to the parser:

```swift
static func extractCleanIngredientName(from text: String) -> String
```

### Design Decisions

- **`static`**: Call sites in views don't hold an `IngredientParsingService` instance. Static avoids requiring DI for a pure utility.
- **Cached parser**: `static let sharedParser` is thread-safe (Swift atomic lazy init). All parsers hold zero mutable instance state.
- **Delegates to parser**: Gets all 7 regex patterns + NLP for free. Eliminates regex divergence.
- **Fallback**: If parser returns empty name, capitalize the trimmed input.

## Behavioral Changes

- **Improvement**: MealPlanDetailView's bulk-add now gets parser-quality name extraction.
- **Qualifier stripping**: The parser doesn't strip leading adjectives ("3 large eggs" -> "large eggs"), but `findOrCreateTemplate(name:)` runs `normalize()` Phase 4 which strips these qualifiers. The stripping still happens, in the right layer.
- **No regression for matching**: Call site using `.lowercased()` comparison after extraction works identically with capitalized output.
