## 1. Problem Statement

The BiLSTM-CRF ingredient parsing model (M8.4) was trained on 68,846 sentences from the strangetom/ingredient-parser dataset. While it achieves 98.49% token accuracy and 95.40% sentence accuracy on that dataset's test split, real-world recipe imports surface parsing failures that the training data does not cover:

- Site-specific formatting (Budget Bytes price annotations, RecipeTinEats double-paren notes)
- Compound prep instructions after commas ("finely minced", "peeled and deveined")
- Can size patterns ("15-ounce can", "28-oz can")
- Range quantities ("1-2 medium", "2 to 3 tablespoons")
- Product variant modifiers ("2% milk", "extra-virgin")

The M16 parsing test harness now runs 50 recipes per cycle, comparing local parser output against Claude API reference parses. Each harness run produces structured JSON with the raw ingredient text, the local parse result, and the AI-labeled result (name, qty, unit, notes). This AI-labeled data is effectively a high-quality labeling oracle that can generate training examples at scale.

**The gap**: We have a training pipeline (`Tools/ml-training/`) and a data collection pipeline (`Tools/ParsingTestHarness/`), but no bridge between them. The harness output (field-level: name/qty/unit/notes per ingredient) needs to be converted to the model's input format (token-level: BIO-tagged sequences in JSONL) before retraining can happen.

## 2. Current State

### Model Architecture (Frozen)
- **BiLSTM-CRF** with word-level embeddings (no char features)
- Embedding dim: 128, Hidden dim: 256, 2 LSTM layers, dropout 0.5
- 7 labels: `QTY`, `UNIT`, `NAME`, `MODIFIER`, `PREP`, `COMMENT`, `OTHER`
- Vocabulary: 5,372 tokens (min_freq=2, `<UNK>`=0, `<PAD>`=1)
- CRF split: CoreML emission scorer (`.mlpackage`) + JSON transitions + Swift Viterbi decoder

### Training Pipeline (Existing)
| Script | Purpose |
|--------|---------|
| `prepare_dataset.py` | strangetom SQLite -> JSONL (80/10/10 split) |
| `train_model.py` | PyTorch BiLSTM-CRF training with early stopping |
| `convert_to_coreml.py` | PyTorch -> CoreML + Viterbi parity gate |
| `retrain_with_corrections.py` | Fine-tune with user corrections JSONL |

### Training Data Format (JSONL)
Each line is a JSON object with parallel `tokens` and `labels` arrays:
```json
{"tokens": ["2", "cups", "all-purpose", "flour"], "labels": ["QTY", "UNIT", "NAME", "NAME"]}
{"tokens": ["3", "cloves", "garlic", ",", "minced"], "labels": ["QTY", "UNIT", "NAME", "OTHER", "PREP"]}
```

### Harness Output Format (JSON)
Each comparison entry in a harness run file:
```json
{
  "raw": "1 (15-ounce) can diced fire-roasted tomatoes in juice",
  "localName": "can diced fire-roasted tomatoes in juice",
  "localNotes": "15-ounce",
  "localQty": 1,
  "localUnit": null,
  "agreement": "ambiguous"
}
```

When AI parsing is enabled, the harness also produces `aiName`, `aiQty`, `aiUnit`, `aiNotes` fields. These AI labels serve as the ground truth for training data generation.

### Tokenizer Contract (Frozen)
Defined in `Tools/ml-training/TOKENIZER_SPEC.md`. The tokenizer is shared between Python (training) and Swift (inference). Pipeline: NFKD normalize -> strip diacritics -> lowercase -> whitespace normalize -> punctuation split -> truncate to 64 tokens. Cross-validated against `data/tokenizer_test_vectors.json` (100 vectors).

## 3. Solution: Harness-to-Training Bridge

### 3.1 Data Conversion — Field Labels to Token Labels

The core challenge: the harness produces **field-level** labels (name, qty, unit, notes per ingredient), but the model trains on **token-level** labels (one label per token in the sequence). Converting between them requires:

1. **Tokenize** the raw ingredient text using the frozen `foragerTokenize()` pipeline
2. **Align** each token to the correct label by matching against the AI-labeled fields

#### Alignment Algorithm

Given a raw ingredient string and its AI-labeled fields (qty, unit, name, notes):

```
Input:  "3 tablespoons butter, melted"
AI:     qty=3.0, unit="tbsp", name="butter", notes="melted"

Step 1 — Tokenize:
  tokens = ["3", "tablespoons", "butter", ",", "melted"]

Step 2 — Match qty tokens:
  "3" matches qty=3.0 -> label QTY

Step 3 — Match unit tokens:
  "tablespoons" normalizes to "tbsp" which matches unit="tbsp" -> label UNIT

Step 4 — Match name tokens:
  "butter" matches name="butter" -> label NAME

Step 5 — Match notes tokens:
  "melted" matches notes="melted" -> label PREP

Step 6 — Remaining tokens:
  "," -> label OTHER (punctuation)

Result:
  {"tokens": ["3", "tablespoons", "butter", ",", "melted"],
   "labels": ["QTY", "UNIT", "NAME", "OTHER", "PREP"]}
```

#### Alignment Edge Cases

| Case | Example | Strategy |
|------|---------|----------|
| Multi-word name | "fire-roasted tomatoes" | Greedy left-to-right match against name tokens |
| Unit normalization | "Tablespoons" -> "tbsp" | Match against unit synonym map (already in MLIngredientParser) |
| Quantity fractions | "1/2" | Match against qty as fraction or decimal |
| Mixed fractions | "1 1/2" | Two tokens both map to QTY |
| Parenthetical sizes | "(15-ounce)" | Tokens "(", "15-ounce", ")" -> label based on content |
| Modifier vs name | "fresh basil" | Default to NAME unless in known modifier list |
| PREP vs COMMENT | "for garnish" vs "optional" | "for garnish" -> COMMENT (purpose), prep verbs -> PREP |
| Range quantities | "1-2" | Single token, label QTY |
| No AI data | AI parsing skipped | Skip ingredient (local-only runs cannot generate training data) |

#### Confidence Filtering

Not all harness comparisons are suitable for training:

- **agreement = "agreement"**: Both local and AI agree -> high confidence, include
- **agreement = "ambiguous"**: AI result available but disagreement -> include AI labels (AI is the oracle)
- **agreement = "local_likely_wrong"**: AI is better -> include AI labels
- **agreement = "ai_likely_wrong"**: AI failed -> EXCLUDE (bad training signal)
- **agreement = "both_wrong"**: Neither is correct -> EXCLUDE
- **No AI fields present**: Skip (no ground truth available)

#### MODIFIER vs NAME Disambiguation

The 7-label schema distinguishes MODIFIER (size descriptors, freshness) from NAME. The AI labels merge these into a single "name" field. To recover the distinction:

- Maintain a **modifier word list**: "large", "small", "medium", "fresh", "frozen", "dried", "canned", "whole", "baby", "extra-virgin", etc.
- If a token is in the modifier list AND appears before the first NAME token -> label MODIFIER
- Otherwise -> label NAME

### 3.2 Vocabulary Extension

The current vocabulary has 5,372 tokens. New harness data will introduce tokens not in the vocabulary (e.g., "epazote", "pasilla", "panko"). Two strategies:

**Option A: Extend vocabulary (recommended)**
- Rebuild vocabulary from combined dataset (original + harness)
- Requires retraining from scratch (embedding layer size changes)
- Better coverage for novel ingredients

**Option B: Keep vocabulary frozen**
- New tokens map to `<UNK>` (ID 0)
- Can fine-tune with `retrain_with_corrections.py` (existing script)
- Worse coverage but simpler pipeline

Recommendation: **Option A** for the first retrain cycle (rebuild vocabulary), then use Option B for incremental fine-tuning between full retrains.

### 3.3 Training Strategy

#### Full Retrain (M16.9.3)

Combine original strangetom data with harness-generated data:

1. Load original `training_data.jsonl` (55,076 samples)
2. Load converted harness data (target: 500-2,000 samples across multiple runs)
3. Deduplicate by token sequence
4. Rebuild vocabulary from combined corpus
5. Split combined data 80/10/10 (ensure harness data appears in all splits proportionally)
6. Train from scratch with same hyperparameters as M8.4
7. Evaluate against original test set AND a held-out harness test set

#### Oversampling

Harness data is a small fraction of the total (~2-4%). To ensure the model learns from it without being overwhelmed by strangetom patterns:

- Oversample harness data by 5-10x in the training split
- Target: harness data = ~10-15% of effective training set
- Matches the approach in `retrain_with_corrections.py` (which targets 4.5% for corrections)

### 3.4 Evaluation Framework

#### Metrics (must match or exceed current model)

| Metric | Current (v1.0) | Minimum for v2.0 |
|--------|----------------|-------------------|
| Token accuracy (strangetom test) | 98.49% | >= 98.00% |
| Sentence accuracy (strangetom test) | 95.40% | >= 95.00% |
| QTY F1 | 0.9968 | >= 0.99 |
| UNIT F1 | 0.9939 | >= 0.99 |
| NAME F1 | 0.9869 | >= 0.98 |
| MODIFIER F1 | 0.9261 | >= 0.92 |
| PREP F1 | 0.9789 | >= 0.97 |

#### Harness-Specific Evaluation

In addition to strangetom test metrics, evaluate on a held-out harness test set:

- **Harness token accuracy**: target >= 95%
- **Harness sentence accuracy**: target >= 90%
- **Regression check**: run the full M16 harness with the retrained model and compare agreement rates against the v1.0 model

#### A/B Comparison Script

New script `compare_models.py` that:
1. Loads both v1.0 and v2.0 models
2. Runs inference on the same test set
3. Reports per-ingredient: which model is better, which is worse, which are tied
4. Flags any regressions where v1.0 was correct but v2.0 is wrong

### 4.2 No Code Changes Required

The Swift inference code (`MLIngredientParser.swift`, `ViterbiDecoder.swift`, `IngredientTokenizer.swift`) does not need changes. The model architecture, input/output shapes, label set, and tokenizer are all frozen. Only the learned weights and vocabulary change.

**One exception**: if vocabulary size changes (Option A), verify that the CoreML model's embedding layer input range accommodates the new vocabulary size. The CoreML model accepts `Int32` token IDs with no upper bound check, so larger vocabularies work without model architecture changes.

### 4.3 Viterbi Parity Gate

After CoreML conversion, the existing `convert_to_coreml.py` parity gate must pass:
- Emission parity (PyTorch vs CoreML): max diff < 0.01
- Viterbi parity (CRF decode vs Python Viterbi): >= 99.9% token agreement
- End-to-end (CoreML emissions + Viterbi vs CRF): >= 99.9%

## 7. Risks and Mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| AI labels are wrong for some ingredients | Medium | Training on bad data | Confidence filtering + manual spot-check in M16.9.2 |
| Token alignment fails on complex ingredients | Medium | Missing or incorrect training samples | Log alignment failures, exclude unaligned samples, iterate on algorithm |
| Retrained model regresses on strangetom data | Low | Worse than current model | Strict minimum thresholds; abort and investigate if not met |
| Vocabulary extension breaks CoreML model | Low | Model fails to load | Verify CoreML input range accepts new vocab size; test on device |
| Insufficient harness data (< 500 samples) | Medium | Model doesn't learn new patterns | Run more harness cycles; consider supplementing with manual labeling |
| Oversampling causes overfitting to harness data | Medium | Good on harness, worse on general data | Monitor both strangetom and harness test metrics; reduce oversample ratio if needed |
