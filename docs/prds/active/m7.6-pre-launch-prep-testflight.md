## Overview

M7.6 prepares Forager for its first external TestFlight submission. This includes app configuration (display name, launch screen, deployment target), production-environment gating (hiding debug tools), a first-launch onboarding walkthrough, Core Data schema cleanup (removing dead entities and fixing mismatches before CloudKit Production locks them permanently), and the actual TestFlight submission.

**Why schema cleanup gates TestFlight**: CloudKit Production schema is append-only. Once deployed, record types and fields can never be removed or renamed. Every unused entity and misnamed field becomes permanent baggage. M7.6.4-M7.6.6 clean up the schema while we still can.

### M7.6.4: Core Data Schema Cleanup — P0 Must Fix (1-1.5 hours)

**Goal**: Remove dead entities and fix critical cardinality error before CloudKit Production deployment.

**Context**: A comprehensive schema audit (February 8, 2026) identified entities and relationships that would become permanent dead weight in CloudKit Production. These MUST be fixed before the first Production schema deployment.

**Changes:**

1. **Remove `Tag` entity** — Entirely unused
   - Never implemented in any view or service
   - No code references beyond the schema definition
   - Would create permanent `CD_Tag` record type in CloudKit Production
   - Action: Delete from Core Data model, remove any generated files

2. **Remove `LeaveRequest` entity** — Explicitly deprecated
   - Was part of an abandoned member-leave approach
   - Replaced by `KeychainHelper`-based pending leave tracking
   - Would create permanent `CD_LeaveRequest` record type in CloudKit
   - Action: Delete from Core Data model, remove any generated files

3. **Fix `Recipe.plannedMeals` cardinality** — toOne should be toMany
   - Current: `maxCount="1"` (a recipe can only be in 1 meal plan)
   - Correct: No maxCount constraint (a recipe can be planned for multiple days/plans)
   - This is a data integrity bug — once locked in Production, cardinality is permanent
   - Action: Change relationship to toMany in the model editor

4. **Create Core Data model v3**
   - New model version for the schema changes
   - Lightweight migration confirmed to support all three changes (per Apple docs):
     - Entity deletion: "You can add, remove, rename entities"
     - toOne→toMany: "Changing a relationship from a to-one to a to-many"
   - No custom NSMappingModel needed — Core Data infers the migration automatically
   - Test migration from v2 data to verify

**Acceptance Criteria:**
- [ ] Tag entity removed from Core Data model
- [ ] LeaveRequest entity removed from Core Data model
- [ ] Recipe.plannedMeals is toMany relationship
- [ ] Model version 3 created with lightweight migration
- [ ] Clean build, no references to removed entities
- [ ] Existing data migrates cleanly from v2 to v3

**Files to Modify:**
- `forager/forager.xcdatamodeld/` — New v3 model, remove entities, fix cardinality
- Remove any `Tag+CoreData*.swift` or `LeaveRequest+CoreData*.swift` files
- Any code that references Tag or LeaveRequest entities

### M7.6.5: Core Data Schema Cleanup — P1 Should Fix (1-1.5 hours)

**Goal**: Fix misnamed fields, wrong delete rules, and code-schema mismatches.

**Changes:**

1. **Remove `Recipe.titleKey`** — Dead fetch index
   - Never populated in any code path
   - Never queried by any fetch request
   - Has a fetch index (`byTitleKey`) consuming resources for nothing
   - `Recipe+Extensions.swift` has a dead helper `titleKey(from:)` that should also be removed
   - Action: Remove attribute, fetch index, property declaration, and helper method

2. **Rename `Household.ownerEmail` to `ownerRecordName`**
   - Currently stores `CKCurrentUserDefaultName` (a CloudKit user record ID), NOT an email
   - The field name is misleading and will be permanently misnamed in CloudKit
   - Action: Add new `ownerRecordName` attribute, migrate data, remove `ownerEmail`
   - Note: CloudKit treats this as adding a new field + old field becomes orphaned (acceptable)

3. **Change `Household.mealPlans` delete rule** — Nullify to Cascade
   - All other Household→child relationships use Cascade (recipes, weeklyLists, categories, etc.)
   - mealPlans inconsistently uses Nullify, which would orphan MealPlans when a Household is deleted
   - Action: Change delete rule to Cascade in model editor

4. **Fix `PlannedMeal` code-schema mismatch**
   - `PlannedMeal+CoreDataProperties.swift` declares `household` relationship and `householdKey` attribute
   - Neither exists in the actual Core Data model schema
   - This is dead code that compiles but does nothing (properties are nil at runtime)
   - Action: Either add to schema or remove from properties file
   - Recommendation: Add `householdKey` to schema for consistency with other household-scoped entities

5. **Fix `Household.plannedMeals` missing relationship**
   - Code declares `plannedMeals` relationship on Household
   - Not present in the Core Data model
   - Related to #4 — if PlannedMeal gets a household relationship, Household needs the inverse
   - Action: Add relationship to schema as inverse of PlannedMeal.household

**Acceptance Criteria:**
- [ ] Recipe.titleKey removed with its fetch index
- [ ] Household has `ownerRecordName` field (ownerEmail data migrated)
- [ ] Household.mealPlans uses Cascade delete rule
- [ ] PlannedMeal.household relationship exists in schema (matches code)
- [ ] Household.plannedMeals inverse relationship exists in schema
- [ ] Clean build, all tests pass
- [ ] Lightweight migration from v3 → v4
- [ ] Recipe+Extensions.swift titleKey(from:) helper removed

**Model version:** v4 (separate from M7.6.4's v3 for independent rollback)

### M7.6.6: Core Data Schema Cleanup — P2 Nice to Fix (1-1.5 hours)

**Goal**: Remove unused fields, fix naming inconsistencies, and clean up data hacks.

**Changes:**

1. **Remove `GroceryItem.ingredientTemplate` and `stapleItems`** — Never used
   - `ingredientTemplate` relationship declared but never populated
   - `stapleItems` relationship declared but never populated
   - These are remnants of an early design that was superseded
   - Action: Remove from schema

2. **Remove `GroceryListItem.isFromRecipe`** — Write-only field
   - Set to `true` when adding from recipe, but never read by any code
   - The `contributingRecipes` relationship (M4.3.1) replaced this flag
   - Action: Remove from schema

3. **Add `Recipe.tags` attribute** — Replace sourceURL hack
   - `Recipe.sourceURL` currently stores tags as `"tags:tag1,tag2"` format
   - This prevents ever using `sourceURL` for its intended purpose (linking to recipe sources)
   - Action: Add a `tags` String attribute to Recipe, migrate tag data from sourceURL prefix
   - Clear sourceURL values that only contained tag data

4. **Standardize date naming** — `dateCreated` vs `createdDate`
   - Some entities use `dateCreated`, others use `createdDate`
   - Pick one convention and standardize
   - Note: CloudKit field names are permanent once deployed, so choose carefully
   - Recommendation: `dateCreated` (matches Apple conventions)

5. **Fix `byisActiveandstateDate` index typo**
   - Missing space/capitalization in compound index name
   - Should be `byIsActiveAndStateDate` or similar
   - Action: Rename the fetch index

6. **Verify default value quote encoding**
   - Some default values in the model XML show `&quot;&quot;` instead of `""`
   - Verify this is normal XML encoding and not causing issues
   - Action: Inspect and fix if needed (likely just XML encoding, no action needed)

7. **Add missing `Household` code declarations for `groceryItems` and `groceryListItems`**
   - Schema defines both relationships (with Cascade delete, inverseName on GroceryItem/GroceryListItem)
   - `Household+CoreDataProperties.swift` does NOT declare either property or accessors
   - Inverse side works fine (`GroceryItem.household`, `GroceryListItem.household`)
   - Action: Add `@NSManaged` properties and generated accessors to `Household+CoreDataProperties.swift`
   - Note: This is a code-only fix, no schema change needed

## Risk Mitigation

| Risk | Mitigation |
|------|------------|
| Apple rejects for missing privacy policy | M7.0 already completed — privacy policy published and linked |
| CloudKit schema deploy fails | Test all schema changes thoroughly in Development first |
| Lightweight migration fails | Test v2→v3 migration with existing data before submitting |
| Schema changes break existing users | Only internal TestFlight users exist — can guide them through reinstall if needed |
| Apple review takes longer than 48h | Work on M7.7 during the wait |

## Common Rejection Reasons

1. **Privacy policy inaccessible** — Verify URL resolves before submission
2. **App name too similar to existing apps** — "forager" is distinctive when paired with subtitle
3. **CloudKit not functional** — Test household sharing on 2 devices before submission
4. **Incomplete App Privacy** — Must show "Complete" status in App Store Connect
5. **Debug UI visible** — M7.6.2 addresses this specifically
6. **Crashes on launch** — Test fresh install on physical device
