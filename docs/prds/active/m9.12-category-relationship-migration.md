# M9.12: Category String → Relationship Migration (PRD)

## Context

IngredientTemplate stores its category as `category: String?` — a plain text field like `"Produce"` or `"Dairy"`. This creates several problems:

1. **Category renames don't propagate** — renaming "Bread & Frozen" → "Bread & Bakery" in ManageCategoriesView doesn't update the 50+ templates still referencing the old string.
2. **String matching is fragile** — case sensitivity, whitespace, and normalization differences cause silent mismatches.
3. **No referential integrity** — deleting a Category leaves templates with orphaned string references.
4. **Inconsistency** — GroceryItem already has `categoryEntity: Category?` (added in v7, actively used by AddStapleView/EditStapleView/ManageCategoriesView). IngredientTemplate is the last major entity still using string-based categories.

**Trigger**: M10.6.20 architecture audit revealed the GroceryItem.categoryEntity relationship was already live (not a future M9.12 concern as ADR 012 assumed). The pattern is proven and working — time to apply it to IngredientTemplate.

**ADR 012 mandate**: "Fix category integrity separately via M9.12 (category string → Category entity relationship)... M9.12 is the right structural fix."

## Scope

Two entities need `categoryEntity: Category?`. Implemented as two phases (separate branches/PRs) sharing the same v8 schema:

| Entity | String Field | Locations | Cross-Store Risk | Phase |
|--------|-------------|-----------|-----------------|-------|
| **IngredientTemplate** | `category: String?` | 50+ across 27 files | None (both HouseholdScoped, migrate together) | Phase A |
| **GroceryListItem** | `categoryName: String?` | 16+ across 11 files | None (travels with WeeklyList, same store as Category) | Phase B |

**ADR 012 rationale for GroceryListItem**: "Renaming a category is correcting a label, not changing history." The `categoryEntity` relationship fixes organizational labels. The snapshot semantics (name, displayText, numericValue) are preserved — those remain flat strings. Only the category label gets a live relationship.

**CloudKit**: Append-only safe — new relationships, no destructive changes.

### Cross-Store Safety Analysis

**IngredientTemplate**: Both IngredientTemplate and Category are `HouseholdScoped`. During household creation, both migrate from private → shared store together. During leave-household, both are copied back together. **No cross-store risk.** Reverse migration needs relationship remapping via `categoryMapping` (built at `HouseholdService.swift:900-924` but currently unused — line 959 copies the string directly). M9.12 must wire up `categoryMapping` consumption for `newTemplate.categoryEntity`.

**GroceryListItem**: Scoped indirectly through `weeklyList: WeeklyList?` (WeeklyList is HouseholdScoped). When WeeklyList migrates to shared store, its GroceryListItems travel with it (same store). Category also migrates to shared store. **No cross-store risk.** Reverse migration copies GroceryListItems as part of WeeklyList copying — `categoryEntity` needs remapping via `categoryMapping`.

**GroceryItem** (staples, for reference): Already handled by M10.6.20. GroceryItem stays in private store while Category moves to shared → cross-store risk exists and is repaired at startup.

### Index Impact

The existing `byTemplateSearch` and `byIngredientManagement` indexes reference the `category` string field. After M9.12, code stops querying by `category` string. These indexes become partially dead weight but cause no harm. No new indexes needed for `categoryEntity` since relationship traversal uses Core Data's built-in indexing.

### Critical Finding: categoryMapping Is Built But Unused

`HouseholdService.migratePersonalDataToHousehold()` builds a `categoryMapping: [UUID: Category]` dictionary (lines 900-924) mapping old household Category IDs to newly created personal Categories. However, **no code currently consumes this mapping**:

- **Line 959**: `newTemplate.category = oldTemplate.category` — copies string directly, ignores mapping
- **Line 1059**: `newItem.categoryName = oldItem.categoryName` — copies string directly, ignores mapping
- **Lines 930-935**: GroceryItem re-linking uses **name-based lookup** instead of categoryMapping

M9.12 must wire up `categoryMapping` consumption at lines 959 and 1059 to properly link `categoryEntity` on copied templates and list items to the correct personal-store Category entities.

### GroceryItem.category References (NOT in M9.12 Scope)

HouseholdService has GroceryItem.category (not IngredientTemplate) references at:
- **Lines 930, 1514-1515**: Break/preserve cross-store GroceryItem→Category relationships during household migration
- **Lines 2316-2317**: `repairCrossStoreGroceryItemRelationships()` startup repair

These are M10.6.20 infrastructure for the GroceryItem cross-store problem and are **not affected by M9.12**.

## ADR 013 Scope Compliance Note

Pre-existing issue: 11+ `@FetchRequest` declarations for Category in views lack `householdKey` predicates (they rely on in-memory filtering). This is **not introduced or worsened by M9.12** — the new `categoryEntity` relationship naturally resolves to the correct-scope Category since templates and categories always live in the same store. No new ADR 013 risk.
