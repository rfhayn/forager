## 1. Overview

M10.5 corpus testing (50 recipes, 442 ingredient lines) revealed **295 errors** across classification and parsing. An LLM-assisted review (5 parallel Claude agents, one per difficulty category) identified **7 systematic bug patterns** responsible for the majority of failures. A Foundation Models (on-device Apple Intelligence) comparison test showed FM achieves 78.7% quantity extraction vs the pipeline's 65.2% — but FM suffers from systematic hallucinations making it unreliable as a numeric extraction replacement.

This PRD documents:
- **Section A**: Foundation Models evaluation findings and verdict
- **Section B**: Pipeline error analysis — 7 systematic bugs with fix specifications
- **Section C**: External LLM API integration design (Claude → GPT → Gemini)
- **Section D**: Milestone structure and phased rollout

## 2. Section A — Foundation Models Evaluation

### 2.1 Methodology

**Corpus**: 50 recipes across 5 difficulty categories (clean, no-headers, unusual-metadata, messy, international), 442 total ingredient lines.

**Pipeline tested**: OCRLineClassifier → HybridIngredientParser (regex tier 1 → ML BiLSTM-CRF tier 2 → NLP tier 3).

**FM tested**: `FoundationModelsIngredientParser` using Apple's Foundation Models framework with `@Generable` structured output. Batch processing per recipe (one LLM call per recipe, not per line).

**Comparison approach**: Both parsers run on the same 442 lines. Results compared field-by-field (quantity, unit, name). Disagreements logged for manual review.

### 2.2 Results Summary

| Metric | Pipeline (before) | Pipeline (after fixes) | Foundation Models |
|--------|-------------------|----------------------|-------------------|
| Qty extracted | 288/442 (65.2%) | 421/477 (88.3%) | 303/477 (63.5%) |
| Disagreements | — | — | 210 lines |
| FM fixes pipeline gaps | — | — | 33 lines |
| FM introduces errors | — | — | ~50+ lines |
| Batch count mismatches | — | — | 7/50 recipes |

**Pipeline (before)**: ML 81.7%, regex 18.3%, NLP 0%. Classification avg 0.520 (low), parsing avg 0.932.
**Pipeline (after fixes)**: regex 79.8%, ML 20.2%, NLP 0%. Classification avg 0.641, parsing avg 0.984.
**Post-fix verdict**: Pipeline now beats FM on quantity extraction (88.3% vs 63.5%).

### 2.3 FM Hallucination Catalog

Foundation Models exhibited consistent, reproducible hallucination patterns:

#### H1: Gram-to-Kilogram Conversion (Critical)
FM converts grams to kilograms uninstructed. `250g chickpeas` → `qty=0.25, unit=g` (should be `qty=250, unit=g`). Also observed with `200g peas` → `qty=0.2, unit=g`, `300g frozen peas` → `qty=0.3, unit=g`. This is a silent, destructive error — the resulting quantity is 1000x too small.

#### H2: Unprompted Unit Conversions
FM converts between unit systems without being asked. `Dash of olive oil` → `qty=0.5, unit=tbsp` (should be `qty=nil, unit=dash`). `1 cucumber` → `qty=1, unit=g` (invented unit). These demonstrate the model "helpfully" normalizing in ways that corrupt the original data.

#### H3: Wrong Unit Assignments
FM assigns semantically incorrect units. `4 slices bread` → `unit=clove` (should be `slice`). `4 chopped spring onions` → `unit=clove`. The model conflates count-unit nouns.

#### H4: Quantity Regressions
FM occasionally loses quantities the pipeline found. `1 tablespoon olive oil` → `qty=nil` (pipeline correctly finds `qty=1, unit=tbsp`). `1 onion` → `qty=nil`. `1 clove garlic` → `qty=nil`. These are basic lines the pipeline handles correctly.

#### H5: Batch Count Mismatches
7/50 recipes returned a different number of results than input lines. When the FM output count doesn't match, the entire recipe comparison is voided. This makes batch processing unreliable without per-line fallback.

### 2.4 FM Verdict

**FM is NOT reliable for numeric extraction.** The hallucination patterns (especially H1: gram-to-kg and H4: quantity regressions) make FM unsuitable as a primary ingredient parser for the structured data pipeline.

**FM IS valuable for soft tasks** where exact numeric fidelity is not required:
- Category suggestion (assigning ingredients to grocery categories)
- Template deduplication (recognizing "butter" and "unsalted butter" as the same ingredient)
- Section detection (classifying lines as ingredient vs instruction vs metadata)
- OCR error correction (fixing common OCR artifacts)

**Strategic direction**: FM augments the deterministic pipeline for soft tasks. External LLM APIs (Claude, GPT, Gemini) serve as the primary high-accuracy parser, with the regex→ML→NLP pipeline as the always-available offline fallback.

## 3. Section B — Pipeline Error Analysis

### 3.1 Error Distribution

Total errors from LLM corpus review: **295**
- Classification errors: ~146
- Parsing errors: ~149

### 3.2 Root Cause: Leading Bullet Prefix (Fix 1)

**Impact**: ~70% of all 295 errors (~206 errors)
**Root cause**: Recipe lines from web extraction commonly start with `"- "`, `"• "`, `"* "`, or numbered `"1. "` prefixes. Both `OCRLineClassifier.startsWithNumber()` and `RegexIngredientParser`'s `^`-anchored patterns fail because the prefix obscures the actual content.

**Example**: `"- 2 cups flour"` → `startsWithNumber()` sees `"-"` (not a digit) → ingredient score misses +0.5 bonus → classified as unknown. In regex parser, `^(\d+...)` fails to match because `"-"` is at position 0.

**Fix specification**:
- **OCRLineClassifier**: Strip bullet/list prefixes at the start of `classifyLines()` before scoring
- **RegexIngredientParser**: Strip bullet/list prefixes at the start of `parse()` before regex matching
- **Prefix regex**: `^\s*[-•*]\s+` and `^\s*\d+[.)]\s+` (bullet/dash/star and numbered list)
- **Critical**: Only strip for scoring/parsing — preserve original text in output

### 3.3 Bug 2: Metric No-Space Pattern (Fix 2)

**Impact**: ~120 parsing failures
**Root cause**: The existing pre-processor handles `"16oz"` → `"16 oz"` but only for letter suffixes. Metric patterns like `"400g"`, `"250ml"`, `"1.5L"` need explicit handling because `g`, `ml`, and `L` are single-character units that the generic `\d+[a-zA-Z]` pattern doesn't separate correctly with unit recognition.

**Example**: `"400g mushrooms"` → pre-processor produces `"400 g mushrooms"` but `g` isn't matched as a unit in `tryStandardPatternInternal()` because the pattern captures `g` as a potential unit, then `isKnownUnit("g")` should return true (it's in the weight map). Actually, the real issue is that after bullet stripping (Fix 1), `"- 400g mushrooms"` becomes `"400g mushrooms"`, and the existing pre-processor `^(\d+(?:\.\d+)?)\s*([a-zA-Z])` should handle this. **Fix 1 resolves most of these.** However, patterns like `"400g"` (no space between number and unit) should be explicitly handled for robustness.

**Fix specification**:
- Add specific metric unit patterns to the pre-processor: `^\d+\s*[gG](?:rams?)?(?=\s|$)` → separate number from unit
- Also handle `ml/mL/ML` and `[lL]` patterns
- Add `"large"` to units that should NOT be treated as the `l` unit alias

### 3.4 Bug 3: Unit-Less Count Items (Fix 3)

**Impact**: ~30 classification failures
**Root cause**: `scoreIngredient()` gives +0.5 for `startsWithNumber()` and +0.35 for `containsUnitWord()`. Lines like `"2 eggs"` get only +0.5 + 0.1 (short line) = 0.6, which is below the instruction score for numbered patterns. The regex parser's `tryStandardPatternInternal()` captures `eggs` as a non-unit word and routes it to the name, but without unit recognition, confidence stays low.

**Fix specification**:
- **RegexIngredientParser**: Add a count-noun fallback after `tryStandardPattern()` that matches `^\d+\s+<count_noun>` patterns
- Count-noun list: egg/eggs, leaf/leaves, bay leaf/bay leaves, clove/cloves, sprig/sprigs, stalk/stalks, strip/strips, sheet/sheets, fillet/fillets, breast/breasts, thigh/thighs, drumstick/drumsticks, rasher/rashers
- These get `unit: nil` but higher confidence (0.85) than the bare fallback (0.0)

### 3.5 Bug 4: Bare Name Ingredients (Fix 4)

**Impact**: ~15 classification failures
**Root cause**: `scoreIngredient()` returns 0.0 for lines with no number, no unit, no fraction. Lines like `"celery"`, `"salt and pepper"`, `"passata"` fall through to unknown.

**Fix specification**:
- **OCRLineClassifier**: Add `containsBareIngredientName()` helper with a curated list of ~40 common bare ingredients
- List includes: salt, pepper, oil, olive oil, butter, flour, sugar, water, celery, parsley, cilantro, basil, thyme, rosemary, oregano, cinnamon, paprika, cumin, garlic, ginger, honey, vinegar, mustard, ketchup, mayo, mayonnaise, cream, milk, cheese, rice, pasta, bread, lettuce, spinach, arugula, passata, stock, broth, wine, beer, soy sauce, fish sauce, sesame oil, cornstarch
- Gives +0.3 ingredient score when matched

### 3.6 Bug 5: Unusual Metadata Patterns (Fix 5)

**Impact**: ~47 classification failures
**Root cause**: `scoreMetadata()` only checks serving/time/yield/temperature patterns. Many metadata lines use other labels: `"Difficulty: Easy"`, `"Author: Jamie Oliver"`, `"Cuisine: Italian"`, `"Source: BBC Good Food"`.

**Fix specification**:
- **OCRLineClassifier**: Add a new regex pattern to `scoreMetadata()` matching `^(difficulty|author|cuisine|source|category|course|diet|skill|level|rating)\s*:` with a score of +0.6
- These are metadata, not ingredients or instructions

### 3.7 Bug 6: Mixed Fraction with Hyphen (Fix 6)

**Impact**: ~10 parsing failures
**Root cause**: `convertToNumeric()` handles `"1 1/2"` (space separator) but not `"2-1/2"` (hyphen separator). The mixed fraction regex `^(\d+)\s+(\d+)/(\d+)` requires a space.

**Fix specification**:
- **RegexIngredientParser**: In `convertToNumeric()`, change the mixed fraction pattern from `^(\d+)\s+(\d+)/(\d+)$` to `^(\d+)[-\s]+(\d+)/(\d+)$` to accept both space and hyphen separators

### 3.8 Bug 7: Parenthetical Prep Methods (Fix 7)

**Impact**: ~15 parsing failures
**Root cause**: The qualifier pattern (Pattern 6) handles `"garlic, minced"` but not parenthetical prep like `"butter (softened)"` or `"chicken thighs (cubed)"`. Parenthetical prep notes get included in the ingredient name.

**Fix specification**:
- **RegexIngredientParser**: Add parenthetical prep extraction early in the `parse()` method
- Pattern: `\s*\(([^)]+)\)\s*` — capture content inside parentheses
- Extract as `notes`, strip from ingredient name
- Apply before main pattern matching so cleaned text flows through existing patterns
- Common parenthetical preps: softened, melted, diced, cubed, chopped, sliced, crushed, thawed, room temperature, at room temperature, drained, rinsed, optional

### 3.8 Remaining Gaps (Post-Fix Round 2)

After implementing Fixes 1-7 (round 1) and Fixes 8-10 (round 2), the FM comparison test shows **25 lines** where the pipeline returns `qty=nil` but FM extracted a quantity (down from 33 after round 1).

**Round 2 fixes applied:**
- **Fix 8**: Expanded descriptive amount patterns (`bunch`, `sprinkling`, `squeeze`) + qualifier patterns (`for dusting`, `for glazing`, `to serve`, `to garnish`, `for garnishing`)
- **Fix 9**: "Juice/Zest of X" prefix-before-quantity pattern (e.g., `"Juice of 1/2 lemon"` → qty=0.5)
- **Fix 10**: Temperature-as-metadata classification (`"Oil temperature: 350F"` → metadata, not ingredient)

**Impact**: FM-fixes-gaps reduced from 33 → 25 (8 fewer gaps, 24% improvement).

**Remaining 25 gaps — categorized:**
- **"X to serve"** (~7): `"Sugar to serve"`, `"Raspberries to serve"`, `"Bread to serve"` — no quantity in text, FM hallucinates one
- **Prose-embedded** (~5): Quantities inside instruction sentences — beyond regex capability
- **Ambiguous multi-ingredient** (~5): `"salt and pepper"`, `"mixed peel"` — unclear how to assign a single quantity
- **Genuinely absent** (~8): Lines where no quantity exists in the original text — FM invents one

**Verdict**: These 25 gaps are **intentionally left for LLM integration** (M10.6). The deterministic pipeline has reached its practical ceiling for regex-based extraction.

## 4. Section C — External LLM API Integration Design

### 4.1 Strategic Rationale

The FM evaluation (Section A) proved that on-device LLM has accuracy advantages over the deterministic pipeline but suffers from hallucinations and availability constraints. External LLM APIs (Claude, GPT, Gemini) offer:
- Higher accuracy than on-device FM (larger models)
- Consistent availability (cloud-based, not device-dependent)
- Structured output guarantees (tool use / function calling)
- No hallucination patterns observed in FM evaluation (hypothesis — needs validation)

The trade-off is latency (network round-trip) and cost (user pays per API call).

### 4.2 Architecture: LLMIngredientParser Protocol

```swift
/// Protocol for LLM-based ingredient parsing with provider abstraction
protocol LLMIngredientParser {
    /// Parse a batch of ingredient lines in a single API call
    func parseBatch(_ lines: [String]) async throws -> [LLMParserResult]

    /// Provider identifier for telemetry
    var providerName: String { get }

    /// Check if this provider is configured and available
    var isConfigured: Bool { get }
}

/// Result type matching ParserResult fields
struct LLMParserResult {
    let name: String
    let quantity: Double?
    let unit: String?
    let notes: String?
    let confidence: Float  // Always high (0.95) for LLM — confidence is binary
}
```

### 4.4 Auth Flow — OAuth Research Findings

**OAuth is not viable for any major LLM provider.** API keys are the only universal approach.

#### Provider-Specific Findings

| Provider | OAuth Status | Auth Method |
|----------|-------------|-------------|
| **Anthropic (Claude)** | **Banned.** Third-party OAuth explicitly prohibited (Jan 9 2026 enforcement, Feb 19 2026 policy update). Apps cannot authenticate users via Anthropic accounts. | API keys via Console |
| **OpenAI (GPT)** | **Not available for this use case.** OAuth flows in the Apps SDK are for ChatGPT connecting to *your* backend (actions), not for your app calling the OpenAI API. | API keys via Platform |
| **Google (Gemini)** | **Possible but complex.** Google Sign-In + OAuth consent screen review adds significant friction. Only viable if using other Google APIs already. | API keys via AI Studio (simpler) |

#### Conclusion: API Keys Only

All three providers require API keys for programmatic access. The UX mitigation strategy:
1. **Deep links** to provider API key pages (one-tap navigation to Console/Platform/AI Studio)
2. **Clipboard auto-detect** on paste (recognize API key format, auto-fill SecureField)
3. **"Test Connection" button** — validate with a minimal parse call before saving
4. **Keychain storage** — `KeychainService.save(key: "llm_api_key_claude", value: apiKey)` (hardware-encrypted)

**Security model**: API key never leaves the device except in HTTPS requests to the provider's API. No server-side proxy. User controls their own keys.

**The app is fully functional without any LLM integration.** The deterministic pipeline (regex → ML → NLP) handles 88%+ of ingredient lines. LLM integration is a power-user enhancement, not a requirement.

### 4.6 Integration Points

#### Primary: RecipeImportService
```swift
// In RecipeImportService.extractIngredients()
func extractIngredients(from lines: [String]) async -> [ParserResult] {
    // 1. Try LLM API (if configured + opt-in)
    if let llmParser = LLMParserFactory.activeParser() {
        do {
            let results = try await llmParser.parseBatch(lines)
            return results.map { $0.toParserResult() }
        } catch {
            // Fall through to pipeline
        }
    }

    // 2. Try on-device FM (if available)
    if FoundationModelsIngredientParser.isAvailable {
        if let results = await fmParser.parseBatch(lines) {
            return results.map { $0.toParserResult() }
        }
    }

    // 3. Deterministic pipeline (always available)
    return lines.map { pipelineParser.parse($0) }
}
```

#### Secondary: Manual Ingredient Entry (Two-Speed)
For manual entry in recipe creation, the LLM API adds a "smart parse" mode:
- **Fast path**: User types → deterministic pipeline parses → instant structured result
- **Smart path**: User taps "AI Parse" → LLM API → higher accuracy result with prep extraction

This is a future enhancement (M10.7+), not part of the initial integration.

### 4.7 Fallback Chain

```
User input
  ↓
[LLM API configured?] → Yes → API call → Success → Return results
  ↓ No                          ↓ Fail
[FM available?] → Yes → FM call → Success → Return results
  ↓ No                    ↓ Fail
[Deterministic pipeline] → regex → ML → NLP → Return results
```

Each level is fully independent. The pipeline always works offline with no configuration.

### 4.8 Prompt Engineering

The LLM prompt uses structured output (tool use) to ensure consistent JSON:

```
System: You are an ingredient parser for a grocery app. Parse each line into structured components.

Rules:
- Extract quantity as a decimal number (e.g., "1/2" → 0.5, "2 1/2" → 2.5)
- Standardize units: tablespoon/tbsp/tbs → "tbsp", teaspoon/tsp → "tsp", etc.
- Separate preparation notes from the ingredient name
- Count items (2 eggs) have quantity but no unit
- Bare names (salt, pepper) have no quantity or unit
- Preserve the original ingredient name casing
- Do NOT convert between unit systems (keep grams as grams, cups as cups)

User: Parse these ingredient lines:
1. 400g mushrooms
2. 2 cups flour, sifted
3. salt and pepper to taste
```

Tool definition ensures output matches `LLMParserResult` schema exactly. No free-form text parsing needed.

### 4.9 Cost & Privacy Considerations

**Cost model**: User pays their own API costs directly to the provider.
- Claude Haiku: ~$0.001 per recipe (10-15 ingredient lines, ~500 input tokens)
- GPT-4o-mini: ~$0.0005 per recipe
- Gemini Flash: ~$0.0002 per recipe
- Typical user imports 5-20 recipes/month → $0.005-$0.02/month

**Privacy model**:
- No data leaves the device without explicit opt-in (toggle must be ON)
- Only ingredient text is sent — no recipe titles, URLs, or personal data
- No server-side proxy — direct HTTPS to provider API
- API key stored in iOS Keychain (hardware-encrypted on-device)
- User can delete their key at any time from Settings

### 4.10 Household API Key Sharing

When a household is configured (M7 CloudKit Shared Store), the API key can be shared across all household members automatically:

- **Household owner** configures API key in Settings → stored in a household-scoped entity (CloudKit shared store)
- **All household members** automatically receive the key via CloudKit sync — no manual distribution needed
- **Member leaves household** → they lose access to the shared store (CloudKit enforces this automatically)
- **Owner rotates/revokes key** → change syncs to all members via CloudKit

**Architecture**: Extend existing `UserPreferences` entity (already has `household` relationship) with `llmAPIKey: String?` field, or add a new `HouseholdSettings` entity in the shared store. Decision deferred to M10.6 implementation.

**Security note**: CloudKit shared zone is accessible to all zone participants — the key is visible to all household members. This is acceptable since the owner explicitly chose to share the household. Non-household users store their key locally in iOS Keychain (personal use, no sharing).

### 4.11 Future: Subscription Model

A future paid subscription tier could provide built-in LLM parsing via a server-side proxy:
- User subscribes → app calls our server → server calls LLM → results returned
- **Eliminates all API key friction** — no key management, no household sharing complexity, just a subscription toggle
- Server-side proxy also enables: rate limiting, usage analytics, model selection, prompt optimization
- Revenue model: ~$1-2/month covers typical usage (5-20 recipes/month at <$0.02/month LLM cost)

**Not an M10.6 deliverable** — this is a future revenue consideration. Current approach (user-provided API keys) is the right first step to validate demand before building server infrastructure.

### 4.12 Error Handling

| Error | User Message | Fallback |
|-------|-------------|----------|
| Invalid API key | "Your API key is invalid. Check Settings → AI Import." | Pipeline |
| Rate limited (429) | Silent retry (3 attempts, exponential backoff) | Pipeline after 3 fails |
| Network unavailable | Silent fallback | Pipeline |
| Provider outage (5xx) | Silent fallback | Pipeline |
| Malformed response | Silent fallback | Pipeline |
