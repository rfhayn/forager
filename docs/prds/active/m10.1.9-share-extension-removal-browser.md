## 1. Background & Motivation

### Share Extension UX Failure

M10.1.7 delivered a functional iOS Share Extension for recipe import. However, the UX was poor:

- The share sheet popup appears briefly, flashes, and disappears
- The user must manually switch to Forager after sharing
- No visual feedback of import progress during the handoff
- Race condition between URL scheme handoff and scenePhase detection

The share extension architecture worked technically (App Group UserDefaults handoff, URL scheme, scenePhase fallback), but the resulting user experience didn't meet the "it should feel native" bar.

### Decision: Replace with In-App Browser

After evaluating the UX, the decision was made to:

1. **Remove** the entire share extension (no tech debt)
2. **Replace** with a Paprika-style in-app WKWebView browser
3. **Fix** ingredient categorization bug discovered during import testing

The in-app browser provides a significantly better UX:
- User stays in Forager throughout the entire flow
- Visual progress bar during page load
- "Import This Recipe" button when ready
- Direct transition to preview/save flow — no app switching

### Categorization Bug

During import testing, `categorizeIngredient()` was found to return hardcoded category names that don't match the seeded Category defaults:

| `categorizeIngredient()` returns | Seeded default |
|---|---|
| "Meat & Seafood" | "Deli & Meat" |
| "Dairy" | "Dairy & Fridge" |
| "Pantry" | "Bread & Frozen" / "Boxed & Canned" |
| "Other" | "Snacks, Drinks, & Other" |

Only "Produce" matched. This created phantom category strings on templates that don't correspond to any real Category entity.

## 2. Implementation

### Commit 1: Remove Share Extension

**Scope**: Clean removal of all M10.1.7 share extension code.

**Deleted**:
- `ForagerShareExtension/` directory (ShareViewController.swift, Info.plist, ForagerShareExtension.entitlements)

**Modified**:
- `foragerApp.swift` — Removed `showShareImport`, `scenePhase`, `.onOpenURL`, `.onChange(of: scenePhase)`, share sheet presentation
- `forager.entitlements` — Removed `com.apple.security.application-groups` (only used for share extension)
- `RecipeImportService.swift` — Removed `checkForPendingImport()` method
- `project.pbxproj` — Removed ~28 entries across 9 pbxproj sections

**Preserved**: `importService` as app-level `@StateObject` + `.environmentObject()` (needed by browser)

### Commit 2: Add In-App WKWebView Browser

**New files**:
- `Services/Import/RecipeBrowserViewModel.swift` — `@Observable` class managing WKWebView state via KVO; extracts recipe HTML from current page
- `forager/RecipeBrowserView.swift` — Full-screen browser with address bar, nav controls, progress bar, "Import This Recipe" button

**Modified**:
- `RecipeListView.swift` — Import toolbar button changed to `Menu` with "Browse for Recipe" (fullScreenCover) and "Paste URL" (sheet)
- `project.pbxproj` — Added RecipeBrowserView entries

**Architecture**:
- Browser reuses `RecipeJSONLDExtractor.extractRecipeDict()` + `SchemaRecipeMapper.map()` — same extraction pipeline as `WKWebViewExtractor`
- No 2-second settle delay needed (user already waited for page to load, unlike headless rendering)
- Extraction result sets `importService.state = .needsReview(draft)` and presents `RecipeImportSheet` as sheet

### Commit 3: Fix Ingredient Categorization (M10.1.10)

**Modified**:
- `IngredientParsingService.swift` — Removed `categorizeIngredient()` method entirely; call site now passes `category: nil`
- `RecipeImportService.swift` — Added `ImportSaveResult` struct; `saveImport()` and `replaceExistingRecipe()` return recipe ID + uncategorized template IDs
- `RecipeImportSheet.swift` — Wired `CategoryAssignmentModal` into save flow; presents after save when uncategorized templates exist

**Pattern**: Same integration as `CreateRecipeView`'s `formData.uncategorizedTemplates` → `CategoryAssignmentModal` pattern. Templates with `category == nil` trigger the modal.

## 5. Post-Ship Bug Fixes (M10.1.10 continued)

### Commit 4: Increase Validation Limits

**Problem**: `IngredientTemplate.name` validation limit of 100 characters caused save failures on imported recipes with verbose ingredients (e.g., "1 ounce (about ⅓ packed cup) grated pecorino Romano, plus additional for serving").

**Fix**:
- `IngredientTemplate+Validation.swift` — name limit: 100 → 250 characters
- `Recipe+CoreDataClass.swift` — title limit: 100 → 300 characters

### Commit 5: HTML Metadata Title Enhancement

**Problem**: JSON-LD `name` field is unreliable across recipe sites. NYT Cooking's "Spaghetti Carbonara" recipe has `"name": "Carbonara"` in its JSON-LD — the full title only exists in the `og:title` meta tag.

**Fix**: Added `RecipeJSONLDExtractor.enhanceTitleFromHTML()` — a post-extraction step that:
1. Extracts `og:title` from HTML meta tags
2. Extracts `<title>` tag content as fallback
3. Only enhances when metadata title is longer AND contains the JSON-LD name (containment safety check)
4. Strips common suffixes (" Recipe", " - Site Name", " | Site Name")

Wired into all three extraction paths:
- `RecipeJSONLDExtractor.extract()` — standard JSON-LD path
- `WKWebViewExtractor.extract()` — headless rendering fallback
- `RecipeBrowserViewModel.extractRecipeFromCurrentPage()` — in-app browser
