## S1 Overview

### 1.1 Problem Statement

**Tier 1 (COMPLETE)** solved the core problem: imported `imageURL` now persists and displays. Remaining gaps:
- Images depend on web availability — if the source site changes URL or goes offline, the image disappears
- Manually created recipes have no image
- No user control over image selection, cropping, or replacement

### 1.2 Current State (post-Tier 1)

- `Recipe.imageURL: String?` persists and displays across detail + list + grid
- `AsyncImage` handles network fetch + in-memory URLCache
- **No local disk cache** — every app launch re-fetches over network
- **No camera/library integration** for manually created recipes
- Core Data model is v11 (includes imageURL, no localImagePath yet)

### 1.3 Design Principles

- **Progressive enhancement** — recipes work fine without images; images are a bonus
- **Import-first** — prioritize web URL images from imports before camera/library for manual
- **Lightweight schema** — minimize Core Data + CloudKit impact
- **Offline-aware** — consider what happens when web URLs go stale

## S2 Tiered Implementation

### Tier 1: Persist Import Image URLs (3-4h) — COMPLETE (shipped as M10.4.0)

The simplest path: save the web URL string from import drafts so it survives beyond the preview screen.

**Schema change:**
- Add `imageURL: String?` (Optional) to `Recipe` entity
- New model version: v6 → v7
- Lightweight migration (additive attribute, no data transform)
- CloudKit: new field auto-propagates (append-only, safe)

**Code changes:**
- `RecipeImportService.saveImport()` — persist `draft.imageURL.value` to `recipe.imageURL`
- `RecipeImportService.replaceExistingRecipe()` — same
- Recipe detail view — `AsyncImage(url:)` hero image at top
- Recipe list rows — small thumbnail via `AsyncImage` with placeholder
- Meal plan cards — optional thumbnail

**Pros:**
- Minimal schema change (1 attribute)
- Zero local storage management
- `AsyncImage` handles caching automatically (URLCache)
- Fast to implement

**Cons:**
- Images break when sites change URLs or go offline
- No images for manually created recipes
- No user control over images
- Depends on network availability

### Tier 2: Local Image Cache + Download (8-12h) — POST-LAUNCH

Download imported images to the app's Documents directory for offline access.

**Adds to Tier 1:**
- `ImageCacheService` — download web image → save to `Documents/RecipeImages/{recipeID}.jpg`
- `Recipe.localImagePath: String?` — new attribute pointing to local file
- Display priority: local file → web URL → placeholder
- Cleanup: delete local image when recipe is deleted
- Background download: fetch image after save, not blocking the save flow
- Compression: resize to max 1024px wide, JPEG at 0.8 quality (~100-200KB per image)

**Storage estimate:** 200 recipes x 150KB = ~30MB — well within reason.

**CloudKit consideration:** Local image files don't sync via CloudKit by default. Options:
- Accept images are device-local (simplest)
- Use `CKAsset` on the Recipe record (complex, bandwidth-heavy)
- Store in iCloud Documents container (medium complexity)

### Tier 3: Full Image Support — Camera + Library (16-20h) — FUTURE

Add image capture/selection for manually created recipes.

**Adds to Tier 2:**
- `PhotosPicker` integration in `CreateRecipeView` — select from library
- Camera capture option in recipe editing
- Image editing: crop to aspect ratio, basic brightness/contrast
- Multiple images per recipe (hero + step photos)
- Schema: `RecipeImage` entity (one-to-many with Recipe) vs single `imageURL`

**Architectural decision needed:** Single image per recipe (simpler) vs multiple images (richer but significantly more complex — new entity, relationship management, UI for image gallery).

## S5 Key Risks and Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| Web URLs go stale (site redesign, CDN change) | Images disappear for imported recipes | Tier 2 local cache; placeholder graceful fallback |
| CloudKit schema is append-only | Can't remove `imageURL` if approach changes | Attribute is Optional String — low-risk, can be ignored |
| Storage growth (Tier 2+) | Disk usage with many recipes | Compress to 150KB, cap at ~500 images, offer "Clear image cache" in Settings |
| Performance — list scrolling with images | Jank on older devices | `AsyncImage` with `.thumbnail` hint; lazy loading; fixed-size frames |
| Extraction reliability | Not all recipe sites expose image URLs | Already handled — `imageURL` is Optional in ImportDraftRecipe, UI shows placeholder when nil |
