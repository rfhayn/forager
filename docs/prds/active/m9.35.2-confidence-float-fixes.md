# M9.35.2: Parsing Pipeline — Confidence Fix + Float Conversion

**Status**: ACTIVE
**Estimated**: 3-4 hours
**Priority**: High (145+ prep-in-name issues, 12+ IEEE 754 float display bugs)
**Last Updated**: March 25, 2026
**Parent**: M9.35 (Parsing Pipeline Hardening)

---

## Problem Statement

Phone stress test (27 recipes, build 88) confirmed M9.35 Phase 1 (P1-P4) code IS in the build and the preprocessor IS called. However, five issues remain from the stress test:

1. **Prep-in-name (~145 instances)** — comma-qualifier pattern returns 0.70 confidence, below the hybrid router's 0.9 auto-accept. ML parser overrides with wrong parse.
2. **IEEE 754 float bug (12+ instances)** — AllRecipes JSON-LD stores ⅓ as `0.33333334326744`. Users see raw float.
3. **Word-split on "egg" (8 instances)** — Standard regex pattern splits "1 egg" as unit="eg", name="g" → "eg g".
4. **Can/package sizes in names (8+ instances)** — "(28 ounce) can" not stripped by preprocessor.
5. **Orphan fragments (8+ garbage ingredients)** — Multi-word phrases like "cut into wedges" bypass `isOrphanFragment()`.

## Fixes

### Fix 1: Raise comma-qualifier confidence (0.70 → 0.92)

**File**: `Services/Parsing/RegexIngredientParser.swift`
**Location**: `tryQualifierPattern()` — both the standard qualifier and comma-qualifier branches

The comma-qualifier pattern correctly parses "garlic, crushed" → name "garlic" + notes "crushed", but returns 0.70 confidence. The hybrid router's threshold is 0.9, so the regex result falls through to the ML parser which returns ~0.75 with incorrect "garlic crushed". Raising to 0.92 lets the regex auto-win.

### Fix 2: IEEE 754 float → fraction conversion

**File**: `Services/Parsing/IngredientPreprocessor.swift`
**New step**: `convertIEEE754FloatQuantities()` inserted between metric stripping and Unicode fractions.

Detects decimals with 8+ digits after the decimal point and converts to slash fractions:
- `0.33333334326744` → `1/3`
- `0.66666668653488` → `2/3`
- `2.3333332538605` → `2 1/3`

Conservative: only triggers on 8+ digit decimals (user input never has this precision).

### Fix 3: Prevent "egg" word-split in standard pattern

**File**: `Services/Parsing/RegexIngredientParser.swift`
**Location**: `tryStandardPatternInternal()`

The standard regex pattern `^(\d+...)\s+([a-zA-Z]+)?\s*(.+)$` greedily splits "egg" into unit="eg" + name="g". When unit is unrecognized, it recombines as "eg g". Fix: when captured unit is unknown AND remaining name is ≤1 character, return nil to let `tryCountNounPattern` handle it correctly.

### Fix 4: Can/package size stripping

**File**: `Services/Parsing/IngredientPreprocessor.swift`
**New step**: `stripCanPackageSizes()` — strips parenthetical sizes before container words.

`1 (28 ounce) can crushed tomatoes` → `1 can crushed tomatoes`

### Fix 5: Improved orphan fragment detection

**File**: `Services/Parsing/IngredientPreprocessor.swift`
**Change**: Expand `orphanPrepWords` set with connecting words and common noun fragments.

Adds: "into", "of", "the", "and", "for", "with", "until", "to", "wedges", "pieces", "chunks", "strips", "rounds", "slices"

## Verification Criteria

- "garlic, crushed" → name "garlic", notes "crushed" (not "garlic crushed")
- "0.33333334326744 cup butter" → "1/3 cup butter"
- "1 egg" → name "egg" (not "eg g")
- "1 (28 ounce) can crushed tomatoes" → "1 can crushed tomatoes"
- "pitted" and "cut into wedges" filtered as orphan fragments
- All existing tests pass
